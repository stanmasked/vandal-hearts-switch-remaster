# MAP02: владельцы 380 неразрешённых исходных PC-символов

## Подтверждённые входные данные

[PR №410](https://github.com/stanmasked/vandal-hearts-switch-remaster/pull/410) — точный коммит `7fd4db37b52c89d1a5e12a88e8a0700daed77005`, [GitHub Actions №39589950986](https://github.com/stanmasked/vandal-hearts-switch-remaster/actions/runs/39589950986), **35/35 успешно**. Исходная PC-компоновка оставила 493 сильных неопределённых имени после SDL2 и четырёх системных графических архивов. Реальный Ubuntu glibc `ld -r` разрешил 51 через сильные и 62 через слабые экспорты, **380** исходных имён осталось без экспортов `libc.a`/`libm-*.a`. Общий результат полного частичного ELF: 701 сильное неопределённое имя (включая 300 SDL2 и 21 новый импорт glibc).

## Новый исследовательский аудит

`tools/check_map02_public_pc_unresolved_module_owners.py` не пытается подключить случайные библиотеки. Вместо этого он определяет, какие из уже скомпилированных оригинальных PC-модулей **используют** каждое из 380 всё ещё неразрешённых исходных имён.

Проверяются четыре конкретных ELF `ET_REL` (исходный 520, после SDL2 1085, после четырёх архивов 983, после glibc 701), закрытые владельцем манифесты, закреплённые SHA-256 и числовой отчёт предыдущего `ld -r`. Отдельно повторяется настоящий объектный GNU Make-инвентарь из исходного public PC: **85 игровых модулей и 33 backend/observer-модуля**, ровно 118. Для каждого `.o` заново проверяется байтовая идентичность, инвентарная принадлежность и список `nm -u` через закрытый дескриптор.

380 имён распределяются по взаимоисключающим категориям:
- употребляются только игровыми объектами;
- употребляются только объектами PC-бэкенда/диагностики;
- употребляются в обеих группах;
- не имеют владельца в инвентаре — **такой случай приводит к отказу CI**, а не к утверждению результата.

Отдельно выводится количество различных модулей, использующих оставшиеся ссылки, и общее число пар «объект — импорт». Повторения внутри одного объекта не завышают число уникальных символов; один импорт вправе встречаться во многих модулях.

**Ограничения:** использование (ссылка из объектного файла) не равно месту, где должна находиться реализация. Отчёт служит для первичного разделения работ над отсутствующими интерфейсами; он ещё не локализует конкретный пропущенный исходный файл и не доказывает игровое поведение. Имена символов, реальные пути пользовательских файлов и игровой образ не загружаются и не выводятся в публичных логах. Эксперимент остаётся Draft и не меняет `main`.

## Следующий этап: ширина использования 314 игровых импортов

Проверенный [PR №414, CI №39591484699](https://github.com/stanmasked/vandal-hearts-switch-remaster/actions/runs/39591484699) — **36/36**, 314 исходных имён используются только игровыми объектами, 26 — только бэкендом, 40 — обеими группами. Теперь среди **314 игровых-only** имён вычисляется фактическое число различных скомпилированных игровых модулей, в которых обнаружен каждый такой импорт.

Публикуются только четыре взаимоисключающих числовых интервала: **ровно один объект**, **2–3 объекта**, **4–7 объектов**, **8 и более объектов**. Их сумма обязана равняться 314. Дополнительно аудируются общее число пар «игровой объект — только-игровой импорт», максимум числа игровых модулей, использующих одно имя, и отдельные пары для 40 совместно используемых имён. CI независимо проверяет, что сумма пар двух групп воспроизводит ранее подтверждённые 1 287 игровых и 84 вспомогательные пары.

Ширина ссылок позволяет оценить, какой отсутствующий интерфейс потенциально затрагивает множество модулей при работе над реализацией, однако **не устанавливает место определения символа, функциональную важность или частоту вызова во время игры**. Наличие одного имени в десяти объектах может быть следствием общих библиотечных утилит, а не системы MAP02. Имена и пути оригинальных пользовательских файлов не публикуются; работа остаётся исследовательской и не подключает игру.

## Проверка типов для 33 зависимостей с широким охватом

По результатам [PR №420, Actions №39594205974](https://github.com/stanmasked/vandal-hearts-switch-remaster/actions/runs/39594205974) исходный GNU `nm` действительно выявил **33 только-игровых имени**, каждое используется не менее чем восемью разными игровыми объектами. Повторное [Actions №39594213683](https://github.com/stanmasked/vandal-hearts-switch-remaster/actions/runs/39594213683) также завершилось 36/36 успешно.

Следующее исследование повторно вызывает настоящий GNU `readelf -Ws` **на запечатанном дескрипторе каждого из 85 исходных игровых ELF `.o`**, уже сопоставленного с инвентарём Make. Из строк `GLOBAL UND` извлекаются типы `FUNC`, `OBJECT`, `NOTYPE` и другие записанные ELF-типы. Если сильная неопределённая ссылка, обнаруженная `nm -u` среди оставшихся 380, не подтверждается таблицей `readelf`, проверка прекращается без публикации имён.

Для 33 имён, встречающихся в восьми и более игровых модулях, выводятся только непересекающиеся количества:
- хотя бы один явный `FUNC`, но ни одного `OBJECT`;
- хотя бы один `OBJECT`, но ни одного `FUNC`;
- обнаружены оба явных типа `FUNC` и `OBJECT` — потенциальное противоречие;
- все записи имеют `NOTYPE`;
- прочие типы или неоднозначные случаи.

Наличие `NOTYPE` также учитывается отдельным пересекающимся счётчиком. Взаимоисключающие пять категорий в сумме обязаны дать **33**, число которых независимо определено исходным `nm`. Строгость проверки обеспечивает согласованность имен между инструментами, а не семантическую истинность объявления.

**Важное ограничение:** `FUNC` в неопределённой строке ELF — это декларация объектного файла, а не доказательство ABI, места реализации или успешного вызова в игре. `NOTYPE` не превращается автоматически в функцию и не заменяется догадкой. При конфликтующих типах отчёт сохраняет категорию неоднозначности; приватные имена и пути не попадают в общий CI-журнал.

## Релокации для 33 широкоупотребимых игровых ссылок

Подтверждённый [PR №426, Actions №39597025314](https://github.com/stanmasked/vandal-hearts-switch-remaster/actions/runs/39597025314) показал: **все 33** оригинальных игровых-only символа с числом пользователей не менее восьми имеют лишь `NOTYPE` в исходных ELF-таблицах. Следовательно, ELF `TYPE` не устанавливает их семантическую роль.

Дополнительный исследовательский аудит читает `readelf -rW` через те же проверенные закрытые дескрипторы **85 настоящих компилированных игровых `.o`**. Для каждого из 33 имён он объединяет реальные записи релокаций по всем использующим его объектам. Публикуются только агрегаты по пяти взаимоисключающим группам:

- только `R_X86_64_PLT32`;
- только `R_X86_64_PC32`;
- встречаются и `PLT32`, и `PC32`;
- есть другие типы, в том числе `GOT`/абсолютные или смешанные;
- для данного неопределённого имени не найдено соответствующей записи релокации.

Отдельно подсчитываются все записи каждого типа и количество имён, имеющих только релокации вне секций `.text`. Сумма пяти групп обязана равняться 33, независимо подтверждённым прежним `nm`. Проверки искусственных файлов включают настоящие GCC / `readelf -rW` и случаи отсутствующих записей.

**Ограничения:** наличие `R_X86_64_PLT32` указывает на PLT-относительную релокацию, но не доказывает, что по этому адресу выполнялся вызов функции, что был задействован конкретный ABI или что ссылка использовалась при реальном прохождении MAP02. `R_X86_64_PC32` часто встречается и для кода, и для данных. Реализацию нельзя автоматически заменять на основании одного вида релокаций. Имена и пользовательские объекты не загружаются в публичные артефакты. Черновик не означает сборку рабочей игры.

## Точная разбивка 222 нестандартных релокаций и секций

По [проверенному PR №431 / Actions №39598546249](https://github.com/stanmasked/vandal-hearts-switch-remaster/actions/runs/39598546249) у **33** широко используемых символов `NOTYPE`: 32 имени имеют только `R_X86_64_PC32`, одно имя — другие/смешанные виды; суммарно **5 690 PC32**, **0 PLT32**, **222 прочих записей**, без неучтённых имён. Исходный PC ELF остаётся незавершённым; результат не подтверждает выполнение MAP02.

Новый этап разбивает **реальные записи**, а не символы, одновременно по двум независимым осям. Типы релокаций: `PC32`, `PLT32`, абсолютные `32`, `32S`, `64`, семейство `GOTPCREL` и прочие. Места исправления: секции `.text`, `.rodata`, `.data`/`.bss`, `.eh_frame`/обработки исключений и прочие. Сумма каждого из двух наборов обязана совпасть с **совокупным числом записей 5 912**, установленным как 5 690 + 222 на предыдущем этапе.

Отдельно проверяются число имён, имеющих тип релокации кроме `PC32`/`PLT32`, количество имён, которые встречаются и в `.text`, и за её пределами, а также имён без записей. Исходные 33 имени используются только внутри закрытых дескрипторов объектов; публичные отчёты содержат лишь числовые группы.

**Важно:** название исходной секции релокации говорит, *в каком месте объектного файла исправляется ссылка*, а не где определён символ. Даже ссылка в `.rela.text` не гарантирует, что цель — функция или что такой код выполнялся в игре. Инструмент не создаёт предполагаемые реализации и не публикует игровые данные.

## Привязка 222 ABS64-релокаций к исходным модулям и смещениям

[PR №432, CI №39600282536](https://github.com/stanmasked/vandal-hearts-switch-remaster/actions/runs/39600282536) подтвердил: для одного из 33 широкоупотребимых `NOTYPE`-имён присутствуют **222 релокации R_X86_64_64** в секциях `.data`; для остальных 32 имён среди этих широкоупотребимых интерфейсов зафиксированы только `PC32` из `.text`. Общие счётчики 5 690 + 222 = 5 912 проверены по двум независимым осям.

Новый анализ повторно обрабатывает штатный вывод GNU `readelf -rW` непосредственно на проверенных объектных файлах. Он собирает **внутренний приватный список смещений в исходных секциях данных** только для широкоупотребимых имён, после чего публикует агрегаты:

- сколько из 85 настоящих игровых `.o` содержит абсолютные 64-битные обращения к этому имени;
- сколько различных `.data`-секций исходных объектных файлов нужно учитывать;
- сколько из 222 мест исправления выровнено по восьми байтам;
- сколько пар соседних релокаций имеют разницу смещений ровно восемь байт;
- максимальная длина подряд расположенных релокаций с шагом восемь байт в *одном* файле и секции.

Сравнение смещений выполняется только внутри одной секции одного объектного файла: одинаковые смещения из разных модулей **никогда** не объединяются в выдуманный непрерывный массив. Дубликат позиции для одного имени в рамках секции отвергается, а суммарное количество обязанo точно совпасть с ранее проверенными 222.

**Ограничение:** даже плотный ряд абсолютных релокаций может принадлежать таблице указателей, таблице структур или другому статическому набору данных. Расположение само по себе не определяет семантику символа и не подтверждает использование ссылки в реальном ходе игры. Имена символов, приватные пути и фактические смещения не печатаются в общих отчётах.

## Диагностика промежутков между 222 исходными ABS64-релокациями

На следующем этапе зафиксированы два независимых успешных запуска [PR №436, Actions №39604827886](https://github.com/stanmasked/vandal-hearts-switch-remaster/actions/runs/39604827886) и [№39604819813](https://github.com/stanmasked/vandal-hearts-switch-remaster/actions/runs/39604819813). На закреплённом исходном объектном коде 222 записи `R_X86_64_64` к **одному** игровому символу распределены между **двумя исходными объектными файлами и двумя секциями данных**. В крупнейшем объекте 219 записей, в другом — 3. Все записи выровнены по 8 байтам; всего **две** пары с шагом ровно 8 байт, максимальная длина такого ряда — 3.

Чтобы не принять несколько далеко расположенных мест исправления за цельную таблицу, новый анализ считает именно **220 промежутков между последовательно отсортированными смещениями в одной секции одного объектного файла**. Он публикует лишь количество промежутков со смещением 8, 16, 24, 32, 40–64, более 64 и не кратных 8 байтам, а также числа записей в двух крупнейших исходных объектах. Число промежутков должно быть равно `222 − 2 = 220`, а количество восьмибайтовых шагов — ранее проверенным **2**. Смещения и имена в публичный результат не попадают.

Такая группировка помогает определить, встречается ли повторяющийся шаг в данных. Но даже если большинство промежутков окажутся одинаковыми, это всё ещё **не доказывает структуру C, таблицу указателей, тип целевого символа или использование его при реальном прохождении игры**. Не добавлять поддельные реализации и не объединять смещения из разных исходных объектных файлов.

## Смещения цели (RELA addend) у 222 абсолютных релокаций

Прежний аудит изучает **места исправления** в секциях `.data` двух исходных объектных файлов (219 и 3 записей). Новый дополнительный этап отдельно измеряет **слагаемое relocation addend**, которое GNU `readelf -rW` отображает после имени целевого символа. Например, позиция исправления 8 байт и addend +24 байта — это два разных числа, относящихся к разным понятиям.

На запечатанных `.o` оригинального публичного PC-проекта новая проверка разбирает только записи `R_X86_64_64` в секциях данных и проверяет, что каждая позиция в точности совпадает с уже подтверждённым списком 222 исходных мест исправления. Addend считывается как **знаковое шестнадцатеричное число**, не десятичное; обработка форм `+ 18` и `- 8` проверена синтетическими тестами и настоящим GCC.

В публичный отчёт поступают лишь числовые сводки: число различных addend-значений, количество нулевых и отрицательных значений, выровненных по 8 байтам, повторно использованных значений и максимальное число записей с одинаковым addend. Сам список адресных смещений и имён символов остаётся в закрытой памяти аудита.

Даже совпадение addend у всех 222 записей означало бы только повторную ссылку на одно относительное смещение целевого символа. Оно **не доказывает таблицу указателей, тип этого символа, адрес в конечной программе или выполнение игрового кода**. Данные игрового образа не считываются, PR остаётся исследовательским.

### Дополнительное разделение повторов addend по границам исходных объектных файлов

Одной глобальной частоты значений недостаточно: одинаковое слагаемое может встретиться один раз в каждом из двух разных исходных файлов, либо несколько раз внутри одного файла. Это разные наблюдения. Аудитор теперь отдельно агрегирует:

- число различных addend-значений, повторяющихся внутри одного исходного объекта;
- число записей, участвующих в таких повторах внутри объекта;
- число различных addend-значений, присутствующих в нескольких исходных объектах;
- число записей, использующих значения, разделяемые между объектами;
- максимум записей с одинаковым addend внутри одного объекта;
- минимум и максимум числа различных addend-значений на исходный объект.

Группировка выполняется в памяти по фактическому индексу исходного `.o`; наружу не выводятся значения addend, пути и символы. Синтетический тест намеренно содержит addend `0`, встретившийся по одному разу в двух объектах, и addend `24`, повторённый дважды только внутри одного объекта, чтобы эти случаи нельзя было спутать. Это всё ещё статистика ELF-релокаций, а не свидетельство типа данных или выполнения игрового кода.
