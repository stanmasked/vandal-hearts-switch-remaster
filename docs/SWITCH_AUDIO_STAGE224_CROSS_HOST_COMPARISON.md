# Vandal Hearts Remake — этап №224: независимое сравнение архивных отчётов между компьютерами

> **HARDWARE NOT TESTED.** Речь только о проверке сохранности байтов и согласованности записей; инструменты не удостоверяют реальный запуск Nintendo Switch, акустическое качество или независимость физических сессий.

## Назначение

Этап №223 проверял один ZIP по заранее сохранённому SHA-256. Новый [инструмент `compare_switch_audio_archive_reports.py`](../tools/compare_switch_audio_archive_reports.py) делает **две независимые проверки** — исходного архива и полученной копии — а затем фиксирует точные различия между ними, не перезаписывая ни один оригинал.

В сравнении участвуют:

- SHA-256 **каждого архива ZIP** из отдельно сохранённых контрольных значений;
- пересчитанный индекс NRO, исходных CSV, манифеста, операторского JSON и карточек (имя, длина, SHA-256);
- полный Git SHA, заявленный исходным манифестом;
- результат полного аудита №222, семь статусов H01–H07, сценарии повторного испытания и признаки несовместимых ручных карточек;
- флаг `HARDWARE NOT TESTED` и требование отдельного ручного заключения.

Каждый отчёт создаётся **из ZIP заново**, после повторного исполнения строгой проверки этапа №223 во временном изолированном каталоге. На этапе сравнения оба ZIP перепроверяются ещё раз, а **любой отредактированный или подставленный отчёт** отклоняется как `SAVED_REPORT_MISMATCH`. Перенесённый JSON без исходного ZIP не может заменить полную проверку.

## 1. Исходный компьютер: создать снимок

После создания архива этапа №223 и сохранения его SHA-256 **в независимом канале**:

```sh
python3 tools/compare_switch_audio_archive_reports.py snapshot \
  /path/to/original/handoff-223.zip \
  --expected-sha256 ORIGINAL_ZIP_SHA256_FROM_TRUSTED_RECORD \
  --output /path/outside-zip/source-snapshot-224.json
```

Файл `source-snapshot-224.json` создаётся **только если его ещё нет**. Команда проверяет ZIP целиком и все файлы внутри, затем формирует воспроизводимую инвентаризацию. Не помещайте JSON в проверяемые папки источника и не изменяйте исходные CSV.

## 2. Другой компьютер: независимый снимок

Проверьте, что ZIP и контрольный SHA-256 получены безопасными раздельными способами. На втором компьютере:

```sh
python3 tools/compare_switch_audio_archive_reports.py snapshot \
  /path/to/received/handoff-223.zip \
  --expected-sha256 RECEIVED_ZIP_SHA256_FROM_TRUSTED_RECORD \
  --output /path/outside-zip/received-snapshot-224.json
```

Если полученная копия **должна быть точно такой же**, в качестве ожидаемого SHA передайте исходный контрольный хеш из отдельного сообщения. Если архив намеренно *переупакован* и его ZIP-хеш изменился, сначала проверьте новый SHA по отдельному доверенному каналу — инструмент покажет это как особое отличие контейнера, не как новую физическую сессию.

## 3. Сравнение без изменения первичных доказательств

Когда оба архива и два отчёта доступны на одной проверяющей машине (например, исходный архив/снимок перенесены обратно в защищённое рабочее пространство), выполните:

```sh
python3 tools/compare_switch_audio_archive_reports.py compare \
  --source-archive /path/to/original/handoff-223.zip \
  --source-sha256 ORIGINAL_INDEPENDENT_ZIP_SHA256 \
  --source-report /path/to/source-snapshot-224.json \
  --received-archive /path/to/received/handoff-223.zip \
  --received-sha256 RECEIVED_INDEPENDENT_ZIP_SHA256 \
  --received-report /path/to/received-snapshot-224.json \
  --format json > /path/to/comparison-224.json
```

Для человекочитаемого списка используйте `--format markdown` вместо `json` и сохраните вывод в отдельный `.md`. Полный JSON включает записи `differences` с `category`, `code`, `subject`, `source` и `received`: видно, какой конкретно файл отличается, какой хеш был раньше и каким стал.

## Интерпретация результата

| `result` | Что обнаружено |
| --- | --- |
| `EXACT_MATCH` | Совпадают SHA-256 ZIP, все файлы, статусы, повторы и заявленные данные обеих сессий сравнения |
| `CONTAINER_ONLY_DIFFERENCE` | ZIP упакован иначе, но все внутренние файлы и результаты аудита совпадают |
| `EVIDENCE_CHANGED` | Появились, пропали или изменились NRO, CSV, карточка, операторский JSON, манифест либо изменён заявленный Git SHA |
| `REVIEW_CHANGED` | Байты первичных файлов одинаковы, но различается политика аудита или итоговые статусы, например явно запрошенный H06/H07 |
| `INVALID_EVIDENCE` | Неверный внешний SHA-256, повреждённый ZIP, несоответствие сохранённого отчёта пересчитанному, небезопасный путь либо неверная структура |

Точный `code` детализации: `EVIDENCE_BYTES_DIFFER`, `EVIDENCE_FILE_MISSING`, `NEW_EVIDENCE_FILE`, `BUILD_SHA_CHANGED`, `REVIEW_FIELD_CHANGED` или `ZIP_CONTAINER_REPACKAGED`. Архив с недопустимыми байтами **не интерпретируется** как обычная разница файлов: сначала возвращается `INVALID_EVIDENCE`.

**Код возврата `0`** означает лишь, что сравнение корректно завершилось. Он не означает `EXACT_MATCH` и не разрешает аппаратную приёмку. **Код `2`** означает ошибку доказательств; исправлять оригиналы для прохождения проверки запрещено.

## Независимость и ограничения

Даже при совпадении обоих отчётов SHA-256 не является электронной подписью. Если атакующий подменит и ZIP, и ожидаемый хеш, используя один недоверенный канал, программа не установит первоначального отправителя. Оба контрольных значения нужно получить из заранее сохранённых независимых записей.

Имена консоли, времена испытаний, звуковые наблюдения и последовательности HOME/сна — заявления оператора. ZIP не содержит удостоверяющей подписи человека и не доказывает работоспособность железа. После выявленного `EVIDENCE_CHANGED` сначала сохраняйте оба оригинальных архива и точный отчёт различий, затем расследуйте причину; **не заменяйте старый CSV новым**.

### Регрессии

[18 синтетических host-тестов](../tests/test_compare_switch_audio_archive_reports.py) покрывают побайтовое совпадение, изменение формата ZIP без замены данных, подмену операторской карточки, исчезновение CSV/карточки, H06-различия, поддельные отчёты, ошибки независимого SHA-256, нештатную запись, CLI JSON/Markdown, воспроизводимость снимка и неизменность исходных файлов. Они включены в `make test` и `make test-audio-stream`, **не** являются испытанием реальной Switch.

## Этап №225 — закрепление и повторение отчёта

Для контроля того, что пересчёт результатов проверки №224 даёт точно тот же JSON на другом компьютере или при более поздней проверке, используйте [инструмент №225](SWITCH_AUDIO_STAGE225_REPEATABLE_REPORTS.md). Он выполняет два прохода строгого аудита, записывает каноническую квитанцию с `receipt_sha256` и проверяет её повторным воспроизведением с **отдельно сохранёнными** хешами ZIP и квитанции. В отличие от сравнения двух архивов №224, №225 требует **того же самого ZIP и семантического результата**. Успешное воспроизведение — лишь сохранность байтов и детерминизм анализа; `HARDWARE NOT TESTED` остаётся в силе.
