# MAP02 — журнал операций изменения GPU VRAM между полигонами

`tools/verify_map02_gpu_write_ledger.py` расширяет приватный
[журнал снимков](MAP02_VRAM_SUBMISSION_TIMELINE.md). Теперь можно
проверить не только **что** VRAM изменилась между двумя отправками FT4,
но и **объясняют ли записанные операции передачи данных** наблюдаемое
содержимое следующего снимка.

Это **офлайн-реплей**, а не автоматический перехват команд игры.
Подлинные игровые ресурсы в репозиторий не добавляются.

## Какие операции поддерживаются

Семантика закреплена на двух оригинальных публичных Git-блобах
PC-порта `HalmyLyseas/VandalHearts-PcPort`:

- `platform/pc/src/libgpu.c` — `9d0fab71c45ed09dda072cfeacd557ab9c5d81e5`;
- `platform/pc/src/pc_raster.c` — `ba8a05d161ad778c0b75e452ff0a11ed163c65cd`.

`LoadImage` загружает 16-битные little-endian слова из заранее
подготовленного буфера (после возможной локализационной модификации
исходного F_WD). При выходе за пределы 1024×512 VRAM применяется
клиппинг, а внутри исходного прямоугольника сохраняется исходный шаг.

`MoveImage` перемещает слова из прямоугольника `rect` в `dest`.
**Копирование последовательно и непосредственно в той же VRAM**:
сначала строки сверху вниз, внутри строки слева направо. Это не
`memmove`, и перекрывающиеся источник и назначение намеренно
воспроизводятся с эффектом самоперезаписи.

`ClearImage` выполняет абсолютное прямоугольное заполнение (не
зависит от drawing area) с упаковкой
`BGR555 = (b >> 3) << 10 | (g >> 3) << 5 | (r >> 3)`.
Координаты за границами VRAM пропускаются.

`StoreImage` читает память и **не включается** в журнал записей.
**Обычная растеризация** `POLY_FT4`, `SPRT`, `TILE` и прочих GPU
примитивов пишет в VRAM через `PutPixel`, но в этой версии
**не воспроизводится**. Если такая операция изменила снимок, проверка
завершится ошибкой. Неизвестные события `GP0` не аппроксимируются.

## Формат приватных данных

Кроме всех файлов
[per-submission timeline](MAP02_VRAM_SUBMISSION_TIMELINE.md) в локальной
папке должны находиться:

- `write-ledger.json` — привязка нового журнала к уже проверенному
  `timeline.json` и исходному PC-порту.
- `gpu-writes.jsonl` — последовательность из 1–512 операций.
- `load-0000.bin`, `load-0001.bin`, ... — только для событий
  `load`, с именем по **общему индексу** события и контрольной
  суммой полезной нагрузки. Путь не принимается из JSON.

Пример манифеста:

```json
{
  "schema": "vh.map02.gpu.transfer-ledger.v1",
  "frame": 411,
  "pc_source_commit": "14552fffa0e0b47e02b57592e274fc6e7a649923",
  "timeline_sha256": "<sha256 реальных байтов timeline.json>",
  "transfers_sha256": "<sha256 реальных байтов gpu-writes.jsonl>"
}
```

Пример трёх **синтетических** событий между первым и вторым
снимками, то есть `before_submission=1`:

```jsonl
{"step":0,"before_submission":1,"op":"clear","rect":[0,0,1,1],"rgb":[160,136,32]}
{"step":1,"before_submission":1,"op":"load","rect":[690,499,1,1],"payload_sha256":"<sha256 файла load-0001.bin>"}
{"step":2,"before_submission":1,"op":"move","rect":[10,12,3,1],"dest":[11,12]}
```

JSONL выше описывает схему; метки `<sha256 ...>` необходимо
заменить настоящими дайджестами локальных файлов.

Операции упорядочены по `step` от нуля, а
`before_submission` монотонно не убывает от 1 до числа
снимков минус 1. Каждая загрузка ограничена 16384 словами
(32768 байт); более крупную передачу можно разбить на
отдельные последовательные операции, сохраняя их порядок.

## Запуск

Из корня репозитория, при наличии только локальных файлов:

```sh
python3 -m tools.verify_map02_gpu_write_ledger /private/map02-timeline \
  > /private/map02-gpu-writes-report.json
```

Для дополнительного контроля исходного кода:

```sh
python3 -m tools.verify_map02_gpu_write_ledger /private/map02-timeline \
  --pc-libgpu /private/VandalHearts-PcPort/platform/pc/src/libgpu.c \
  --pc-raster /private/VandalHearts-PcPort/platform/pc/src/pc_raster.c \
  > /private/map02-gpu-writes-report.json
```

Сначала повторно проверяются SHA, карта, все GTE-измерения,
привязка уникальных граней, палитры и каждый снимок предыдущего
этапа. Затем копия `gpu-vram-000.bin` изменяется строго
последовательными `load/move/clear` операциями. **Перед каждым
следующим полигоном она обязана полностью, побайтово совпасть с
`gpu-vram-NNN.bin`.** Любая необъяснённая запись — ошибка, а не
автоматическое «подтверждение» растеризации.

Отчёт включает только SHA-256, количество операций каждого вида,
количество 16-битных записей, число объяснённых отличий и флаги
ограничений. Исходные байты VRAM, цвета и положение героев/камеры
никогда не попадают в JSON-отчёт.

## Границы доказательства

- Контрольные суммы подтверждают целостность **предоставленных
  файлов**, но не подлинность игрового источника.
- Журнал и снимки могут быть созданы искусственно. Совпадение
  последовательности не доказывает, что операции действительно
  исполнились в оригинальной игре и в указанный момент.
- Между двумя снимками могли происходить записи с последующей
  отменой; этот формат не доказывает отсутствие таких событий.
- Для полноценной GPU-причинности необходим инструментированный
  оригинальный GPU backend с захватом последовательности `DrawOTag`,
  `PutPixel`, передач текстур и операций с CLUT **по времени
  выполнения**, включая сохранение/изменение drawing state.
- Сборки и синтетические тесты этого инструмента не означают
  воспроизведение реальной MAP02 на Nintendo Switch.

Оригинальные VRAM, бинарники игры, кадры и журналы событий
не публиковать в открытых GitHub-артефактах.
