# Vandal Hearts Remake — этап №227: независимые контрольные точки истории на двух архивных копиях

> **HARDWARE NOT TESTED.** Речь исключительно о целостности и воспроизводимости компьютерных данных, не о реальном тестировании звука на Nintendo Switch. Хеши и контрольные точки не доказывают физическую независимость запусков и не заменяют ручное заключение.

## Назначение

После [цепочки №226](SWITCH_AUDIO_STAGE226_RECEIPT_CHAIN.md) добавлен [`tools/checkpoint_switch_audio_receipt_chain.py`](../tools/checkpoint_switch_audio_receipt_chain.py). Он позволяет зафиксировать **контрольную точку всей цепочки** на каждом компьютере и независимо проверить, что две архивные копии содержат одинаковую последовательность исходных проверенных ZIP и квитанций.

Каждая контрольная точка — стабильный JSON, не содержащий имени компьютера, текущей даты или абсолютных путей. В него входят:

- полный `chain_head_sha256` и точное `count`;
- упорядоченный список номеров и SHA-256 каждой записи, исходного ZIP и его квитанции №225;
- `entries_sha256` — SHA-256 канонического упорядоченного списка;
- явные `hardware_status: HARDWARE NOT TESTED`, `physical_independence: NOT_ATTESTED`, `manual_signoff: REQUIRED_NOT_AUTOMATED`.

Список вычисляется **только после полного воспроизведения всей цепочки №226**, с повторной проверкой каждого ZIP и каждой квитанции. Нельзя просто подложить готовый JSON и миновать аудит.

## Перед началом

Нужны **две локальные папки**, содержащие проверенные копии оригинальных архивных доказательств. Например:

```text
computer-A/
  audio-history-226/
    chain/000001.json
    chain/000002.json
    archives/...
    receipts/...
  source-checkpoint-227.json       # ВНЕ audio-history-226

computer-B/
  audio-history-226/
    chain/000001.json
    chain/000002.json
    archives/...
    receipts/...
  received-checkpoint-227.json     # ВНЕ audio-history-226
```

Для **каждой** копии заранее сохраните в независимом доверенном месте *три значения*: точное количество записей, актуальный `chain_head_sha256`, а после создания контрольной точки — SHA-256 **самого файла контрольной точки**. Эти значения должны быть зафиксированы отдельно от ZIP, записей цепочки и JSON-контрольной точки; размещение хеша рядом с файлами не защищает от совместной подмены.

## 1. Создание контрольных точек

На первом компьютере:

```sh
python3 tools/checkpoint_switch_audio_receipt_chain.py checkpoint \
  /safe/path/computer-A/audio-history-226 \
  --expected-count PINNED_SOURCE_COUNT \
  --expected-head-sha256 PINNED_SOURCE_64_HEX_CHAIN_HEAD \
  --output /safe/path/computer-A/source-checkpoint-227.json
```

На втором компьютере аналогично, но используя именно **его независимо закреплённую** голову, количество записей и другой выходной путь:

```sh
python3 tools/checkpoint_switch_audio_receipt_chain.py checkpoint \
  /safe/path/computer-B/audio-history-226 \
  --expected-count PINNED_RECEIVED_COUNT \
  --expected-head-sha256 PINNED_RECEIVED_64_HEX_CHAIN_HEAD \
  --output /safe/path/computer-B/received-checkpoint-227.json
```

Каждый `checkpoint` создаётся **только один раз**, без замены существующего файла. Его нельзя записывать внутрь папки с ZIP/цепочкой, чтобы не смешивать первичные материалы и результат анализа.

Ответ `INDEPENDENT_HISTORY_CHECKPOINT_CREATED` включает `checkpoint_sha256`: сохраните отдельно от JSON.

## 2. Сравнение на проверяющем компьютере

Получите обе архивные копии вместе с отдельными контрольными точками. Сохраните ранее закреплённые SHA-256 контрольных точек, головы цепочек и количества записей **из независимого источника**.

```sh
python3 tools/checkpoint_switch_audio_receipt_chain.py compare \
  --source-root /safe/path/computer-A/audio-history-226 \
  --source-checkpoint /safe/path/computer-A/source-checkpoint-227.json \
  --source-checkpoint-sha256 ORIGINAL_SOURCE_CHECKPOINT_SHA256 \
  --source-head-sha256 ORIGINAL_SOURCE_CHAIN_HEAD_SHA256 \
  --source-count PINNED_SOURCE_COUNT \
  --received-root /safe/path/computer-B/audio-history-226 \
  --received-checkpoint /safe/path/computer-B/received-checkpoint-227.json \
  --received-checkpoint-sha256 ORIGINAL_RECEIVED_CHECKPOINT_SHA256 \
  --received-head-sha256 ORIGINAL_RECEIVED_CHAIN_HEAD_SHA256 \
  --received-count PINNED_RECEIVED_COUNT \
  > /safe/path/outside-both-copies/compare-227.json
```

Команда заново вычисляет SHA-256 контрольных JSON, отклоняет неверные схемы/порядок/повторные ключи, затем повторяет **весь** аудит каждой цепочки, включая ZIP и вложенные CSV/NRO по этапам №223–226. Только после этих проверок она сравнивает результаты. Сохранённая контрольная точка с хешем, пересчитанным атакующим, всё равно отвергается, если её записи не соответствуют полной цепочке с независимо сохранёнными `head` и `count`.

## Как читать результат

| `result` | Значение |
| --- | --- |
| `EXACT_HISTORY_MATCH` | Все упорядоченные записи, ZIP и квитанции обеих независимо проверенных цепочек совпадают |
| `RECEIVED_HISTORY_EXTENDED` | На второй копии есть дополнительные, **независимо проверенные и закреплённые** записи после общего префикса |
| `RECEIVED_HISTORY_SHORTER` | Во второй копии отсутствует хвост, который есть в первой, но обе истории согласованы с *разными* предварительно сохранёнными контрольными точками |
| `DIVERGENT_VALID_HISTORIES` | Уже записанные элементы или их порядок различаются при независимо подтверждённых головах обеих цепочек |
| `INVALID_EVIDENCE` | Неверный SHA, повреждённый ZIP/квитанция, несовпадающая контрольная точка, неверное число записей, подмена старой записи или иной сбой строгого аудита |

Массив `differences` показывает последовательный номер `sequence`, `code` (`MISSING_IN_RECEIVED_COPY`, `ADDED_IN_RECEIVED_COPY` или `DIVERGENT_CHAIN_ENTRY`) и хеши записей/архивов до и после.

**Особенно важно:** если заявлено, что обе папки — побайтовые копии одного состояния, принимать можно **только** `EXACT_HISTORY_MATCH`. Более короткая или дополненная история — не эквивалентная копия, даже если сама по себе успешно прошла проверку. Статус `RECEIVED_HISTORY_SHORTER` не означает, что можно удалить последний элемент и незаметно закрепить новый укороченный HEAD: обе головы и оба количества должны быть подтверждены **независимыми ранее сохранёнными** записями.

## Что не доказывается

- Ни SHA-256 ZIP, ни контрольная точка не являются цифровой подписью автора или испытателя.
- Контрольная точка не доказывает, что разные JSON-карточки происходят от разных физических запусков Nintendo Switch.
- Изменение истории и одновременно всех внешних контрольных хешей одним злоумышленником нельзя обнаружить без доверенной независимой записи или подписи.
- `code 0` означает лишь, что построено осмысленное сравнение; он **не** означает `EXACT_HISTORY_MATCH` и не разрешает аппаратный `PASS`.
- Не загружайте в публичный GitHub приватные или защищённые авторским правом игровые ресурсы, исходные карточки и персональные сведения.

[17 host-only регрессионных тестов](../tests/test_checkpoint_switch_audio_receipt_chain.py) проверяют совпадающие копии, детерминированные контрольные точки, подмену/обрезание записи, порчу ZIP, изменение внутреннего JSON, хеш/HEAD/count, обе разновидности изменения длины истории, явное расхождение, безопасность выходного пути и запрет автоматической аппаратной приёмки. Входные данные **синтетические**, без реальных измерений Switch. Тесты включены в `make test` и `make test-audio-stream`.
