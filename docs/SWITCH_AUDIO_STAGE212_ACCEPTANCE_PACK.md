# Vandal Hearts Remake — этап №212: пакет аппаратной приёмки аудио Nintendo Switch

**Назначение:** получить воспроизводимые реальные измерения и протокол прослушивания, не смешивая результаты GitHub Actions с испытаниями физической консоли.

**Текущий статус: \`HARDWARE NOT TESTED\`.** Этот документ не утверждает, что Switch, динамики, док-станция либо аппаратная SD уже проверены. Эталонная точка разработки защиты CSV — [\`9c0833009bbb44ed2be8896a32597a45c23b68e0\`](https://github.com/stanmasked/vandal-hearts-switch-remaster/commit/9c0833009bbb44ed2be8896a32597a45c23b68e0); это **не заменяет SHA коммита, реально использованного при сборке тестируемого NRO**.

Связанный подробный протокол: [SWITCH_AUDIO_HARDWARE_VALIDATION.md](SWITCH_AUDIO_HARDWARE_VALIDATION.md). Этот пакет фиксирует *происхождение сборки, журналов и человеческих наблюдений* и критерии решения.

## 1. Зафиксировать тестируемый бинарник

1. Откройте **успешный** запуск GitHub Actions **Switch toolchain readiness** именно на ветке \`test/cdxa-extract-decode-pipeline\`. Проверьте **Head SHA** запуска, а не только название ветки или общий статус. Архив с именем \`vandal-hearts-switch-prototype\` содержит NRO из шага **Upload NRO artifact**. Не используйте отдельные SDL2/audout-пробы вместо основного тактического прототипа.
2. Сохраните полный 40-символьный Head SHA, ссылку на запуск Actions, дату, имя NRO и SHA-256 **самого извлечённого файла NRO** (не только ZIP). При новой сборке считайте её *новым кандидатом* даже при неизменной версии приложения \`0.1.0\`.
3. Выполните структурную проверку NRO и зафиксируйте её результат:

\`\`\`sh
python3 tests/check_nro.py /path/to/vandal-hearts-prototype.nro
shasum -a 256 /path/to/vandal-hearts-prototype.nro
# На Linux допустимо: sha256sum /path/to/vandal-hearts-prototype.nro
\`\`\`

Структурный \`PASS\` проверяет заголовок/диапазоны NRO, но **не** подтверждает запуск, качество звука или работоспособность после сна. Запишите также тип сборки (\`GitHub Actions\` или \`local devkitPro\`), версию devkitPro/libnx, если известна; для локальной сборки — точный commit SHA и команду \`make verify-nro\`. Не подставляйте примерный SHA из документа вместо фактического.

## 2. Карточка испытаний и сохранение доказательств

Для каждого **отдельного запуска** NRO создайте копию [карточки сессии](SWITCH_AUDIO_STAGE212_SESSION_TEMPLATE.md) и заполните её. Разложите собранные материалы локально (не добавляйте реальные бинарники/журналы в исходный Git):

\`\`\`text
switch-audio-hardware-212/
  BUILD.md                       # NRO SHA-256, точный Git commit, CI URL, окружение
  nro/                           # неизменённый тестируемый NRO
  session-01/                    # заполненная карточка + исходный CSV + sha256
  session-02/
  session-03/                    # дополнительные прогоны и повторное чтение SD
  analysis/                      # JSON/text-вывод обоих анализаторов
  MANUAL_ACCEPTANCE.md           # решение и подпись/дата ответственного
\`\`\`

Сохраните и оригинальный CSV с SD, и проверенную копию; не редактируйте CSV «для исправления» пропущенных строк. Сохраняйте артефакты в каталоге с ограниченным доступом, если на скриншотах видны данные пользователя.

Обязательные поля карточки: NRO SHA-256 и commit SHA, консоль/версия системы (по возможности), Application/app\-let режим, handheld/dock, динамики/HDMI/Bluetooth, способ установки и тип SD, START/EXIT, прошедшее время, количество циклов HOME/сон, номер CSV, SHA-256 файла, наличие \`.tmp\`, результаты прослушивания и необычных состояний \`STATE/ERROR\`.

## 3. Сценарии на реальном устройстве

| ID | Испытание | Минимальный объём | Обязательная запись |
| --- | --- | --- | --- |
| H01 | Чистый запуск, игровая сцена и штатный выход \`Plus\` | **2 независимых сессии**, каждая с \`>= 1000\` *наблюдаемых* подтверждённых PCM-страниц | NRO SHA, по одному новому номерному CSV на сеанс, строгий анализ каждого |
| H02 | Восстановление после HOME | **10 HOME → возврат** при активной музыке | \`STATE PLAYING\`, счётчики, наблюдения об обрывах/щелчках |
| H03 | Сон и пробуждение | **5 циклов** с музыкой | Зависания/задержка до слышимого звука (ручная), ошибки reopening |
| H04 | Продолжительная работа | **30–60 минут** с включённой диагностикой | Фактическая длительность, \`output_pages\`, отказы, ограничение на последние 128 строк |
| H05 | Целостность файлов после перезапуска | Как минимум **1 повторный запуск** после сохранённого CSV | Сравнить SHA-256 старого CSV до/после; новый номер не должен заменить старый |
| H06 | Ошибки сохранения (по возможности) | Только **безопасный сценарий** на отдельном носителе/каталоге без важных данных | Видимая ошибка, прежние CSV неизменны, \`.tmp\` не объявлен успешным |
| H07 | Сравнение NRO «до/после» | **2 независимые CSV на каждую версию**, \`>= 1000\` наблюдаемых PCM-страниц на CSV | \`compare_switch_audio_sessions.py\`, совпадение звукового выхода/режима и условий |

\`H07\` не нужен для первоначальной приёмки **одной** версии, но обязателен для заявления «нет регрессии между версиями». Для сравнения ошибок HOME инструменту дополнительно требуется **>= 10 наблюдаемых HOME-возвратов в каждой группе**; для p95 — **>= 10 индивидуальных измерений задержки в каждой группе**. Пробелы в 128-строчном кольцевом журнале нельзя интерпретировать как отсутствие инцидентов. Значения \`last_pcm_us\` / \`worst_pcm_us\` — время подтверждения буфера, **не** аппаратная задержка слышимого звука.

**Безопасность:** не вынимайте SD на работающей консоли и не отключайте питание для имитации ошибки. Тесты этапа №211 доказали отбраковку повреждённых файлов при программно имитированных сбоях; они **не доказывают** сохранность данных после физической потери питания или корректность flush на конкретной SD/FAT.

## 4. Анализ только реальных CSV

После штатного завершения \`Plus\`, чтения SD на компьютере и сохранения SHA-256:

\`\`\`sh
python3 tools/analyze_switch_audio_log.py --format json \
  /path/session-01/audio-diagnostics-0000.csv \
  /path/session-02/audio-diagnostics-0001.csv > analysis/observations.json
\`\`\`

Если сравниваются **две различные сборки**, а не повторные запуски одного NRO:

\`\`\`sh
python3 tools/compare_switch_audio_sessions.py \
  --baseline /path/old-1.csv /path/old-2.csv \
  --candidate /path/new-1.csv /path/new-2.csv \
  --baseline-version OLD_FULL_GIT_SHA \
  --candidate-version NEW_FULL_GIT_SHA \
  --format json > analysis/comparison.json
\`\`\`

Проверяйте и **код завершения**, и поле вердикта. Строгий парсер возвращает \`2\` при повреждённом CSV; сравниватель возвращает \`1\` для \`POTENTIAL_REGRESSION\`, \`2\` при неверных данных/аргументах, но \`0\` **как для \`NO_REGRESSION_FLAG\`, так и для \`INCONCLUSIVE\`**. Последний вариант не равен успешной приёмке. Не используйте синтетические CSV host-тестов как аппаратные результаты.

## 5. Правила принятия решения

- **\`PASS\` (только после аппаратных тестов):** документированы происхождение NRO и физические условия; H01–H05 выполнены; все требуемые реальные CSV прошли строгий разбор, достаточно наблюдаемых PCM-страниц, предыдущие сохранённые файлы не изменились; после HOME/сна поток возвращается к \`PLAYING\` без зависаний/подтверждённых слышимых артефактов; неожиданные \`ERROR\`, \`pcm_fail\`, \`home_fail\`, \`lease_fail\` отсутствуют либо расследованы с подтверждённым исправлением и повторным испытанием. В H07 отдельно выполнены условия сравнимости, если заявляется отсутствие регрессии.
- **\`FAIL\`:** доказанная порча ранее подтверждённого CSV, неподтверждённое успешное сохранение, воспроизводимый критический дефект звука/зависание или воспроизводимая ошибка восстановления. Приложите сведения об окружении и минимальные шаги.
- **\`INCONCLUSIVE\`:** недостающие CSV, меньше необходимого числа страниц/сессий, несопоставимые режимы вывода, недоступные измерения, непройденный/неполный сценарий или недостаточное ручное прослушивание. Не переводите такой результат в \`PASS\`.
- **\`HARDWARE NOT TESTED\`:** исходный статус до первого подтверждённого запуска на физической Switch. Успешные GitHub Actions/NRO/ASan/UBSan не меняют его автоматически.

Вручную подписанный итоговый протокол должен перечислять каждый H01–H07 как \`PASS\`, \`FAIL\`, \`INCONCLUSIVE\` или \`NOT RUN\`, ссылаться на соответствующие CSV/хеши/фото и разделять **телеметрию**, **слуховую оценку**, **файловую целостность** и **долговечность хранения после питания** (последняя остаётся отдельным, не подтверждённым программными тестами свойством).

## 6. Перед передачей пакета

Контрольная отметка этапа №212 означает только **готовность документации и сценариев** к испытаниям, а не завершение физической приёмки. Не публикуйте оригинальные игровые ресурсы, записи с персональными данными или неподтверждённые численные показатели. После получения реальных журналов можно назначить отдельный этап аппаратных измерений и лишь затем менять статус.
