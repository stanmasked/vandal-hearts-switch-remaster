# Nintendo Switch — аппаратная диагностика музыки (этап №202)

**Статус:** протокол для ручной проверки на реальной консоли. Успешный GitHub Actions/NRO build **не означает**, что прослушивание или измерение на Switch уже состоялись. Исходные игровые SEQ/VH/VB не нужны для первичной проверки: допускаются встроенные синтетические музыкальные сцены.

## Как получить подходящий NRO

Откройте успешный GitHub Actions workflow **Switch toolchain readiness** на ветке `test/cdxa-extract-decode-pipeline` и скачайте артефакт `vandal-hearts-switch-prototype` (шаг **Upload NRO artifact**). Это главный тактический прототип с интегрированным звуковым потоком, а не отдельные исторические SDL2 или standalone audout-пробы.

Или соберите локально с настроенным devkitPro:

```sh
make verify-nro
```

Перенесите полученный `.nro` на свою Switch и запускайте его в разрешённой homebrew-среде. Поддержка HOME и сна зависит от режима запуска: предпочтителен полноценный Application context. Если приложение запущено в несовместимом applet-режиме, отметьте это в результате, а не приравнивайте к ошибке аудиодвижка.

## Панель аудиодиагностики

В главном тактическом прототипе нажмите **Minus** для показа/скрытия панели справа. Это только отображение атомарных счётчиков; само открытие панели не перезапускает SEQ/SPU или аудиосервис. **Plus** — штатный выход, **A/B/D-Pad** — обычное управление. На экране применён тот же встроенный 5×7 шрифт, никакие игровые шрифты или ресурсы не загружаются.

| Поле на экране | Что означает |
| --- | --- |
| `STATE` | PLAYING, PAUSED, START или ERROR (конкретная ошибка отдельно возвращается кодом API) |
| `HOME RESUMES` | Сколько раз аудиопоток **обработал** изменение serial HOME/OnResume |
| `FIRST PCM COUNT` | Сколько раз было подтверждено завершение первого PCM-блока после старта/возобновления |
| `LAST PCM US`, `WORST PCM US` | Время в **микросекундах** от начала попытки запуска `audout` до возвращения **первого завершённого PCM-буфера** |
| `OUTPUT PAGES` | Сколько PCM-страниц принято с подтверждением; не число слышимых сэмплов |
| `PCM FAIL`, `RESTART` | Ошибки отправки и попытки пересоздания аудиосеанса |
| `HOME FAIL`, `REOPEN` | Ошибки запуска при восстановлении, попытки повторного открытия |
| `LEASE FAIL`, `RESET` | Неоднозначные/чужие освобождения PCM-буфера, сброшенные при закрытии сеансы |
| `VAB WARN`, `RECOVERED` | Предупреждения разрешения инструментов; суммарные успешные восстановления аудиовывода |

Счётчики читаются **не блокируя аудиопоток**: значения разных строк могут относиться к соседним аудиоблокам. `FIRST PCM` измеряет подтверждение libnx, **не** момент фактического появления звука из динамика и не гарантирует задержку после сна. Показатели сбрасываются при новом старте аудиопотока.

## Запись результатов на SD-карту — этап №203

В главном тактическом NRO нажмите **Minus**, чтобы открыть панель, и **Y**, чтобы включить запись. Повторное **Y** приостанавливает запись; следующее Y продолжает её в рамках той же сессии. В панели отображаются текущий режим записи и количество сохранённых строк. Данные собираются **только по явному запросу**, ни один оригинальный SEQ/VH/VB-сэмпл и никакие PCM-аудиоданные не записываются.

Сбор выполняется главным игровым потоком: события `HOME/RESUME`, `STATE`, `ERROR` записываются при обнаружении изменений, в отсутствие событий — снимок не чаще одного раза в **5 секунд**. Буфер содержит максимум **128 записей**. После заполнения самые старые вытесняются без увеличения памяти. При длительной сессии сохранится **последний** отрезок, а не вся история 30+ минут.

Выполните штатный выход кнопкой **Plus** (аудиопоток уже будет остановлен), и прототип создаст **новый** файл, не перезаписывая предыдущие:

```text
sdmc:/switch/vandal-hearts-remake/audio-diagnostics-0000.csv
sdmc:/switch/vandal-hearts-remake/audio-diagnostics-0001.csv
...
```

Файл содержит столбцы `elapsed_ms`, `event`, `status`, количества HOME, PCM, ошибок, повторных открытий и показатели задержки до подтверждения PCM. Строки расположены по времени от старых к новым. Все поля — числовые значения или фиксированные обозначения событий, без имён файлов, адресов, музыки и пользовательского текста. Обновление CSV при каждой записи **не выполняется**: файловые операции происходят только **после завершения аудиопотока**. Каждый новый прогон занимает следующий свободный номер от **0000 до 0063**. Если все 64 номера заняты, экспорт прекращается с ошибкой и старые отчёты остаются целыми. После копирования нужных CSV можно вручную удалить старые файлы на SD-карте.

**Ограничения:** при аварийном завершении, внезапном отключении питания или невозможности записи на SD **данные из оперативной памяти не сохранятся**. Отсутствие файла не говорит о том, что музыка не работала. Если нужно документировать ошибки при аварии, сделайте фотографию открытой панели непосредственно в момент ошибки. Физические показатели в этой документации по-прежнему **не измерены**.

Для длительного теста запустите 30–60-минутную сессию с включённым Y, периодически переключайте сцены, повторите HOME/сон и проверьте CSV после выхода. Ориентируйтесь на рост `output_pages`, отсутствие неожиданных `status<0`, адекватность `last_pcm_us/worst_pcm_us` и событий `ERROR`. Небольшой фиксированный журнал не является осциллографом и не может сам определить слышимость щелчков.

## Безопасное сохранение при ошибках SD-карты — этап №209

Запись диагностики теперь производится **только после полной остановки аудиопотока** по двухэтапной схеме: создаётся служебный файл `audio-diagnostics.tmp` в том же каталоге, затем проверяются запись всех строк CSV, `fflush` и `fclose`. Только после успешного завершения временный файл переименовывается в ближайший свободный `audio-diagnostics-XXXX.csv`.

При полном носителе, запрете записи, неверном каталоге, сбое открытия, короткой записи, ошибке flush/close/rename или отсутствии свободных имён программа **не объявляет экспорт успешным** и завершает работу с ненулевым кодом `2`. По возможности неполный временный файл удаляется. **Предыдущие корректные номерные CSV не открываются на запись и не удаляются.** При внезапном отключении питания может остаться `.tmp`; он не считается подтверждённым отчётом и будет заменён при следующей попытке экспорта.

Для тестирования программной защиты добавлен модуль `vh_audio_diag_export.[ch]` с имитацией шести типов отказов файловой системы. При этом **невозможно гарантировать сохранность при аппаратном сбое или потере питания** — для подтверждения долговечности на реальной SD/FAT требуется испытание на физической Switch. Переименование файла выполняется после его закрытия и проверки ошибок, но само по себе не доказывает физическую синхронизацию накопителя и не заменяет аппаратную проверку.

Отдельные тесты используют граничные значения 32- и 64-битных счётчиков. Даже при переполнении счётчика число CSV-строк остаётся ограниченным 128; обработчик не должен записывать неполный отчёт как готовый.

## Повторные запуски после незавершённой записи — этап №210

Подготовлена сквозная host-проверка **четырёх независимых игровых сеансов**, объединяющая настоящий C-экспортёр диагностического журнала, CSV-проверку и оба Python-анализатора. Каждый сеанс выполняется в отдельном процессе и заново создаёт ограниченный 21-строчный журнал. Это не проверка аппаратной SD, а воспроизводимая симуляция завершения/нового запуска NRO без игровых ресурсов.

- Первый процесс сохраняет `audio-diagnostics-0000.csv` с 2 400 подтверждёнными PCM-страницами, 40 событиями HOME и нормальными временами подтверждения.
- Затем отдельный процесс записывает заведомо неполный `audio-diagnostics.tmp`, как после обрыва сохранения. Строгий анализатор отвергает этот временный файл; первый CSV сохраняет свой SHA-256.
- Следующий независимый процесс сохраняет `audio-diagnostics-0001.csv`, вытесняя неполный `.tmp` без перезаписи `0000.csv`. Содержимое обоих корректных журналов сравнивается побайтно.
- Последующие процессы создают `audio-diagnostics-0002.csv` и `0003.csv` с искусственно инъецированными сбоями PCM/HOME. Из каждой группы по два журнала накапливается 4 800 подтверждённых PCM-страниц — достаточно для ранее установленных порогов сравнения.

В конце `analyze_switch_audio_log.py` проверяет все четыре файла; `compare_switch_audio_sessions.py` подтверждает `NO_REGRESSION_FLAG` для эталонной группы и `POTENTIAL_REGRESSION` для инъецированных ошибок/задержек. В проблемной группе должны быть распознаны ошибки PCM и HOME, а также увеличение p95 времени подтверждения. Все временные значения здесь **синтетические**, не показания реального `audout`.

Локально:

```sh
make build/switch_audio_export_session
python3 tests/test_switch_audio_export_restart_e2e.py
```

Этот сценарий входит в `make test`, `make test-audio-stream` и CI **Host SPU audio regressions**. Его входные файлы и режимы тестового процесса `tests/switch_audio_export_session.c` не включены в поставляемый Switch NRO; штатный экспортёр из `source/vh_audio_diag_export.c` используется одновременно в NRO и host-фикстуре.

На консоли для нескольких реальных прогонов требуется нажать Minus → Y, затем штатно выйти кнопкой Plus, повторно запустить NRO и выбрать свободные номерные CSV. При обнаружении оставшегося `.tmp` не трактуйте его как удачный отчёт. Программные проверки демонстрируют непротиворечивость файлового протокола, но **не доказывают сохранность данных после реального отключения питания**: FAT, контроллер и кэш SD-карты могут вести себя иначе.

## Автоматический анализ CSV — этап №204

После штатного выхода через Plus и копирования файла `audio-diagnostics-0000.csv` со своей Switch на компьютер можно выполнить **локальный анализ без сети и без игровых ресурсов**:

```sh
python3 tools/analyze_switch_audio_log.py /path/to/audio-diagnostics-0000.csv
```

Для машинной обработки или сравнения нескольких сеансов:

```sh
python3 tools/analyze_switch_audio_log.py --format json session1.csv session2.csv > audio-reports.json
```

Результат содержит типы событий, количество подтверждённых PCM-страниц в сохранённом окне, изменения счётчиков ошибок, число повторяющихся групп ошибок в пределах **60 секунд**, возможные паузы вывода дольше **10 секунд**, количество переходов в `ERROR` и показатели подтверждения PCM-буферов (медиана, p95 и максимум, в микросекундах). При ошибочном формате, неправильных типах данных или неправильной временной последовательности программа завершится кодом **2**, не выдавая ошибочный отчёт.

Обозначения результата:

- `NO_OBSERVED_FAULTS` — в **сохранённом отрезке** не обнаружены признаки сбоев; это **не сертификат исправности звука**.
- `REVIEW` — обнаружены подозрительные задержки, нарушения счётчиков или временной шкалы.
- `INVESTIGATE` — обнаружены приращения ошибок, вход в `ERROR` или возможное отсутствие новых страниц PCM при активном состоянии.

**Принципиальное ограничение:** аппаратный журнал хранит **лишь последние 128 записей**. Начальное значение каждого накопительного счётчика принимается за *базу*, а не за число происшествий за всё время запуска. Анализатор подсчитывает лишь приращения между сохранёнными строками и отдельно отмечает сбросы счётчиков. Если `first_pcm_count` вырос сразу на несколько единиц, известна лишь последняя задержка `last_pcm_us`: остальные индивидуальные значения восстановить нельзя. Данные `worst_pcm_us` отражают максимальное время подтверждения освобождённого буфера, **не** время появления звука из динамика.

Повторяющиеся ошибки группируются по времени и счётчикам `pcm_fail`, `home_fail`, `lease_fail`. Группировка — признак для исследования, а не доказательство аппаратной неисправности. Возможная остановка PCM помечается только когда обе соседние записи показывают `PLAYING`, между ними прошло хотя бы 10 секунд и `output_pages` не вырос. Редкие снимки могут скрывать краткосрочные события или реальный переход HOME; такие выводы нужно сверять с ручным протоколом и прослушиванием.

Скрипт проверяется в GitHub Actions на искусственных CSV, в том числе с обрезанным журналом, переполнением счётчиков, неверным заголовком, повреждёнными строками, несколькими кластерными ошибками и тестом CLI. **Реальных измерений физической Nintendo Switch пока нет.**

## Сравнение стабильности звука между версиями NRO — этап №205

Чтобы искать регрессии после изменений аудиодвижка, запишите **как минимум две разные сессии** на каждой из двух версий NRO. Сохраняйте CSV из каждой сессии отдельно: новые версии создают номерные файлы и не перезаписывают прежние отчёты. Рекомендуется повторять одинаковые условия (handheld/dock, динамики/HDMI/Bluetooth, количество переходов HOME, длительность, путь запуска homebrew) и записывать SHA сборки NRO.

```sh
python3 tools/compare_switch_audio_sessions.py \
  --baseline old-session-1.csv old-session-2.csv \
  --candidate new-session-1.csv new-session-2.csv \
  --baseline-version old-git-sha \
  --candidate-version new-git-sha
```

Машиночитаемый отчёт:

```sh
python3 tools/compare_switch_audio_sessions.py \
  --baseline old-session-1.csv old-session-2.csv \
  --candidate new-session-1.csv new-session-2.csv \
  --format json > comparison.json
```

Инструмент работает локально, не подключается к Switch и не требует оригинальных музыкальных файлов. Он анализирует только **сохранённые окна до 128 снимков**, а не всю историю сессии. Начальные накопленные значения ошибок/PCM/HOME **не считаются** новыми событиями; сравниваются их наблюдаемые приращения.

Показатели сравнения:

- `pcm_fail`, `lease_fail`: количество зарегистрированных ошибок на **10 000 завершённых PCM-страниц**.
- `home_fail`: ошибки на **100 зарегистрированных возвратов HOME** (не число PCM-страниц).
- `ack_latency_p95_us`: 95-й процентиль подтверждённого завершения PCM-буфера **в микросекундах** по доступным отдельным измерениям. Это не задержка звука в динамиках.
- Раздел `quality_problems` отмечает один снимок, отсутствие EXIT, откат часов, откат счётчиков и недостаточное число PCM-страниц. Данные с такими дефектами нельзя автоматически объявить регрессией.
- `warnings` отдельно указывает обрезанные окна (без START), неодинаковую частоту HOME, недостаток отдельных измерений задержек и невосстановимые пропущенные значения.

Минимум для сравнения: **2 разных CSV на версию**, не менее **1 000 наблюдаемых завершённых PCM-страниц на каждый CSV** и отсутствие откатов накопительных счётчиков. Для скорости сбоев HOME дополнительно нужно не менее **10 зарегистрированных возвратов в каждой группе**; для сравнения задержек p95 — не менее **10 индивидуальных измерений в каждой группе**. Недостаточные показатели помечаются `comparable: false`, а не трактуются как ноль.

В отчёте используются осторожные оценки:

| Вердикт | Значение |
| --- | --- |
| `NO_REGRESSION_FLAG` | Доступные сопоставимые показатели не пересекли пороги ухудшения. Не доказывает отсутствия регрессии |
| `POTENTIAL_REGRESSION` | Зафиксировано ухудшение по настроенным эвристикам: исследовать вручную и повторить аппаратный тест |
| `INCONCLUSIVE` | Группы короткие или повреждены; количественное сравнение преждевременно |

Эвристика для ошибок требует **минимум три события в новой группе**, рост частоты как минимум в **1,5 раза** и минимум **+0,5 ошибки на соответствующий масштаб**. Для задержки p95 требуется рост как минимум в **1,5 раза** и не менее **20 000 мкс**. Эти пороги — диагностические, **не статистическая оценка значимости**, особенно на малом числе сеансов.

Коды возврата CLI: **0** для `NO_REGRESSION_FLAG` и `INCONCLUSIVE` (программы должны проверять сам вердикт), **1** для `POTENTIAL_REGRESSION`, **2** для повреждённых CSV/неправильных аргументов. Дублирование одного CSV в группе запрещено: копирование файла не создаёт независимую сессию.

Тесты сравнения входят в `make test`, `make test-audio-stream` и GitHub Actions. Проверяются синтетические ухудшения, рост ошибки на разном объёме PCM, обрезанные окна, различные HOME-нагрузки, недостаток измерений и некорректные/повторные файлы. **Физических результатов Switch пока нет**; отчёт не заменяет слуховое тестирование.

## Сквозной сценарий восстановления HOME/сна — этап №206

Добавлен тест реального программного пути от **SEQ → SPU → реверберация → ресемплер → восстановление аудиовывода → диагностический журнал → CSV → анализаторы**. Он использует тот же модуль `vh_audio_diag_journal.c`, что и Switch, и те же поля `VhAudioDiagnostics`. Вместо вручную написанных фиктивных CSV тест записывает **счётчики из двух параллельных аудиопотоков**: контрольного и с преднамеренно отклонёнными PCM-отправками и ошибками запуска.

Один симулированный прогон `tests/test_vh_music_lifecycle_soak.c` синтезирует **512 PCM-страниц, 63 HOME/сон-перехода, 12 временных отказов запуска и 67 повторных отправок PCM**, сохраняя идентичные PCM-данные, музыкальное время, переходы сцен и содержимое ревербератора в обоих потоках. По желанию он записывает два журнала в **точном 18-колоночном формате** Switch:

```sh
make build/test_vh_music_lifecycle_soak
./build/test_vh_music_lifecycle_soak --csv-prefix /tmp/vh-206
python3 tools/analyze_switch_audio_log.py /tmp/vh-206-clean.csv /tmp/vh-206-fault.csv
```

Без `--csv-prefix` C-тест ничего не записывает. Экспорт выполняется **после** закрытия имитируемого аудиоустройства и отсоединения банков. Память журнала по-прежнему ограничена 128 последними снимками, а записанная временная шкала искусственная. Временные показатели подтверждения PCM в этих журналах специально задаются **12 000 мкс**: они **не** являются измерением реального `audout` или фактического вывода звука на Switch.

`tests/test_switch_audio_telemetry_e2e.py` дважды выполняет C-симуляцию, читает четыре полученных CSV, подтверждает обнаружение аппаратно-подобных ошибок **только** в соответствующем потоке, отсутствие откатов часов и накопительных счётчиков, сохранение последнего PCM и 63 возобновлений. Затем он сравнивает два набора через `compare_switch_audio_sessions.py`.

**Ожидаемый результат сравнения — `INCONCLUSIVE`.** Даже при видимых ошибках 512 подтверждённых PCM-страниц на сеанс не достигают ранее установленного порога **1 000**, а журнал содержит только последние 128 событий. Выдавать уверенный вердикт `POTENTIAL_REGRESSION` по такому краткому окну было бы неверно. Сквозной тест специально блокирует подобную ложную оценку, не скрывая сами сбои в подробных отчётах.

Проверки доступны через:

```sh
make test-audio-stream
# или отдельно после сборки C-теста
python3 tests/test_switch_audio_telemetry_e2e.py
```

GitHub Actions выполняет их в стандартном аудиопроцессе; C-сценарий дополнительно запускается под ASan/UBSan. Он не использует оригинальные игровые ресурсы, не замеряет реальную задержку HOME и не проверяет слышимые щелчки. Настоящие аппаратные CSV со Switch остаются отдельным, обязательным этапом проверки.

## Длинные сопоставимые испытания — этап №207

Короткий сценарий этапа №206 корректно возвращал `INCONCLUSIVE`, потому что 512 подтверждённых PCM-страниц было меньше минимального объёма 1 000 на сеанс. Для проверки самих сравнительных порогов добавлен **второй, независимый по параметрам профиль** к тому же C-движку синтетического воспроизведения:

- **2 048 PCM-страниц на сеанс**, 10 последовательных циклов HOME/сон, 2 восстановимых отказа повторного запуска, 7 ошибок PCM-отправки у потока с инъекцией отказов.
- Пауза выполняется каждые 192 PCM-блока, а редкие ошибки PCM распределены по всему сеансу. Это сохраняет все 2 048 страниц в **128-строчном кольцевом журнале** без потери базового START; слишком частые ошибки вытеснили бы нужные исходные снимки, даже при длительном воспроизведении.
- Во время каждого HOME/сна проверяется, что **23 последовательных замороженных шага** не продвигают PCM-страницы, музыкальные часы, SPU, ресемплер, хвост реверберации и количество записей журнала.
- Сквозной Python-тест дважды запускает C-сценарий, получая **четыре независимых CSV** (две чистые сессии, две с отказами). Обе группы содержат по 4 096 наблюдаемых PCM-страниц и по 10 счётчиков HOME. Времена подтверждения PCM `12 000 мкс` — **синтетические константы**, не время консоли.

Запустить локально:

```sh
make build/test_vh_music_lifecycle_soak
./build/test_vh_music_lifecycle_soak --long-csv-prefix /tmp/vh-long
python3 tools/analyze_switch_audio_log.py /tmp/vh-long-clean.csv /tmp/vh-long-fault.csv
python3 tests/test_switch_audio_long_cohort.py
```

Тест `tests/test_switch_audio_long_cohort.py` проверяет **два положительных сценария**: идентичные чистые сессии получают `NO_REGRESSION_FLAG`; исправно обработанные, но намеренно добавленные ошибки PCM/HOME в проблемной группе корректно обнаруживаются как `POTENTIAL_REGRESSION` с нормировкой на число PCM-страниц и HOME-событий. Он также проверяет достаточность индивидуальных измерений задержек и отсутствие ложного роста p95.

Обратите внимание: `POTENTIAL_REGRESSION` в этих CSV **не означает неисправности рабочего аудиодвижка** — ошибки намеренно внесены *в тестовый имитатор*, а PCM-данные, аудиочасы и реверберация продолжают совпадать с контрольным потоком. Это тест устойчивости инструментов диагностики, а не свидетельство аппаратной поломки.

Обычный запуск `test_vh_music_lifecycle_soak` или `--csv-prefix` **по-прежнему использует оригинальный профиль 512 страниц / 63 HOME-паузы**, чтобы не менять уже проверенные сценарии. Длинный профиль выбирается только явно и работает лишь на host-компьютере, не добавляя нагрузку в выпускаемый Switch NRO. Проверки входят в `make test`, `make test-audio-stream` и GitHub Actions.

**Реальные журналы с физической Nintendo Switch пока не получены.** Уверенность диагностических порогов на искусственных числах не подтверждает качество звука из динамиков или задержку реального HOME.

## Сохранение истории при переполнении журнала — этап №208

При очень длительном воспроизведении или частом появлении ошибок 128-строчный журнал ранее терял **и начальный снимок накопительных счётчиков**, и хронологию старых событий. В таком файле внешние анализаторы могли ошибочно принять спокойный конец сессии за отсутствие проблем за всю сессию.

Теперь первоначальный снимок `START` хранится **отдельно от кольцевого буфера** в фиксированной памяти. При переполнении экспорт содержит:

1. Первоначальный `START` — исходные значения накопительных счётчиков.
2. Специальную строку **`GAP`** — первый из сохранённых поздних снимков (самые старые подробные строки уже вытеснены).
3. Последние 126 хронологических снимков, включая финальный `EXIT`.

Общее число строк **по-прежнему не превышает 128**, структура CSV остаётся прежней (18 колонок), память не растёт в течение сессии. `GAP` — новое возможное значение колонки `event` в экспортируемом CSV; для чтения новых файлов требуется обновлённый Python-анализатор проекта.

**Что сохраняется:** разность накопительных счётчиков между началом и концом сессии (например `pcm_fail`, `home_fail`, `lease_fail`), даже если произошедшие в начале ошибки вытеснены. Анализатор показывает их в полях `unlocalized_faults` и `observed_counter_increments` и выставляет `INVESTIGATE`, когда такие ошибки ненулевые.

**Что восстановить нельзя:** точное время и порядок вытесненных ошибок, отдельные значения задержек `last_pcm_us`, распределение старых инцидентов по 60-секундным кластерам. Ошибки из `GAP` **не привязываются искусственно ко времени границы**, не учитываются как возможная 10-секундная остановка PCM и не добавляются в выборку p95. Пропавшие индивидуальные задержки отмечаются в `missing_individual_samples`.

При сравнении NRO, если хотя бы одна сессия содержит `GAP`, инструмент возвращает **`INCONCLUSIVE`** с явным объяснением, даже если полные накопительные суммы ошибок видны и PCM-страниц достаточно. Это не скрывает ошибки: они остаются в отчёте, но детальная временная структура была утрачена, поэтому сравнение некорректно считать доказанным.

Регрессия на стороне C записывает **более 1 400 строк** после первых 8 ошибок PCM, 3 ошибок HOME и 2 ошибок освобождения буфера; затем проверяет, что `START`, `GAP`, исторические суммы и `EXIT` экспортируются корректно, несмотря на много оборотов кольца. Python-регрессии проверяют, что старые инциденты видны без ложных кластеров, а сравнение версий остаётся консервативным.

Это **проверка корректности журнала**, не аппаратное воспроизведение; на физической Switch по-прежнему необходимы реальные испытания и прослушивание.

## Воспроизводимый протокол

1. **Базовая запись.** Запустите NRO, включите Minus и убедитесь, что `STATE PLAYING`; записывайте `FIRST PCM COUNT`, `WORST PCM US`, `PCM FAIL`, `HOME FAIL`, `LEASE FAIL` и субъективно слышимые артефакты. В синтетическом режиме выберите героя клавишей A, сделайте B/смену сцены и убедитесь, что музыка переключается.
2. **HOME/возврат ×10.** При активном звуке нажмите HOME, оставьте приложение в фоне 5–10 секунд и вернитесь. После каждого возвращения проверьте, что звук снова идёт, `STATE PLAYING`, увеличиваются необходимые счётчики, музыкальная сцена не сбрасывается неожиданно. Зафиксируйте щелчок, тишину, дубликат звука или задержку, если они слышны. Не ожидайте дополнительных PCM-страниц во время паузы.
3. **Сон/пробуждение ×5.** При активной музыке переведите Switch в сон, подержите 30–60 секунд, разбудите, вернитесь в приложение и повторите измерения. Отметьте, было ли устройство подключено к док-станции, ТВ или наушникам.
4. **Смена сцены во время теста.** Сделайте несколько переходов «поле → выбранный герой → поле» с A/B/D-Pad до и после HOME/сна; послушайте переходы, хвост реверберации и отсутствие застрявших нот. Помните, что прототип использует две синтетические сцены, когда оригинальные активы отсутствуют.
5. **Штатный выход ×3.** При активной музыке нажмите Plus. Проверьте отсутствие зависания приложения; при фокусированном выводе используется максимум 12 мс ожидания для необязательного 2-мс затухания. Затем запустите NRO повторно и убедитесь, что накопленные ошибки не переносятся в новый сеанс.
6. **Отказ/восстановление.** Если появляется `STATE ERROR`, запишите значения всех счётчиков и обстоятельства. Не продолжайте тест в расчёте, что музыка сама восстановится после терминальной ошибки.

## Критерии оценки

**Программные тесты CI** проверяют только форматирование панели, стабильную сборку devkitPro, проверки SPU, обработку аудиосеансов, санитайзеры и синтетические PCM-траектории. **Аппаратную готовность** можно подтвердить лишь на физической консоли: стабильный вывод, возврат из HOME/сна, отсутствие зависаний, корректный exit и субъективно приемлемая непрерывность звука.

Даже при `WORST PCM US` ниже некоторого порога нельзя утверждать отсутствие слышимой задержки: libnx сообщает об освобождении буфера, а не о времени первого физического звучания. Любые аппаратные результаты должны быть отдельно отмечены как **измеренные**; пока таковых нет.
