# Vandal Hearts Remake — этап №228: сохранность старой контрольной точки при пополнении истории

**Аппаратный статус — `HARDWARE NOT TESTED`.** Это проверка воспроизводимости компьютерных доказательств, не испытание физической Nintendo Switch. Успех не означает, что музыка действительно воспроизводилась, а операторские карточки подлинны.

## Какая проблема решена

На этапе [№227](SWITCH_AUDIO_STAGE227_CROSS_COPY_CHECKPOINTS.md) две полные копии истории можно было сравнить между собой. Однако у одного набора архивных доказательств история **растёт**: новая запись №2 добавляется к уже закреплённой записи №1. Проверять старую контрольную точку командой полного воспроизведения против **уже удлинённого каталога** неправильно — этап №226 требует точного совпадения текущего числа файлов с запрошенной длиной.

[Инструмент `tools/verify_switch_audio_checkpoint_continuity.py`](../tools/verify_switch_audio_checkpoint_continuity.py) проверяет преемственность иначе: он читает сохранённую старую контрольную точку с её независимо закреплённым SHA-256, затем **заново проверяет всю текущую удлинённую историю**, включая каждый NRO, исходный CSV, архив и квитанцию. После этого он требует, чтобы **все старые записи**, в том же порядке и с теми же SHA-256, оставались точным префиксом новой истории.

Поэтому отдельную копию старого каталога сохранять не обязательно, но **сам старый JSON-контрольный снимок и его независимый SHA-256 сохранить обязательно**.

## Последовательность

1. Создайте первую проверенную цепочку №226, а затем [контрольную точку №227](SWITCH_AUDIO_STAGE227_CROSS_COPY_CHECKPOINTS.md). Сохраните отдельно файл `prior-checkpoint.json`, его фактический SHA-256, HEAD цепочки и точное количество записей.
2. Добавьте новую запись по процедуре №226 — только с прежним закреплённым HEAD и прежним количеством элементов. Не редактируйте старые ZIP, CSV, квитанции и старые JSON.
3. Создайте **новую** контрольную точку этапа №227 для нового количества и нового HEAD, сохранив её отдельный SHA-256.
4. Сверьте переход при помощи нового инструмента:

```sh
python3 tools/verify_switch_audio_checkpoint_continuity.py \
  --prior-checkpoint /safe/outside-evidence/prior-checkpoint.json \
  --prior-checkpoint-sha256 ACTUAL_PREVIOUS_CHECKPOINT_SHA256 \
  --prior-head-sha256 ACTUAL_PREVIOUS_CHAIN_HEAD_SHA256 \
  --prior-count 1 \
  --current-root /safe/path/audio-history-226 \
  --current-checkpoint /safe/outside-evidence/current-checkpoint.json \
  --current-checkpoint-sha256 ACTUAL_CURRENT_CHECKPOINT_SHA256 \
  --current-head-sha256 ACTUAL_CURRENT_CHAIN_HEAD_SHA256 \
  --current-count 2 \
  --require-growth
```

Числа `1` и `2` выше приведены **только как пример**. Указывайте фактические числа из независимых записей. Хеши должны быть переданы из отдельного доверенного места, а не просто прочитаны из того же потенциально изменённого каталога. Включайте `--require-growth` при обязательном добавлении новой сессии.

## Результаты

| Результат | Интерпретация |
| --- | --- |
| `CONTINUITY_PRESERVED_WITH_NEW_RECORDS` | Старая цепочка сохранена без изменения, появились новые полностью проверенные записи |
| `CONTINUITY_PRESERVED_NO_GROWTH` | Старая история сохранена, но новых записей нет |
| `INVALID_EVIDENCE` | Не совпали независимые HEAD/count/SHA, изменён старый элемент, потеряны данные или выявлена другая ошибка аудита |

При `--require-growth` отсутствие новых записей даёт `HISTORY_NO_GROWTH` / `INVALID_EVIDENCE` с кодом `2`. Успешное сравнение без этого флага возвращает код `0`, **но это не аппаратный PASS**.

Специальные ошибки включают `HISTORY_ROLLBACK` при сокращении длины, `HISTORY_PREFIX_DIVERGED` при перестановке или изменении прежних записей, `HISTORY_PRIOR_ANCHOR_MISMATCH` при несоответствии старой контрольной точки старому закреплённому HEAD/count. Нарушение исходных ZIP/CSV/квитанций блокируется нижележащим аудитом №223–227.

`new_record_inventory` перечисляет исключительно добавленные записи с `sequence`, SHA-256 записи/ZIP/квитанции и статусом анализа. `old_records_changed: false` появляется только после точного сравнения старого префикса с полностью перепроверенной новой цепочкой.

## Безопасность и научная интерпретация

- Утилита **только читает** архивы, NRO, CSV, карточки, квитанции и контрольные точки. Новые папки не создаются, источники не переписываются, секретные ключи и серийные номера Switch не нужны.
- Контрольная точка может быть подменена **вместе** со своим контрольным хешем, если все хеши хранятся рядом без независимой записи. Поэтому внешние контрольные SHA-256/HEAD/count — обязательная часть процедуры.
- Старые файлы могут быть заменены валидными новыми файлами при полном контроле злоумышленника над историей и внешними хешами; это не цифровая подпись и не неизменяемое удалённое хранилище.
- Новая запись не доказывает независимого физического запуска или правильного звука. Все устройства, результаты прослушивания и H01–H07 остаются **самозаявленными**, пока человек не проведёт испытание на физической Switch и не оформит заключение.

[17 синтетических регрессионных тестов](../tests/test_verify_switch_audio_checkpoint_continuity.py) покрывают рост цепочки, отсутствие роста, исходную GENESIS, неверные SHA/HEAD/count, изменение старой контрольной точки, повреждение старого ZIP и новой квитанции, пропуск первой записи, расхождение префикса, откат истории, CLI-результаты и неизменность входных файлов. Они включены в `make test` и `make test-audio-stream`. Реальных журналов Nintendo Switch в тестах нет.
