# MAP02 — два слова VRAM в одном нативном DrawOTag

Этот экспериментальный путь дополняет [однопиксельную синхронную
корреляцию](MAP02_PUTPIXEL_DRAWOTAG_CORRELATION.md) и **не** заменяет
анализ независимых приватных сеансов. Он захватывает события ровно
**двух разных** координат VRAM из **одного инструментированного
экземпляра** оригинального публичного PC-порта.

## Генерация из закреплённого PC-источника

Исходники должны точно совпадать с публичным PC-портом на коммите
`14552fffa0e0b47e02b57592e274fc6e7a649923`.
`tools/instrument_map02_multi_putpixel_scope.py` проверяет Git blob SHA
обоих файлов и отказывается перезаписывать существующую папку:

```sh
python3 -m tools.instrument_map02_multi_putpixel_scope \
  /private/VandalHearts-PcPort/platform/pc/src/libgpu.c \
  /private/VandalHearts-PcPort/platform/pc/src/pc_raster.c \
  --output-dir /private/map02-multiscope-build
```

Компилировать `libgpu.multiscope.c` и `pc_raster.multiscope.c`
**вместе**, вместо обычных копий PC GPU, с обоими флагами:
`-DVH_MAP02_GPU_CAPTURE -DVH_MAP02_MULTI_PUTPIXEL_SCOPE`.
Без этих флагов дополнительные функции исключены; оригинальные
`WritePixel` и `DrawOTag` не подменяются. Путь `s_hires`
не инструментирован.

Выбрать приватную директорию и два **разных** слова VRAM:

```sh
export VH_MAP02_GPU_CAPTURE_DIR=/private/map02-two-word-gpu
export VH_MAP02_GPU_CAPTURE_FRAME=12
export VH_MAP02_PUTPIXEL_DIR=/private/map02-two-word-gpu
export VH_MAP02_PUTPIXEL_FRAME=12
export VH_MAP02_PUTPIXEL_X=30
export VH_MAP02_PUTPIXEL_Y=30
export VH_MAP02_PUTPIXEL_X2=35
export VH_MAP02_PUTPIXEL_Y2=35
```

Все пути — заранее созданные локальные папки. Координаты и метки
кадров **синтетические примеры**, не доказанные координаты настоящей
MAP02. Некорректная или одинаковая пара координат отключает запись.
Перед запуском `tools.run_map02_private_native_capture` использует
обновлённый предварительный контроль: если указана `X2` или `Y2`,
обязательны **обе** ASCII-десятичные переменные, значения должны
попадать в VRAM 1024×512 и отличаться от основной пары `X/Y`.
Это только проверка конфигурации; она не доказывает, что конкретный
локальный EXE действительно собран с двухточечным наблюдателем.
Два адреса разделяют **один глобальный** `step`, один кадр и
`primitive_ordinal` каждого оригинального `DrawOTag`; события
сохраняют точный порядок между точками.

Ограничение — **64 вызова на обе точки суммарно**, не по 64 на
каждую. Достигший лимита журнал отклоняется как потенциально
обрезанный; для GPU-снимков действует отдельный лимит 64 события.

## Приватный манифест и проверка

После завершения приватного двухточечного захвата используйте команду
**проверки с публикацией**. Она вычисляет SHA-256 из реальных файлов,
проверяет всю цепочку GTE/FT4/OT/VRAM/PutPixel до появления
нового манифеста и только затем создаёт его приватно (права `0600`):

```sh
python3 -m tools.publish_map02_multi_capture_manifest \
  /private/map02-source /private/map02-two-word-gpu \
  > /private/map02-public-receipt-summary.json
```

Прежний файл `gpu-putpixel-multi-ot.json` никогда не перезаписывается;
ошибка в исходном журнале, алгоритме `BlendG1`, контрольной сумме
или попытка использовать ссылку для каталога оставляют свидетельство
неопубликованным. Публикатор теперь сохраняет **приватную опись SHA-256
всех плоских файлов** исходного и нативного каталогов (включая
GTE/FT4/OT и полные снимки VRAM), повторяет сравнение после полного
анализа и после `fsync` манифеста и каталога. Изменение файла,
подмена inode, ссылка, вложенная папка или превышение лимита
приводят к отказу; если манифест уже создан, обнаруженная ошибка
удаляет его. Опись остаётся **в оперативной памяти**, без публикации
частных имён и контрольных сумм отдельных игровых файлов. Пример
структуры нового манифеста:

```json
{
  "schema": "vh.map02.native-putpixel-multi-ot.v1",
  "source_frame": 411,
  "gpu_draw_frame": 12,
  "overdraw_manifest_sha256": "<SHA256 gpu-native-overdraw.json>",
  "native_events_sha256": "<SHA256 gpu-native-events.jsonl>",
  "putpixel_events_sha256": "<SHA256 putpixel-native-events.jsonl>"
}
```

Запуск проверки:

```sh
python3 -m tools.verify_map02_putpixel_multi_scope \
  /private/map02-source /private/map02-two-word-gpu \
  > /private/map02-multi-word-report.json
```

Валидатор обязательно повторяет исходный GTE/FT4/OT/VRAM-аудит,
проверяет совпадение кадров, SHA, строгий JSONL, **общий**
монотонный `step` и `primitive_ordinal`, ровно две различные
координаты, неизменность PC accurate/legacy-режима, оригинальную
арифметику `WritePixel/BlendG1`, непрерывность значения
каждого слова внутри примитива и границы **тех же самых**
полных снимков VRAM для обеих координат. Приписывать вызовы
исходным FT4 можно только по независимо проверенному пакету
и порядку OT. Любая необъяснённая наблюдаемая перемена выбранного
слова у сопоставленного FT4 отклоняется.

Публичный отчёт включает **только агрегаты**, контрольные суммы,
количество выборок и отдельные счётчики для ABR0–ABR3,
повторных записей и временного восстановления слова. Он не
включает значения BGR555, координаты, абсолютные пути, геометрию
или пользовательские игровые байты.

Дополнительный анализ сопоставленных исходных FT4 считает:

- `source_ft4_draws_with_both_words_observed` — количество
  исходных FT4, у которых зарегистрированы вызовы `PutPixel`
  для **обоих** выбранных слов;
- `source_ft4_draws_changing_both_sampled_words` — количество
  FT4 с изменениями **обоих** слов между собственными
  снимками PRE/POST; этот показатель не равен числу вызовов;
- `source_ft4_draws_with_both_words_semitransparent` —
  количество FT4, у которых для каждого из двух адресов
  зарегистрирован хотя бы один `semi=1`;
- `source_ft4_draws_with_interleaved_word_revisit` —
  количество FT4 с наблюдаемым возвратом к уже обработанной
  координате после другой, например `A → B → A` или
  `A → B → B → A`. Непрерывные `A → A → B` этому
  условию не соответствуют.
- `source_ft4_draws_with_both_words_changed_by_putpixel` —
  количество FT4 с **реально зарегистрированными изменившими
  слово вызовами PutPixel** по обоим выбранным адресам. Этот
  показатель может быть больше числа FT4 с изменениями обеих
  точек между снимками PRE/POST: промежуточная запись могла
  быть отменена следующим вызовом.
- `source_ft4_draws_with_both_words_changed_but_one_net_delta` —
  подмножество предыдущих FT4, где оба адреса временно
  менялись через PutPixel, но только **одно** слово отличается
  между полными VRAM-снимками этого примитива. Пример:
  `A: 0 → bit15 → 0` и `B: 0 → цвет` в одном FT4. Это
  доказательство *наблюдённой временной последовательности*,
  а не полноценной пиксельной растеризации.

Все показатели агрегированы **по FT4**; конкретные координаты
и порядок цветов наружу не выводятся. Они выявляют заявленные
совместные записи и пересечение *наблюдений* двух точек, но
не доказывают полное покрытие растеризацией, единственную
причину изменения VRAM или физическую точность PS1 GPU.

## Подготовка сборки двухточечного GPU и DDA через настоящий Make

Вместо ручной замены C-файлов в checkout теперь предусмотрен
**внешний Make-overlay** для закреплённого публичного US PC-порта.
Он объединяет в одном `libgpu.o + pc_raster.o` исходные события
GPU/VRAM, синхронные две точки `PutPixel`, ошибки растеризации,
вертикальные DDA-отклонения и *реально выполненные* DDA-span.
Все наблюдатели остаются опциональными. В частности, DDA-span
не доказывает горизонтальное покрытие строк, отклонённых до
вызова `dda_span`.

```sh
python3 -m tools.prepare_map02_private_gpu_make_overlay \
  /private/VandalHearts-PcPort \
  --output-dir /private/map02-pinned-gpu-make \
  > /private/map02-pinned-gpu-make-report.json

python3 -m tools.build_map02_private_gpu_make_overlay \
  /private/VandalHearts-PcPort \
  --output-dir /private/map02-pinned-gpu-make \
  --manifest /private/map02-pinned-gpu-make-report.json \
  --build-dir build-map02-private \
  > /private/map02-pinned-gpu-sealed-objects.json
```

После генерации и **непосредственно перед приватной линковкой**
можно независимо перепроверить подготовленный Make-overlay:

```sh
python3 -m tools.verify_map02_private_gpu_make_overlay \
  /private/VandalHearts-PcPort \
  --output-dir /private/map02-pinned-gpu-make \
  --manifest /private/map02-pinned-gpu-make-report.json \
  > /private/map02-pinned-gpu-make-audit.json
```

В Linux для сборки **только двух диагностических объектов** теперь
предпочтителен приведённый выше `build_map02_private_gpu_make_overlay`:
он сначала выполняет независимый аудит, затем закрепляет точные байты
оригинального Makefile, инструментированного Make-overlay и обоих C-файлов
в четырёх анонимных `memfd` с `F_SEAL_WRITE/GROW/SHRINK/SEAL`.
Перед препроцессированием сборщик читает список отслеживаемых
`.h`/`.inc`/`.hpp` из закреплённого коммита публичного PC-порта.
Каждый заголовок сверяется с исходным Git blob SHA-1, а затем его
байты помещаются в отдельный запечатанный Linux `memfd`.
Приватное дерево `-I` содержит только контролируемые ссылки
`/proc/self/fd/N` на эти неизменяемые файлы; никакие копии с
доступным для изменения содержимым больше не используются.
После препроцессирования проверяются целостность запечатанных байтов,
назначение каждой ссылки и точный инвентарь: посторонние файлы
или перенаправленные ссылки приводят к отказу. Количество
проверенных и запечатанных заголовков фиксируется в отчёте.
После этого GNU Make выполняет два препроцессорных прохода
из запечатанных C-файлов с исходными флагами компиляции. Полные
результаты раскрытия заголовков (по одному `.i` на каждый C-файл)
тоже запечатываются в `memfd`, а объектные файлы компилируются
только из этих двух неизменяемых препроцессированных входов.
Всего задействовано **шесть базовых дескрипторов плюс по одному
на каждый проверенный заголовок**;
их SHA-256 и два результирующих объектных SHA-256 отражаются
в приватном отчёте без раскрытия игровых ресурсов.
При отсутствии Linux sealing или ошибке аудита небезопасного
автоматического fallback к открытию путей нет. Сборка использует
новый пустой изолированный `BUILD_DIR` и проверяет два объектных SHA-256;
для полного локального запуска игры этот инструментарий не предназначен.

Перед вызовом препроцессора устанавливаются Linux `inotify`-наблюдатели
на каждую директорию приватного дерева `-I`. Если ссылка или имя файла
изменятся даже на мгновение и будут восстановлены до повторной проверки,
событие останется в очереди. Любое событие изменения либо переполнение
очереди приводят к отказу **перед компиляцией объектных файлов**.
Добавлены регрессионные тесты временной подмены ссылки и создания с
последующим удалением постороннего заголовка.

Это **не полная аттестация сборки**: контроль `inotify` относится только
к отслеживаемому приватному дереву, между установкой наблюдателей и
завершением препроцессирования; он обнаруживает, но не предотвращает
злонамеренное чтение во время подмены. Системные заголовки, другие
исходники, компилятор и его зависимости по-прежнему не удостоверены.
Полное раскрытие заголовков фиксируется в запечатанном `.i` только
**после завершения препроцессирования**.
Другие исходники, системные заголовки и сам компилятор не удостоверены
механизмом `memfd`. Не считайте успешную сборку аттестацией всего ELF,
подтверждением происхождения игрового журнала или разрешением
включить HD-графику. Ручной вызов `make -f Makefile -f ...` остаётся
доступным, но не получает эту гарантию привязки байтов ко времени
запуска компилятора.

Для проверки неизменности инструментов диагностики дополнительно
фиксируются SHA-256 исполняемых файлов драйвера системного `cc`,
`cc1` и ассемблера `as`. Обе стадии GNU Make запускаются с явно
закреплённым абсолютным путём к этому драйверу. После завершения
сборки бинарники повторно сверяются по SHA-256.

Список задействованных системных заголовков извлекается из
строк местоположения исходников `# line "PATH"`, которые GCC
записывает непосредственно в два препроцессированных файла `.i`.
Сборщик пересчитывает SHA-256 заголовков, фигурирующих в этих строках,
и повторно сверяет их после объектной компиляции. Это охватывает
пути, показанные препроцессором, но не является полным перечнем
всех системных файлов, использованных инструментами.
Приватный отчёт сохраняет только агрегированный SHA-256, число
заголовков и контрольные SHA-256 трёх инструментов — без имён
локальных заголовков и приватных путей.

Отдельно снимается ограниченный Linux `ldd`-инвентарь файлов
динамического загрузчика и разделяемых библиотек, разрешаемых для
драйвера GCC, `cc1` и `as`. Библиотеки сверяются по SHA-256 до и
после сборки. В отчёте сохраняются только их количество, агрегированный
SHA-256 и результат повторной проверки, без локальных путей.

Это **не** подтверждает, какие библиотеки фактически были отображены
дочерними процессами компилятора, и не заменяет аттестацию `ld.so`,
запущенных процессов, ядра или всех файлов инструментов. `ldd`
применяется только к уже выбранным системным бинарникам компилятора.
В дополнительном контролируемом запуске Make выставлены GNU
`LD_DEBUG=libs` и приватный `LD_DEBUG_OUTPUT`. Полученные журналы
динамического загрузчика разделяются по PID, а их записи
`initialize program` сопоставляются с драйвером GCC, `cc1` и `as`.
Для каждого требуется хотя бы одно наблюдение. PID в имени `trace.N`
должен совпадать с PID каждой непустой записи журнала; пути к
`cc1` и `as` сопоставляются с разрешёнными путями к выбранным
компонентам GCC, а не только с именем программы. Если загрузчик
указывает лишь `as`, оно разрешается через ограниченный системный
`PATH=/usr/bin:/bin`, используемый Make. Это не подтверждение
фактического `/proc/PID/exe`. Файлы из записей
`calling init` сверяются с уже проверенным набором `ldd` и SHA-256. В отчёте отображаются только численность процессов
по типу, число различных библиотек и агрегированный SHA-256.

Отдельно Linux-only инструмент дважды запускает драйвер GCC, `cc1`
и `as` как специально остановленные контрольные процессы:
`PTRACE_TRACEME` удерживает их на `SIGTRAP` сразу после `execve`,
а файл `/proc/PID/exe` сверяется по inode и SHA-256. Контрольные
процессы прекращаются до начала пользовательского кода. При отсутствии
поддержки `ptrace` защищённая сборка отклоняется. Всего фиксируются
шесть отдельных свидетельств. **Это не наблюдение за настоящими
дочерними процессами Make** и не доказывает их фактические inode.

Это **диагностическое свидетельство**, а не доказательство полноты:
журнал загрузчика не защищён от привилегированного вмешательства,
динамические загрузки после инициализации могут не попасть в набор
`calling init`, а подмена с последующим восстановлением между
измерениями теоретически возможна.


Основной этап компиляции двух GPU/DDA-объектов теперь сразу
запускает **настоящий GNU Make под Linux `ptrace`**, с неизменёнными
запечатанными файлами `.i` и исходным Makefile. События
`TRACEFORK`, `TRACEVFORK`, `TRACECLONE` и `TRACEEXEC`
позволяют наблюдать настоящие дочерние процессы Make; в момент
остановки `execve` бинарники GCC, `cc1` и `as` сравниваются
с выбранными SHA-256 и inode в `/proc/PID/exe`. Отсутствие
любой роли, изменённый исполняемый файл или ошибка трассировки
приводят к отказу. Результаты этого прохода становятся итоговыми
объектными файлами; отдельная повторная сборка объектов больше
не выполняется.

На остановке процесса непосредственно перед выходом (событие Linux
`PTRACE_EVENT_EXIT`) аудитор дополнительно читает отображения из
`/proc/PID/maps` реальных процессов GCC, `cc1` и `as`.
Для каждой отображённой разделяемой библиотеки он сверяет inode,
идентификатор устройства и SHA-256 с закреплённым списком
динамических зависимостей `ldd`. Отсутствие отображений любой
из трёх ролей или чужая библиотека приводят к отказу. В отчёте
сохраняются лишь количество, агрегированный SHA-256 и счётчики
процессов по ролям — без локальных путей.

Это позволяет удостоверить фактические исполняемые файлы
трёх выбранных дочерних компонентов **именно основной сборки**,
но не означает аттестацию всех системных программ или библиотек
и не заменяет реальный запуск MAP02. Оболочка, GNU Make, другие
утилиты, системные библиотеки и ядро не входят в проверку
исполняемых объектов этого уровня.

### Использование двух готовых объектов без подмены входов

После завершения настоящего GNU Make отдельный обязательный
`consume_map02_sealed_gpu_objects.py` вновь сверяет оба
`libgpu.o`/`pc_raster.o` по SHA-256 из квитанции основной
сборки и проверяет признаки подтверждённой компиляции.
Точные байты помещаются в два неизменяемых Linux `memfd`.
Команды `nm`, `strings` и `ld -r` получают **только**
`/proc/self/fd/N` этих дескрипторов; пути к обычным объектным
файлам не передаются binutils. Если объект подменили после
проверки, это не меняет компоновку уже запечатанных байтов.
Проверяются необходимые GPU-символы, две метки DDA и ELF ABI.

Связанный ELF сначала создаётся во временном каталоге; после
проверки структуры и SHA-256 публикуется через исключительную
жёсткую ссылку, не перезаписывая существующий результат.
Отдельная квитанция связывает SHA-256 исходных объектов с
SHA-256 связанного ELF и не содержит приватных путей.
**Имя опубликованного связанного файла само по себе не
запечатано**: дальнейшие потребители обязаны снова проверять
его SHA-256. Теперь следующим обязательным этапом CI запускается
`verify_map02_linked_gpu_object.py`: он связывает первичную
квитанцию со связанной, заново читает опубликованный ELF и
сравнивает SHA-256 до любого `nm`/`strings`. Затем запечатывает
именно проверенные байты в отдельный `memfd`, и только этот
дескриптор передаёт анализаторам. Отрицательные тесты проверяют
подмену дискового ELF до чтения, ложную исходную квитанцию,
символьную ссылку и подмену файлового пути после запечатывания.
Отчёт повторной проверки сохраняет контрольный SHA-256 и не
содержит приватных путей. **Любой последующий независимый
потребитель снова обязан проверять этот SHA-256**. Это не
доказательство выполнения MAP02.

### Защита цепочки квитанций в пределах одного процесса

Новый обязательный этап `run_map02_sealed_gpu_receipt_chain.py`
вызывает компиляцию, связывание и повторную проверку ELF
последовательно **в одном Python-процессе**. После каждого этапа
его JSON-квитанция канонизируется и помещается в неизменяемый
Linux `memfd`; следующий этап получает только независимо
прочитанную и проверенную копию. Ранее промежуточные JSON-файлы
в `/tmp` могли заменяться между отдельными запусками команд.
Теперь эти файлы не управляют следующим шагом цепочки.
Проверяются также отсутствие изменений переданных копий,
точное соответствие SHA-256 исходных объектов и связанного ELF,
и сохранение выключенного HD-gate.

Итоговый JSON содержит три квитанции и их SHA-256, но
`externally_authenticated=false`: корреляционные хеши внутри
одного отчёта **не являются подписью доверенной внешней стороны**.
Квитанция может быть аутентифицирована вне процесса лишь при
независимом закреплении хеша или ключа доверенным наблюдателем.
Этот шаг не доказывает реальный запуск MAP02.

Инспектор **не исполняет игру и не запускает Make**. Он
заново генерирует в памяти оба инструментированных исходника и
текст Make-overlay из трёх исходных файлов с закреплёнными
Git blob-хешами, отдельно повторяет проверку полного Git checkout,
сравнивает точные байты трёх подготовленных файлов и строго
перепроверяет исходный JSON-манифест. Символьные ссылки,
изменённые файлы, дополнительные файлы в каталоге,
дублированные ключи JSON и даже согласованная подмена
сгенерированного файла и записанного SHA-256 не принимаются.
Файлы читаются через дескриптор с запретом следования ссылкам
и проверкой идентичности inode/mtime/ctime до и после чтения.

Только приватные хеши **публичного инструментированного кода**
попадают в итоговый отчёт, без пути к исходному checkout и
без пользовательских игровых ресурсов. GitHub Actions
выполняет этот аудит дважды — до и после компиляции
GPU/PutPixel/DDA-объектов — и сравнивает оба отчёта. Повторная
проверка не удерживает каталог неизменным на всё время
последующей полной линковки: это отдельная контрольная точка,
а не доказательство неизменности кода после неё.

Если приватные оригинальные ресурсы и все штатные зависимости
PC-порта уже установлены локально, для полного линкования можно
использовать отдельную опциональную цель (она **не запускается в CI**):

```sh
cd /private/VandalHearts-PcPort/platform/pc
make -f Makefile -f /private/map02-pinned-gpu-make/map02_private_gpu.mk \
  REGION=us BUILD_DIR=build-map02-private map02-private-pc-link
```

Она добавляет исходной цели `link` требование `objs`,
чтобы до линковки гарантированно собрать все игровые,
графические и генерируемые data-объекты. Штатное правило
самой линковки остаётся оригинальным. Генератор дополнительно
проверяет соответствие закреплённому Makefile этого графа
зависимостей (`default -> GAME_O_FILES/BACKEND_OBJS`,
`objs -> default/DATA_OBJS`, `link -> DATA_OBJS`).
Тесты выполняют `make -n` с настоящей программой GNU Make
на синтетическом малом checkout: видны все приватные и игровые
объекты до строки линковки; при ошибочном регионе и пути
сборки правила закрываются отказом.

Это **инструкция для приватного запуска**, а не заявление,
что собственные игровые ресурсы доступны в среде GitHub
или что итоговый исполняемый файл уже создан.

Генератор требует совпадения Git blob-хешей оригинальных
`platform/pc/Makefile`, `platform/pc/src/libgpu.c` и
`platform/pc/src/pc_raster.c` с закреплённым коммитом.
Дополнительно проверяются **точный `git rev-parse HEAD`**
(`14552fffa0e0b47e02b57592e274fc6e7a649923`) и
`git status --porcelain --untracked-files=no`: изменённые
отслеживаемые игровые или backend-исходники запрещают генерацию
даже при правильных трёх GPU/Make blob-хешах.
Неотслеживаемые пользовательские игровые ресурсы при проверке
не перечисляются. При отказе приватные имена изменённых файлов
не выводятся. Это проверка состояния checkout во время генерации,
не непрерывная фиксация дерева до полного выполнения компилятора.
Он откажется работать внутри upstream, перезаписывать готовую
директорию и использовать путь с символами управления Make/shell.
Исходные файлы checkout **не меняются**; в Make-overlay
переопределяются ровно два объектных правила. Для внешних
генерируемых C-файлов сохраняется `-Isrc`, иначе они не смогут
найти локальные заголовки вроде `pc_gpu_internal.h`:
в обычной сборке исходники находятся непосредственно в
`platform/pc/src`, и компилятор ищет заголовок рядом с ними.
Разрешены только
`REGION=us` и изолированный `BUILD_DIR=build-map02-*`,
поэтому диагностические файлы не заменят обычные объекты
`build/` случайно. Внутри `BUILD_DIR` разрешены лишь
латинские буквы, цифры, дефис и подчёркивание; пустой суффикс,
пробелы, символы оболочки и компоненты `../` отклоняются
**до исполнения рецептов**. Это ограничение относится к имени
каталога, а не превращает GNU Make в песочницу для произвольных
внешних команд или непроверенных Makefile.

Для последующего полного локального `make ... link` понадобятся
**собственные** исходные игровые и BIOS-зависимые данные,
подготовленные по руководству публичного PC-порта, а также
системные зависимости SDL2/OpenAL и другие штатные библиотеки.
Они не копируются в новый Make-overlay и **никогда не должны
загружаться в GitHub Actions или в этот репозиторий**.
Сама компиляция двух GPU/DDA-объектов не требует игровых данных
и потому отдельно проверяется CI на настоящем Makefile
закреплённого PC-порта. После успешной компиляции CI сохраняет
в артефакт `map02-original-gpu-candidate-evidence` отдельный
`private-make-gpu-dda-objects.sha256` с тремя проверенными
SHA-256: `libgpu.o`, `pc_raster.o` и `gpu-two-word-dda.o`.
Это воспроизводимые хеши объектных файлов публичного PC-порта,
**не** приватные журналы, игровые данные или доказательство
исполнения карты.

Сборка этих объектов не означает успешную линковку игры,
наступление выбранного кадра, завершение полного захвата или
подлинность приватного MAP02-журнала. Перед первым приватным
запуском по-прежнему требуются инспектор ELF, строгие
квитанции v3 и независимый GPU/FT4/VRAM-аудит.

## Исполняемые проверки инструментирования

В дополнение к синтетическим Python-проверкам
`tests/test_instrument_map02_multi_putpixel_c11.py` компилирует
порожденный двухточечный наблюдатель вместе с маленьким
**искусственным** C11 `WritePixel`-драйвером. Он проверяет:

- что четыре вызова двух выбранных адресов попали в общий
  JSONL со сквозными `step` и исходными полями
  `frame/primitive_ordinal`;
- что вызов по третьему адресу, события вне заявленного кадра,
  совпадающие либо недопустимые координаты не создают
  лишние записи;
- что 70 последовательных вызовов ограничиваются
  **64 общими записями**, а не 64 для каждой точки;
- что компиляция без опционального флага не оставляет
  диагностические символы в обычном объектном файле.

GitHub Actions дополнительно компилирует
`libgpu.multiscope.c` и `pc_raster.multiscope.c`,
полученные из двух настоящих закреплённых публичных
исходников PC-порта, с включённым и выключенным
наблюдением, и запускает тесты приватной публикации
манифеста. Полный CI предыдущей версии на коммите
`af96c4edf10ea95eb2e2d6c94d65eba344c89f9f` успешно
завершился (GitHub Actions №39059304545); новые изменения
требуют новой проверки. Синтетический драйвер не
воспроизводит карту MAP02 или фактическую
полупрозрачную растеризацию игры.

## Сопоставление с завершённым приватным запуском PC-порта

Для одного выбранного нативного каталога теперь можно независимо
сопоставить **успешно перепроверенное свидетельство запуска**
(`map02_private_native_process_receipt_v1`) с двухточечным
FT4/PutPixel-свидетельством:

```sh
python3 -m tools.audit_map02_launch_two_word_binding \
  /private/map02-two-word-gpu /private/map02-source \
  --launch-receipt /private/map02-process-receipt.json \
  --preflight-report /private/map02-preflight.json \
  --executable /private/VandalHearts-PcPort/game \
  --require-native-elf-image \
  > /private/map02-launch-two-word-join.json
```

Команда сначала повторно проверяет оригинальную квитанцию
`run_map02_private_native_capture.py`: завершение процесса,
предзапусковый SHA-256 исполняемого файла, приватные журналы GPU
и DDA, снимки VRAM и неизменность исходных данных. Затем полностью
повторяет независимую проверку исходных GTE/FT4/OT, смешивания
BGR555 и обеих координат `PutPixel` на **том же** нативном
каталоге. Совпасть должны номер нативного кадра и SHA-256 точного
файла `gpu-native-events.jsonl`; одинаковые названия каталогов
или другие контрольные суммы это требование не заменяют.

Дополнительная защита от изменения файлов во время этого
составного аудита: **до первой проверки** создаётся приватная
опись SHA-256 и файловых метаданных всего плоского комплекта
исходных трасс и нативных снимков VRAM.

При **каждом** независимом повторном анализе квитанции запуска
`verify_map02_private_capture_receipt.py` также теперь удерживает
непубличные идентификаторы файлов `dev/inode/size/mtime/ctime`
для квитанции, `preflight` и локального исполняемого файла.
Небольшие JSON-файлы дополнительно связываются SHA-256 точных байтов,
прочитанных через дескрипторы с запретом символьных ссылок. После
проверки GPU/DDA идентичность всех трёх входов проверяется снова:
даже замена на **другой inode с теми же байтами**, изменение
исполняемого файла на месте или появление символьной ссылки
отклоняются. Для открытия применяется `O_NOFOLLOW/O_NONBLOCK/O_CLOEXEC`:
замена входа специальным FIFO не должна повесить проверку.
Отрицательные тесты охватывают FIFO для исполняемого файла,
preflight и итоговой квитанции. Это не закрывает все возможные
гонки в пользовательской
файловой системе и **не** доказывает, что проверенный исполняемый
файл действительно создал конкретный GPU-журнал. **После анализа FT4**
полностью повторяется проверка квитанции запуска, а затем
заново сопоставляются опись всех файлов и точные байты
двухточечного манифеста. Если файл или исполняемый процесс
изменился между проверками, итоговое согласованное свидетельство
не выдаётся. Это программный контроль непротиворечивости,
а не криптографическое свидетельство происхождения данных.

Публичная сводка сообщает только контрольные суммы двух
свидетельств, номер кадра и количество проверенных FT4; ни
координаты, ни цвета, ни локальные пути не публикуются.

Это **связь согласованных файловых свидетельств**, а не
криптографическое доказательство, что именно запущенный процесс
на самом деле сформировал все файлы: прежний наблюдатель не
имеет аутентифицированного ядром канала записи. Поля
`native_process_to_log_causality_authenticated`,
`retail_map02_gameplay_authenticated` и
`ps1_or_switch_pixel_equivalence_verified` поэтому
всегда равны `false`. Настоящий захват по-прежнему требует
локального оригинального исполняемого файла пользователя
и его приватных игровых ресурсов.

### Исполнение закреплённого бинарного файла на Linux

Теперь `run_map02_private_native_capture.py` после preflight и до
создания процесса открывает пользовательский исполняемый файл через
`O_NOFOLLOW/O_NONBLOCK/O_CLOEXEC`, подтверждает SHA-256 точных
байтов и идентичность `dev/inode/size/mtime/ctime`. На Linux
`subprocess.Popen` получает `executable=/proc/self/fd/N` и
`pass_fds=(N,)`: ядро исполняет **уже открытый файл**, а не
выполняет повторный поиск по потенциально заменённому пути.
Для ELF `argv[0]` остаётся оригинальным путём; для скрипта
с shebang имя сценария может отображаться как `/proc/self/fd/N`.
Дескриптор остаётся открытым у родителя до конца процесса,
после чего перепроверяется идентичность открытого inode и
существующего пути, а дескриптор закрывается.

Тесты с синтетическим скриптом меняют путь **в момент Popen**:
исполняется исходный закреплённый файл, но подмена пути
приводит к `executable_changed` и отказу подтверждать
захват. Подмена сразу после preflight и до открытия
закреплённого дескриптора также отклоняется. Для платформ
без Linux `/proc/self/fd` этот маршрут закрыт: автоматического
отката к обычному запуску по пути нет.

Это уменьшает гонку проверки SHA и исполнения, но не
защищает от всех видов изменения содержимого **того же inode**,
аутентификации процесса-писателя GPU или проверки прав на
игровой образ. Настоящий исполняемый файл игры должен быть
проверен отдельно, а локальные ресурсы пользователя
по-прежнему не загружаются в GitHub.

### Проверка готовности локального PC ELF к захвату

Перед тем как пытаться записывать настоящую карту MAP02, запустите
**отдельную статическую проверку** локально собранного PC-порта:

```sh
python3 -m tools.check_map02_private_pc_binary \
  /private/VandalHearts-PcPort/game \
  > /private/map02-private-elf-readiness.json
```

Команда не исполняет игру и не читает игровой образ. Она проверяет
ELF, SHA-256, неизменность файловой идентичности и наличие четырёх
диагностических символов в локальной `nm`-таблице. `nm` анализирует
тот же закреплённый дескриптор `/proc/self/fd/N` с `pass_fds`,
а не повторно открывает исходный путь к бинарнику; подмена пути
во время анализа приводит к отказу. Требуемые функции:
`VH_CaptureEvent`, `VH_Map02PixelScopeSet`,
`VH_Map02PixelScopeClear` и `VH_PixelSampleRecord`.
Программа `nm` выбирается только из системных каталогов `/usr/bin:/bin`,
без доверия пользовательскому `PATH`, и запускается с очищенным окружением.
Отрицательный тест подставляет ложную `nm` в пользовательский `PATH`
и проверяет, что инспектор её не исполняет.
Дополнительно требуются строковые селекторы второй координаты
`VH_MAP02_PUTPIXEL_X2/Y2`. Отсутствующие символы,
`strip`-обработанный ELF, скрипт или подмена inode
отклоняются. Инструмент возвращает только агрегированные
флаги готовности и SHA-256 самого исполняемого файла —
без приватных путей, символов в отчёте, координат и игровых данных.

Для первого захвата можно **потребовать** эту проверку
непосредственно до запуска, без отдельного ручного шага:

```sh
python3 -m tools.run_map02_private_native_capture \
  --require-native-elf-image \
  --require-native-probe-symbols \
  --executable /private/VandalHearts-PcPort/game \
  --preflight-report /private/map02-preflight.json \
  --summary-report /private/map02-process-receipt.json \
  --timeout-seconds 300
```

Такой запуск сначала закрепляет открытый дескриптор ELF, сверяет
его SHA-256 с preflight и выполняет `nm` **на этом же дескрипторе**
через `/proc/self/fd/N`, а не на повторно открытом пути.
Тот же самый FD затем используется для запуска дочернего процесса.
Идентичность пути и дескриптора повторно проверяется после инспекции
и после публикации preflight-квитанции, ещё до `Popen`, поэтому даже
замена на **другой inode с идентичными байтами** отклоняется
до запуска. Все эти проверки предшествуют или сопровождают
наблюдение `/proc/<pid>/exe` у настоящего нативного процесса. Успешный
локальный захват получает отдельную приватную квитанцию
`map02_private_native_process_receipt_v3` с обязательными
`native_probe_symbols_required=true` и
`native_probe_symbols_inspected=true`. В повторной проверке
квитанции ELF-инспектор запускается **ещё раз** и требует тот же
SHA-256. Старые v1/v2 остаются совместимы, но **не могут**
пройти новый флаг `--require-native-probe-symbols` при
связывании источника, GPU и FT4.

Для объединённого свидетеля используйте оба флага:
`--require-native-elf-image --require-native-probe-symbols`
в `tools.audit_map02_launch_two_word_binding`. При несовпадении
режимов аудит отказывает, не подтверждая реальный кадр MAP02.

**Это предварительная подсказка о наличии кода**, а не доказательство,
что он исполнялся или был получен из закреплённых исходников.
Строковые литералы и таблицу символов возможно подделать.
Проверка проводится независимо от последующего `--require-native-elf-image`
и не заменяет мониторинг GPU, DDA, PutPixel, FT4 и VRAM.
При сборке без `-g` локальные символы могут всё же сохраняться;
при полном удалении таблицы `nm` инспектор отказывает, не
пытаясь обходить отсутствие доказательств.

### Строгий режим нативного ELF для первого реального PC-захвата

Для подлинного Linux PC-порта доступен отдельный, **необязательный**
режим запуска:

```sh
python3 -m tools.run_map02_private_native_capture \
  --require-native-elf-image \
  --executable /private/VandalHearts-PcPort/game \
  --preflight-report /private/map02-preflight.json \
  --summary-report /private/map02-process-receipt.json \
  --timeout-seconds 300
```

Режим применяет все существующие проверки исполняемого файла,
окружения, GPU/VRAM и DDA, но до запуска дополнительно требует
подходящий Linux **ELF32/ELF64**, а после `Popen` сверяет
`/proc/<pid>/exe` ядра с ранее закреплёнными `dev/inode`
исполняемого файла. Преждевременное завершение процесса,
недоступный `/proc`, скрипт вместо ELF или иной
исполняемый образ запрещают присваивать захвату статус
`capture_verified`. Новый формат приватной квитанции
`map02_private_native_process_receipt_v2` указывает
`native_elf_image_required=true` и
`native_elf_image_observed=true`; её повторный аудит
отклоняет неподтверждённое поле. Старые синтетические
квитанции v1 продолжают поддерживаться без изменения.

Интеграционный тест `test_map02_native_elf_process_image.py`
**действительно компилирует и запускает нативный ELF**,
который копирует только искусственные GPU/VRAM-данные и
DDA-фикстуру. Затем повторяет приватный аудит квитанции
и двухточечного FT4. Этот ELF **не является игрой** и
не удостоверяет происхождение нативных журналов от неё.
Даже совпадение ядром наблюдённого исполняемого образа
не доказывает, какие библиотеки, игровые ресурсы или
GPU-журналы фактически сформировал процесс.

Чтобы связанный частный захват обязательно прошёл именно
нативный ELF-режим, укажите `--require-native-elf-image` **также**
при вызове `tools.audit_map02_launch_two_word_binding`.
Без этого флага прежние синтетические квитанции v1 допустимы
для регрессионных тестов. С флагом они отклоняются ещё до
исходного FT4/VRAM-аудита, если квитанция запуска не
содержит проверенного наблюдения ELF-образа процесса.
В отчёте отдельно отображаются
`native_elf_image_required_for_join` и
`native_elf_process_image_observed`, без PID и приватных путей.

### Проверка окружения запуска

Закрепление исполняемого файла не гарантирует, что динамический
загрузчик или интерпретатор не подмешают другой программный код.
Поэтому `run_map02_private_native_capture.py` **до создания
preflight-квитанции** проверяет окружение дочернего процесса,
отклоняет нестроковые значения и ключи, а также настройки
`LD_*`, `DYLD_*`, `PYTHONPATH`, `PYTHONHOME`,
`PYTHONSTARTUP`, `PYTHONINSPECT`, `PYTHONBREAKPOINT`,
`BASH_ENV`, `ENV`, `GCONV_PATH`, `GLIBC_TUNABLES`.

Обычные переменные `DISPLAY`, `WAYLAND_DISPLAY`, `LANG`,
`XDG_RUNTIME_DIR` допускаются. Для запуска из рабочего окружения
с `LD_LIBRARY_PATH` следует настроить разрешение библиотек в
отдельном чистом Linux-окружении или использовать RPATH/установленные
системные зависимости; **автоматического разрешения опасных
переменных нет**. Результат не содержит их приватных значений.
Это ограниченный контроль способов подмешивания библиотек,
а не песочница или доказательство подлинности загруженных
динамических библиотек.

### Атомарная публикация квитанций запуска

`run_map02_private_native_capture.py` теперь записывает приватные
`preflight` и `process-receipt` через отдельные временные файлы
с правами `0600`. Сначала полностью сериализует JSON и вызывает
`fsync` для файла, затем создаёт окончательное имя с помощью
исключительной жёсткой ссылки (существующий файл или символьная
ссылка не заменяются), синхронизирует каталог, удаляет временное
имя и повторно синхронизирует каталог.

При сбое записи/синхронизации публикация откатывается:
частичный JSON не остаётся под окончательным именем,
а существующий чужой файл не удаляется. Файловая система
должна поддерживать жёсткие ссылки в пределах каталога и
`fsync` каталога; небезопасного режима обхода этих требований
нет. Тесты искусственно вызывают сбои посреди записи,
после связывания файлов и при гонке за окончательное имя.
Этот механизм гарантирует **структуру локальной публикации**
в рамках принятой модели ФС, но не удостоверяет подлинность
исходной игры или процесса-писателя GPU-журналов.

## Неподменённая проверка полного цепочного запуска

Отдельный тест
`tests/test_map02_launch_two_word_process_integration.py`
запускает **реальный локальный subprocess** с искусственным
исполняемым скриптом без игровых ресурсов. Скрипт помещает
**синтетические** нативные GPU-снимки и DDA-журнал в заранее
пустую приватную папку. Затем тест без имитации функций
`capture`, `replay_receipt`, `verify_multi_pixel_ot` или
`audit_launch_two_word` повторно проверяет исполняемый файл,
завершение процесса, исходные FT4/OT, BGR555/VRAM, глобальные
номера двух точек `PutPixel`, один и тот же GPU SHA-256 и
устойчивость файлового комплекта.

Отрицательные случаи проверяют повреждение снимка VRAM после
завершения программы, изменение исходной FT4-трассы и
процесс с кодом возврата ноль, который не создал ни одного
журнала. **Этот процесс намеренно синтетический и копирует
только созданные тестами данные**. Успех не подтверждает, что
оригинальный PC-порт исполнялся с настоящими ресурсами MAP02,
что был аутентифицирован процесс-писатель журнала или что
изображение построено на Nintendo Switch.

## Достоверность и пределы

Один согласованный журнал действительно позволяет **проверить
заявленную общую последовательность** наблюдений двух точек лучше,
чем сложение двух независимых запусков. Но совпадающие SHA и
внутренние счётчики **не доказывают фактическое происхождение
журнала** из одного исполнявшегося процесса. Отчёт неизменно
оставляет `native_capture_process_identity_authenticated=false`,
`complete_original_putpixel_stream_proven=false`,
`physical_ps1_pixel_equivalence_verified=false` и
`real_map02_gameplay_authenticated=false`.

Проверка оригинального нативного PC-кода и синтетические тесты
не означают, что реальная MAP02 запущена на Nintendo Switch,
и **не разрешают** включать HD-подмену. Оригинальные игровые
ресурсы остаются только в приватном владении пользователя.
