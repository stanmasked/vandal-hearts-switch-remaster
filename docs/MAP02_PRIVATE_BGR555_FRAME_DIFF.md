# MAP02 — локальное сравнение кадров BGR555 (PS1 ↔ PC)

Это инструмент измерения **различий двух необработанных экранных кадров**,
а не средство получения игры, кадров или подтверждения их происхождения.
В публичный GitHub не попадают изображения, ресурсы или пиксели.

## Подготовка данных

Понадобятся независимо полученные пользовательские кадры одного состояния
MAP02: `reference.bgr555` (заявленный PS1-ориентир) и
`candidate.bgr555` (заявленный PC-порт). Каждый файл содержит ровно
`width × height × 2` байт: 16-битные little-endian BGR555-пиксели
без BMP/PNG-заголовков, с битом STP на позиции 15. Перед сравнением
необходимо отдельно убедиться в единой видимой области, ориентации,
моменте захвата, палитре и разрешении. Инструмент **не делает**
масштабирование, выравнивание, цветокоррекцию или догадки о палитре.

В приватном каталоге создаётся `frames.json` вида:

```json
{
  "schema": "vh.map02.private-bgr555-frame-comparison.v1",
  "frame": 411,
  "width": 320,
  "height": 240,
  "pixel_format": "bgr555_le",
  "images": {
    "reference.bgr555": {
      "sha256": "СЮДА_64_СИМВОЛА_SHA256",
      "frame": 411,
      "origin": "ps1_reference_claimed"
    },
    "candidate.bgr555": {
      "sha256": "СЮДА_64_СИМВОЛА_SHA256",
      "frame": 411,
      "origin": "pc_port_candidate_claimed"
    }
  }
}
```

Фактические SHA-256 каждого файла можно вычислить локально командой
`sha256sum`. Числа в примере иллюстративны, не являются данными
реального захвата. Все три файла должны остаться **приватными**.

```sh
python3 -m tools.compare_map02_private_bgr555_frames /private/map02-frame-pair \
  > /private/map02-frame-differential-summary.json
```

Сводка содержит хеши входов и карты различий, число одинаковых и
отличающихся полных 16-битных пикселей, число изменённых строк
и блоков 16×16, количество несовпадений STP, сумму абсолютных
ошибок трёх 5-битных каналов и максимальную ошибку на пиксель.
Она **не содержит** цветов, координат отдельных пикселей,
локальных путей, сырых кадров или авторских игровых ресурсов.

## Что проверяется и что остаётся неизвестным

- Точная длина каждого BGR555-файла, отсутствие символьных ссылок,
  FIFO и повреждённых/меняющихся файлов.
- SHA-256 каждого файла, строго заданный формат и одинаковый номер
  кадра. Пропущенные и лишние поля, дубли JSON и ложные типы отклоняются.
- Различие STP-бита считается отдельно от ошибки цветовых каналов:
  пиксель, отличающийся только STP, всё равно считается несовпадающим.
- Хеш карты различий не раскрывает положения отдельных пикселей.
- Метки `ps1_reference_claimed` / `pc_port_candidate_claimed`
  являются **утверждениями оператора**, не аттестацией эмулятора или
  оригинальной PlayStation.
- Даже **ноль различий** не доказывает розничное происхождение кадров,
  полную аутентичность игры, временную согласованность VRAM или
  эквивалентность GPU PlayStation. Для такого утверждения нужны
  независимые свидетельства процесса, игровых ресурсов и захвата.

CI запускает только синтетические маленькие кадры, включая тесты
STP, ошибок каналов, подмены SHA-256, неверных размеров и путей.
Реальных PS1/PC кадров в CI нет. HD-подмена остаётся запрещённой.


## Привязка меток кадра к приватной проверке запущенного ELF

После получения обоих кадров и отдельного двухточечного
`DrawOTag`/FT4/VRAM-журнала можно запустить второй, более строгий
**локальный** аудитор. Он повторяет исходное BGR555-сравнение
**до и после** независимого `audit_map02_launch_two_word_binding.py`,
который перепроверяет приватную квитанцию запуска, статические
инструментальные символы, факт наблюдения Linux ELF в `/proc`,
записи GPU/DDA и два разных VRAM-слова.

```sh
python3 -m tools.bridge_map02_private_frame_native \
  --frame-pair /private/map02-frame-pair \
  --native-capture /private/native-gpu-logs \
  --source-capture /private/source-ft4-evidence \
  --launch-receipt /private/launch-receipt.json \
  --preflight-report /private/preflight.json \
  --executable /private/verified-pc-elf \
  --compiler gcc > /private/map02-frame-native-join.json
```

Требуется строгая проверка **обоих** признаков оригинального
зафиксированного процесса: `native_elf_image_observed` и
`native_probe_symbols_inspected`. Кадр в `frames.json` обязан
совпадать с `source_frame` и `native_gpu_frame` записи исходной
FT4/VRAM-сессии. Проверяются стабильность файлов кадров и JSON
на протяжении независимого повторного анализа, SHA-256
исходного журнала GPU, совпадение двух VRAM-слов и запрет HD.
В итоговом отчёте находятся лишь SHA-256 и агрегированные
счётчики; приватные файлы не публикуются.

**Критическая граница доверия:** совпадение номера кадра, SHA-256
и даже нулевые различия BGR555 **не связывают сами байты
скриншотов причинно с запущенным процессом**. Приватный
отладочный бинарник мог просто скопировать готовые файлы
(что показывают существующие синтетические тесты).
Поля `frame_bytes_causally_bound_to_executed_game`,
`retail_disc_resources_authenticated`,
`ps1_reference_capture_authenticated`,
`pc_port_frame_capture_authenticated`,
`ps1_hardware_pixel_equivalence_verified`
и `hd_replacement_authorized` всегда `false`.
Следующий реальный шаг — независимый доверенный канал захвата
обеих кадровых поверхностей из известных процессов, а не
повторение самосогласованного журнала.

## Создание приватной пары из проверенного кадра живого ELF

Чтобы избежать ручного копирования неподтверждённого PC-кадра,
можно использовать `tools.prepare_map02_private_frame_pair`.
Требуются отдельно полученный **сырой** BGR555 reference-файл
размером 1024×512×2 байта, ранее захваченный приватный
`process-frame.bgr555` с квитанцией, GPU-журнал того же запуска
и исходный SHA-проверенный Linux ELF.

```sh
mkdir -m 700 /private/map02-verified-pair
python3 -m tools.prepare_map02_private_frame_pair \
  --reference-bgr555 /private/original-claim/reference.bgr555 \
  --live-frame /private/live-elf-frame \
  --gpu-journal-dir /private/live-elf-gpu-journal \
  --executable /private/pinned-native-elf \
  --frame-pair-dir /private/map02-verified-pair \
  > /private/pair-generation-summary.json
```

Каталоги источников и результата должны быть раздельными,
закрытыми для других пользователей; эталонный файл — только
`0600`, без дополнительных жёстких ссылок. Каталог результата
должен существовать и быть **пустым**. Инструмент проверяет
изображение через два полных независимых повтора квитанции
запуска и GPU-журнала, затем записывает приватную тройку
`reference.bgr555`, `candidate.bgr555`, `frames.json`.
При несовпадении хешей, подмене файлов либо ошибке данные
новой тройки удаляются.

Вывод содержит только хеши и агрегированные показатели.
**Метка PS1-эталона остаётся утверждением пользователя:**
наличие настоящей игры, происхождение эталона от PlayStation,
точный момент игрового кадра и эквивалентность рендеринга
не удостоверяются. Пиксели и исходные ресурсы остаются локальными.
Тесты под GCC и Clang используют исключительно синтетический
Linux C11 ELF и искусственный эталон.

## Проверка повторяемости двух независимых запусков ELF

Для воспроизводимого кадра MAP02 одного полного повтора сохранённых
файлов недостаточно. Теперь можно отдельно выполнить **два независимых
локальных захвата** одного и того же SHA-проверенного Linux ELF,
обязательно с GPU-журналом для каждого запуска, а затем сравнить их:

```sh
python3 -m tools.audit_map02_private_frame_repeatability \
  --first-frame /private/capture-A/frame \
  --first-journal /private/capture-A/gpu \
  --second-frame /private/capture-B/frame \
  --second-journal /private/capture-B/gpu \
  --executable /private/pinned-native-elf \
  > /private/map02-native-two-run-report.json
```

Оба захвата должны относиться к одинаковому номеру кадра, одному
исполняемому файлу и содержать полный BGR555 VRAM размером 1024×512.
Четыре каталога должны быть раздельными и приватными. Каждый захват
дважды проверяется исходным независимым анализатором GPU-журнала,
затем сравниваются хеши терминальных кадров, полные 16-битные пиксели,
число отличающихся строк, STP-биты и хеши событий GPU.

Различие кадров является **результатом измерения**, а не автоматическим
подтверждением неисправности порта: возможны и реальные игровые
изменения состояния между двумя запусками. Отчёт всегда отдельно
сообщает, совпали ли кадры и журналы. Все файлы остаются локальными;
сводка не раскрывает цвета, координаты, пиксели или пути.

Важно: двойной захват подтверждает только воспроизводимость указанного
PC ELF в данных условиях; он не удостоверяет исходный образ PS1,
розничную версию игры и аппаратную эквивалентность PlayStation.
Новые синтетические тесты компилируются отдельно под GCC/Clang,
запускают C11-производитель дважды и проверяют как совпадение,
так и изменение одного слова VRAM при одинаковом ELF.

### Защита двух независимых захватов от подмены файлов

Аудитор повторяемости теперь фиксирует все четыре закрытых каталога
(кадр A, GPU-журнал A, кадр B, GPU-журнал B) **до первого воспроизведения**.
По каждому файлу он запоминает внутри процесса inode, устройство,
владельца, права, число ссылок, размер и метаданные времени.
После каждого повторного аудита и перед выдачей отчёта эти идентификаторы
сверяются снова, включая все промежуточные снимки GPU, а не только
конечный кадр. Это позволяет обнаружить подмену идентичными байтами,
которую обычный SHA-256 не отличает от исходного файла.

Новые синтетические тесты проверяют замены как конечного BGR555,
так и JSONL-журнала событий GPU. Ни идентификаторы файлов, ни
оригинальные изображения в итоговом отчёте не выводятся.

### Журнал команд и конечная видеопамять — разные результаты

При повторном запуске записи `gpu-native-events.jsonl` могут быть
побайтно одинаковыми, даже когда конечные BGR555-кадры отличаются:
JSONL фиксирует последовательность и атрибуты операций, а сами
снимки VRAM хранятся отдельно. Поэтому отчёт не делает вывод о
тождестве пикселей из совпадения хеша журнала. Отдельно публикуются
флаги `repeated_gpu_event_journal_identical`,
`repeated_gpu_final_vram_identical` и
`repeated_native_frame_pixels_identical`.
Синтетический тест изменяет одно VRAM-слово при одинаковом ELF и
одинаковом JSONL-журнале; различие фиксируется по исходным
пиксельным данным, а не по метаданным команды.

### Сопоставление всех промежуточных снимков VRAM

Повторяемость нельзя оценивать только по последнему экранному
кадру: промежуточная видеопамять может различаться после одной
операции DrawOTag и вновь совпадать к завершению кадра. Новый
аудитор сравнивает по отдельности все подтверждённые сохранённые
`gpu-XXXX-vram.bin` до и после каждой пары GPU-операций из
обоих приватных захватов. Проверка использует те же закрытые
дескрипторы каталогов и сверяет их полный inode-инвентарь
между чтениями.

В отчёте появились количество снимков каждой сессии, число
сопоставленных, число несовпадающих снимков в общей части,
количество оставшихся без пары и порядковый индекс первого
несовпадения. **Это индекс события, а не координата пикселя.**
Сами кадры, их цвета и пиксельные координаты не публикуются.
При различных количествах GPU-операций результат отражает
несопоставленные снимки, не выдавая ложного заявления о полном
побайтовом совпадении.

Синтетические тесты доказывают два разных случая: (1) изменённый
конечный кадр при одинаковом JSONL-журнале, (2) изменённый
начальный снимок VRAM при одинаковом конечном кадре и
одинаковом журнале. Оба запуска используют один и тот же
SHA-256 исполняемого ELF, а изменение задаётся только его
тестовым аргументом.

## Запуск двух независимых захватов одной командой

Для повторяемости MAP02 больше не требуется вручную запускать два
захвата и затем отдельно вызывать аудитор. Создайте **четыре разных
пустых каталога с правами 0700** и укажите SHA-256 доверенного
локального Linux ELF. Два запуска используют один номер кадра,
одинаковый исполняемый файл и **те же самые аргументы**:

```sh
mkdir -m 700 /private/map02-A-frame /private/map02-A-gpu \
             /private/map02-B-frame /private/map02-B-gpu

python3 -m tools.run_map02_private_two_live_captures \
  --executable /private/native-map02-elf \
  --executable-sha256 SHA256_ИЗ_64_СТРОЧНЫХ_HEX_СИМВОЛОВ \
  --first-frame /private/map02-A-frame \
  --first-journal /private/map02-A-gpu \
  --second-frame /private/map02-B-frame \
  --second-journal /private/map02-B-gpu \
  --frame 123 \
  > /private/map02-two-live-runs-report.json
```

Если нужны аргументы ELF, используйте одинаковые повторяемые
`--elf-arg` для обоих запусков. Инструмент отказывается работать
с непустыми, общедоступными или совпадающими физическими каталогами
**до первого запуска**. После каждого захвата фиксирует идентичности
реально опубликованных файлов при ещё открытых дескрипторах
каталогов, а затем проверяет эти же файлы перед/после независимого
аудита. Каждый захват проверяет полный журнал GPU и снимки VRAM.
Приватные BGR555 и оригинальные ресурсы в GitHub не публикуются.

При ошибке **отчёт об успешном сравнении не выдаётся**. Уже
созданные приватные файлы оставляются локально для диагностики;
повторный запуск следует делать в новых пустых каталогах.
Сопоставление двух кадров подтверждает только воспроизводимость
предоставленного ELF при указанном аргументном окружении и не
доказывает запуск розничной игры или соответствие PlayStation.

## Диагностика первого несовпадения VRAM

Аудитор двух независимых запусков теперь указывает, на какой **GPU-паре**
и в какой фазе («before»/«after») впервые отличается видеопамять.
Для первого такого снимка он подсчитывает только число различающихся
полных BGR555-пикселей, затронутых строк и STP-битов. Дополнительно
считает, сколько снимков разошлось до операций и сколько после них.

Эти агрегаты полезны для определения момента расхождения
DrawOTag/FT4 без публикации координат, цветов, кадров, путей или
внутренних inode. Если общая часть снимков идентична, все показатели
первого расхождения равны `null`, даже при разном количестве
снимков; число неимеющих пары файлов отражается отдельно.

Проверяется три синтетических случая при неизменном SHA-256 ELF:
различие только конечной VRAM (after), временное различие перед
операцией (before), а также расхождение только STP-бита в
промежуточной VRAM при совпавшем конечном кадре.

## Восстановление совпадения VRAM между GPU-операциями

Теперь сравнение двух запусков дополнительно отслеживает
**временную динамику расхождений** в проверенной общей части
промежуточных GPU-снимков: последний отличавшийся снимок,
первый снимок, на котором совпадение восстановилось,
количество переходов «совпадает ↔ отличается» и факт
повторного расхождения после восстановления.

Поле `gpu_vram_reconverged_at_common_prefix_end` указывает,
что после одного или нескольких отличий **последний сопоставленный
снимок** совпал. Оно не означает, что весь захват воспроизводим:
если одной сессии не хватает соответствующих снимков, это
отдельно отмечается счётчиком `unmatched_gpu_vram_snapshots`.
Если различий вообще не было, восстановление совпадения
не заявляется, а индексы остаются `null`.

Проверки используют как реальные синтетические Linux C11 запуски,
так и локальные последовательности из четырёх GPU-снимков
(разошлись → совпали → разошлись → совпали). Отчёт не
содержит карт изображений, значений отдельных пикселей
или их координат.

## Строгий режим воспроизводимости GPU/VRAM

По умолчанию два независимых запуска ELF исследуются как **диагностика**:
оба захвата могут быть полностью проверены, даже если промежуточная
VRAM или конечные кадры различаются. Это не является подтверждением
побайтовой воспроизводимости.

Для локального приёмочного теста можно добавить
`--require-identical-gpu-timeline` к команде
`tools.run_map02_private_two_live_captures`. Тогда инструмент
**отказывается выдавать успешный отчёт**, если отличаются
хотя бы один проверенный GPU VRAM-снимок, число снимков,
конечные 16-битные BGR555-пиксели или JSONL-журнал GPU-событий.
Нельзя обойти эту проверку, показав совпадение только конечного
кадра: промежуточные отличия также считаются отказом.

Успешный строгий отчёт содержит
`strict_gpu_timeline_match_required=true` и
`strict_gpu_timeline_match_verified=true`. В обычном
диагностическом режиме оба поля `false`, даже если
кадры совпали случайно. При неуспехе приватные файлы
остаются локально для анализа и никакой успешной сводки
не выдаётся.

Синтетические C11-тесты проверяют строгий проход, отказ при
различном конечном GPU VRAM-слове и одинаковом GPU JSONL,
сохранение диагностического режима, проверку структуры
свидетельств и вызов через CLI. Строгий режим **не удостоверяет**
происхождение эталонных кадров от PlayStation или реальное
исполнение розничных игровых ресурсов.

## Непрерывная идентичность ELF между двумя захватами

Помимо криптографической проверки SHA-256 исполняемого кода при
каждом запуске, однокомандный двойной захват теперь удерживает
открытый файловый дескриптор **одного ELF** с момента проверки
четырёх приватных каталогов до полного завершения аудита GPU/VRAM.

Перед первым запуском, после каждого запуска и после анализа
всех промежуточных VRAM-снимков повторно проверяются SHA-256,
inode, устройство, размер, права, владелец и времена изменения
файла. Таким образом, замена ELF другим inode с **идентичными
байтами** между захватами больше не может быть ошибочно принята
за непрерывную идентичность исходного файла. Прямые символьные
ссылки на исполняемый файл запрещены.

Успешный локальный отчёт содержит
`same_executable_inode_and_sha_pinned_through_both_launches=true`.
Это дополнительное подтверждение целостности *пользовательского
Linux ELF*, а не удостоверение происхождения игры от розничного
образа PS1 или достоверности её экранных кадров.

Три новых синтетических регрессионных теста проверяют подмену ELF
новым inode с теми же байтами после первого захвата, изменение
времени модификации и символьную ссылку. Каждый отказ происходит
без успешной сводки, а второй процесс не запускается при
обнаруженной подмене перед ним.

## Хеш полной упорядоченной последовательности GPU VRAM

Для дальнейших локальных воспроизведений MAP02 аудитор теперь
вычисляет два независимых SHA-256 **всех снимков видеопамяти в
точном порядке их появления**, включая хвостовые снимки, если
два запуска содержат разное число GPU-операций. Хеш включает
версию формата, число снимков, индекс каждого снимка и все его
BGR555-байты. Это не тот же хеш, что SHA-256 текстового
GPU JSONL: два идентичных журнала операций могут сопровождаться
разной видеопамятью.

Итоговая сводка содержит
`first_gpu_vram_timeline_sha256`,
`second_gpu_vram_timeline_sha256` и
`gpu_vram_timeline_commitments_identical`.
Сами промежуточные изображения, индивидуальные цвета и
координаты пикселей не раскрываются. Контроль inode, прав
доступа и полной независимой проверки каждого захвата
по-прежнему обязателен; хеши не заменяют этот контроль.

В опциональном строгом режиме совпадение хешей всей
VRAM-последовательности также обязательно наряду с
попиксельным сравнением, совпадением количества снимков
и GPU-журнала. Необычный случай «конечные кадры совпали, но
промежуточная VRAM отличалась» будет виден как различие
двух хешей, даже если обе сессии имели один исполняемый ELF.
Эти хеши доказывают только согласованность приватных PC-захватов,
а не их происхождение от настоящей PlayStation.

## Первый отличающийся GPU-событийный журнал

Хеш JSONL-журнала GPU позволяет обнаружить расхождение записей,
но не указывает, **на каком событии** оно возникло. Поэтому аудитор
теперь выполняет дополнительное локальное, побайтовое сравнение
строк двух журналов после строгой независимой проверки каждого
захвата. Чтение происходит через уже закреплённые дескрипторы
приватных каталогов, с повторной проверкой inode, владельца,
прав доступа, SHA-256 и допустимого размера файла.

В сводке отображаются число событий каждого запуска,
число сопоставленных, число различных записей, число записей
без соответствия и **порядковый номер первого различия**
вместе с индексом GPU-пары и фазой before/after. Текст JSONL,
FT4-координаты, цвета, отдельные приватные операции и
исходные данные никогда не переносятся в отчёт.

При разном числе GPU-событий общая часть анализируется
отдельно, а лишние записи не скрываются. Строгий режим
приёмки требует побайтовой идентичности всех записей GPU
наряду с совпадением SHA-256 журналов, кадров и полной
истории видеопамяти. Результат подтверждает согласованность
двух локальных PC-запусков, но не аутентичность PS1.

## Совместная локализация первого расхождения GPU/VRAM

Синхронизированные JSONL-события и промежуточные BGR555-снимки
проверенного приватного захвата теперь сопоставляются **по одному
порядковому индексу** (две фазы `before`/`after` на GPU-пару).
Новый агрегированный отчёт содержит
`first_joint_gpu_divergence_index`,
`first_joint_gpu_divergence_pair_index`,
`first_joint_gpu_divergence_phase` и
`first_joint_gpu_divergence_kind`.

Последнее поле принимает `event-only`, `vram-only`,
`event-and-vram`, `unmatched-tail` либо `null`, если обе
полные последовательности идентичны. При различной длине журналов
несопоставленный хвост считается отдельным видом расхождения,
даже если все записи общей части совпадают. Если ранее в
общей части уже возникло расхождение, оно имеет приоритет
перед хвостом. Несогласованное количество событий и VRAM-снимков
между источниками приводит к отказу аудита.

Классификация опирается только на уже проверенные локальные
GPU-журналы и снимки VRAM: ни значения JSONL, ни координаты,
ни цвета, ни пиксели, ни приватные пути не публикуются.
Она не доказывает причинность: `event-only` означает лишь,
что первое *наблюдаемое* расхождение раньше появилось в журнале
событий, а не обязательно что оно вызвало следующее изменение VRAM.
Строгий режим по-прежнему требует полного побайтового совпадения
обеих последовательностей и кадров, а не только совпадения
первого индекса.

### Строгая приёмка совместной GPU/VRAM-диагностики

Помимо прежнего побайтового равенства GPU JSONL, всех снимков VRAM,
последнего BGR555-кадра и двух хешей истории видеопамяти, строгий режим
`--require-identical-gpu-timeline` теперь требует согласованного
количества событий и VRAM-снимков в каждом независимом захвате.
Все четыре поля `first_joint_gpu_divergence_*` должны **присутствовать**
и принимать `null`: отсутствие нового поля нельзя трактовать как
доказательство отсутствия расхождения.

В синтетических проверках два реальных Linux C11-процесса могут
выдать разные, но по отдельности корректные GPU-события при равной
видеопамяти, или разные GPU-события и промежуточную VRAM при
совпавшем конечном кадре. Оба случая должны вызывать отказ строгого
режима, даже если конечное изображение совпадает. Отдельные негативные
тесты моделируют отсутствующую диагностику, несогласованные
числа записей и подмену `null` индексом расхождения.

Эти проверки подтверждают внутреннюю непротиворечивость **синтетических
PC-захватов**, но не удостоверяют исходную игру PlayStation, реальные
GPU-пакеты MAP02, аппаратную эквивалентность или возможность HD-подмены.

### Двухпроцессная проверка отказа строгого режима

К проверкам отдельного аудитора добавлен сквозной синтетический тест
`tools.run_map02_private_two_live_captures.run`: два независимых
Linux C11-процесса с одним и тем же SHA-256 исполняемого ELF
публикуют собственные приватные GPU/VRAM-свидетельства. Только тестовый
драйвер изменяет аргумент **второго** запуска, чтобы искусственно
создать расхождение. В обычном рабочем режиме команда по-прежнему
передаёт обоим запускам одинаковые аргументы.

Проверяются две ситуации:

- `event-only`: записи GPU JSONL различаются, но каждый промежуточный
  снимок VRAM и конечный BGR555-кадр совпадают.
- `event-and-vram`: GPU-событие и промежуточная VRAM различаются с
  самого первого индекса, затем видеопамять сходится к одинаковому
  конечному кадру.

Диагностический режим должен сообщить классификацию и не утверждать
успешную строгую приёмку. Режим `--require-identical-gpu-timeline`
обязан завершиться отказом **после двух реальных синтетических запусков
и полной проверки опубликованных свидетельств**, без успешной сводки.
Оба варианта дополнительно проверяются без публикации приватных путей
и байтов игровых ресурсов. Это тест контракта локального PC-аудитора,
не доказательство совпадения с аппаратной PlayStation.

### Позднее расхождение во второй GPU-паре

Сквозные тесты теперь могут запустить один и тот же синтетический
Linux C11 ELF с **двумя последовательными DrawOTag-парами**
(четыре GPU-события `before/after` и четыре приватных снимка VRAM).
Между первой парой и второй проверяется непрерывность видеопамяти,
а конечный BGR555-кадр по-прежнему подтверждается собственным
последним GPU-снимком.

Новые сценарии разделяют:

- совпадение всех четырёх событий и снимков в строгом режиме;
- различие только GPU-метаданных на индексе 2 (вторая пара, `before`);
- различие только VRAM на индексе 3 (вторая пара, `after`);
- сначала различие GPU-метаданных на индексе 2, затем VRAM на индексе 3;
- отказ строгой приёмки во всех трёх несовпадающих сценариях.

Отдельный тестовый драйвер изменяет только аргумент второго запуска.
Оригинальные ресурсы PlayStation, FT4-пакеты и приватные BGR555-байты
не попадают в CI или публичную сводку. Это регрессии синтетической
двухпроцессной инфраструктуры: подтверждение реального оригинального
MAP02 и аппаратного соответствия PS1 по-прежнему требуется отдельно.

### Несопоставленный хвост GPU-пар

Добавлена сквозная синтетическая проверка двух независимых Linux ELF-запусков,
в которой один процесс сохраняет одну GPU-пару, а другой — две.
Оба направления (короткий первый или короткий второй захват) тестируются
отдельно. Общие начальные события JSONL и снимки VRAM в этих сценариях
побайтово совпадают; совпадает и итоговый BGR555-кадр.

Аудитор всё равно обязан указать `unmatched-tail` как первое расхождение
в позиции 2 (вторая GPU-пара, фаза `before`), показать по две
несопоставленные записи GPU и VRAM и **не** подтверждать строгое
равенство. Тот же сценарий с `--require-identical-gpu-timeline`
должен отвергаться в обоих направлениях после независимой проверки
первичного опубликованного свидетельства.

Такой тест защищает от ложной приёмки укороченных или дополненных
журналов. Он опирается на синтетические данные: реальный захват
оригинального MAP02 и графическая эквивалентность PS1 всё ещё не
подтверждены; HD-подмена остаётся выключенной.

### Проверка непротиворечивости первого GPU/VRAM-расхождения

Перед построением объединённого диагноза аудитор теперь отдельно
проверяет числовые свойства подтверждённых последовательностей:
количества GPU-событий и VRAM-снимков обязаны быть целыми (не
логическими `true/false`), чётными и укладываться в лимит
`MAX_RECORDS`. Пустые и нечётные полные последовательности,
отрицательные или нечётные несопоставленные хвосты, а также
несогласованные общие префиксы отклоняются.

Кроме того, каждое ненулевое число разных GPU-событий либо снимков
VRAM должно сопровождаться индексом **первого** отличия в общей части.
И наоборот: если отличий не было, такой индекс должен быть `null`.
Противоречия — включая подмену счётчика булевым значением — приводят
к ошибке вместо ложного результата `first_joint_gpu_divergence_kind=null`.

Новые отрицательные регрессии моделируют повреждённые агрегаты,
не раскрывая исходные журналы, координаты или пиксели. Эти проверки
защищают контракт диагностического инструмента от последующих
ошибок рефакторинга. Они **не** подтверждают оригинальный PS1 MAP02
или пригодность HD-рендеринга к включению.

### Связь первого расхождения с порядком GPU-событий

Объединённый аудитор дополнительно подтверждает, что индекс первого
несовпадения согласуется с его GPU-парой (`index // 2`) и фазой
(`before` для чётного индекса, `after` для нечётного).
Проверка применяется раздельно к журналам GPU-событий и снимкам VRAM.
Все четыре позиционных поля должны присутствовать; отсутствующая
или противоречивая метаинформация вызывает отказ.

Число отличающихся записей общего префикса не может превосходить число
оставшихся позиций, начиная с индекса первого отличия. Например, если
в последовательности из четырёх событий первое различие обнаружено
только на индексе 3, допустимо ровно одно отличающееся событие,
но не два. Нарушение обнаруживается как повреждённое агрегированное
свидетельство, без чтения и публикации значений игровых пикселей
или JSONL-содержимого в отчёте.

Это защита математической согласованности локального приватного
аудита, а не подтверждение реального захвата оригинальной игры
или графической эквивалентности PlayStation.

### Исчерпывающая синтетическая проверка классификатора расхождений

Для объединённого классификатора добавлен независимый
пошаговый эталонный алгоритм. Он перебирает все комбинации различий
между двумя журналами длиной от одной до трёх GPU-пар: от двух
до шести событий `before/after` и столько же снимков VRAM.
Всего анализируются **4944** сочетания длины последовательностей,
маски несовпадающих GPU-событий и маски несовпадающих VRAM-снимков.

Эталон проходит события по порядку, отдельно определяя
`event-only`, `vram-only`, `event-and-vram` и
`unmatched-tail`; проверяются индекс первого отличия,
номер пары и фаза `before/after`. Эти 4944 проверки
используют лишь локально созданные целочисленные агрегаты,
а не оригинальные игровые кадры, GPU-журналы или содержимое VRAM.

Цель теста — выявлять ошибки логики классификации, которые могут
остаться незамеченными при нескольких вручную подобранных примерах.
Он не доказывает корректность самого источника данных, совпадение
с графическим процессором PlayStation или готовность HD-подмены.

### Проверка симметрии независимого сравнения двух захватов

Добавлен сквозной тест, который создаёт **два настоящих независимых
синтетических C11-захвата** из одного подтверждённого ELF, затем
дважды выполняет полный приватный GPU/VRAM-аудит: сначала A→B,
после этого B→A. Оба прохода повторно проверяют исходные опубликованные
свидетельства, включая пары `before/after` и конечный BGR555-кадр.

Проверяется неизменность количества отличающихся пикселей,
линий и STP-битов, а также индекса, фазы, GPU-пары и вида первого
расхождения. Хеши исходных кадров, GPU JSONL и упорядоченных
последовательностей VRAM обязаны **обменяться местами** вместе
с обозначениями источников.

Покрываются четыре сценария: `event-only`, `vram-only`
в фазах `before` и `after`, а также `event-and-vram`.
Публичные ответы обоих направлений не должны раскрывать абсолютные
пути к приватным файлам; признак разрешения HD-подмены всегда
остаётся `false`.

Симметрия свидетельствует о согласованности локального аудитора, но
не о совпадении исходной игры с оригинальным GPU PlayStation.

### Симметрия несопоставленного хвоста GPU-журнала

Дополнительно проверяется особый случай неодинаковой длины двух
полностью повторно проверенных синтетических C11-захватов:
в одном записана одна пара DrawOTag, в другом — две. Аудитор
сравнивает **одни и те же** опубликованные данные сначала A→B,
затем B→A. Выполняются оба варианта: длиннее первый либо второй захват.

Независимо от порядка сохраняются `unmatched-tail`, индекс
первого отличия 2, номер пары 1, фаза `before`, количество
несопоставленных событий и VRAM-снимков, идентичность общего
префикса и итогового BGR555-кадра. Количество подтверждённых
GPU-пар, длины журналов и все хеши, относящиеся к отдельным
источникам, обязаны поменяться местами.

Повторное направление аудита также проверяется строгим режимом,
который не должен принимать дополнительную GPU-пару за
битовое совпадение. Результаты обоих направлений не раскрывают
приватные пути; это синтетическая защита локальной диагностики,
а не проверка настоящих PS1-ресурсов или разрешение HD-подмены.

### Фиксация аргументов двух независимых ELF-запусков

Оркестратор `run_map02_private_two_live_captures` принимает список или
кортеж аргументов запуска, проверяет их типы, а затем **один раз
копирует значения в неизменяемый кортеж до первого запуска**.
Это закрывает ситуацию, при которой вызывающий код изменяет
исходный список аргументов во время захвата: один и тот же
SHA-256 исполняемого ELF сам по себе ещё не гарантирует
одинаковые входные параметры двух процессов.

Отдельный сквозной тест использует два настоящих синтетических
C11 ELF-запуска и меняет исходный список аргументов после
завершения первого процесса на вариант, изменяющий VRAM.
Аудитор должен передать обоим процессам **первоначальные**
аргументы, получить четыре одинаковых GPU-события, четыре
одинаковых VRAM-снимка и подтвердить строгий режим.
Тест не утверждает, что любой внешний механизм изменения
процесса исключён: это защита именно от случайной или
конкурентной мутации аргументов вызывающей стороны.

Все захваты остаются приватными, а разрешение HD-подмены —
`false`; проверка не удостоверяет происхождение оригинального
MAP02 или соответствие PlayStation.

### Проверка согласованности VRAM-сводки

После полного независимого повторного воспроизведения обоих захватов
аудитор теперь дополнительно проверяет **внутреннюю непротиворечивость
самой агрегированной сводки VRAM**, прежде чем объединять её с
GPU-событиями:

- Сумма несовпадений для фаз `before` и `after` обязана совпадать
  с общим числом различающихся снимков; фазовые счётчики ограничены
  числом реально сравнимых GPU-пар.
- Индексы первого/последнего отличия и первого восстановления должны
  находиться в допустимой хронологии. Признаки повторного расхождения
  после восстановления и совпадения в конце общей части сверяются
  с этими индексами.
- Упорядоченные SHA-256 двух последовательностей должны согласовываться
  с флагом равенства хешей и с заявлением о полном совпадении всех
  снимков. Проверяются также границы количества изменённых пикселей,
  строк и STP-битов при первом отличии.
- Испорченные агрегаты приводят к отказу проверки, а не к
  публикации противоречивого отчёта.

Отрицательные тесты подменяют только **синтетические агрегаты**.
Дополнительный тест проверяет, что полный приватный аудитор
отказывается продолжать при искажении фазового счётчика на выходе
сравнения VRAM. Проверка не публикует сырые журналы, координаты
или пиксели и не устанавливает аппаратную эквивалентность PS1.

### Хронология переходов VRAM и реальное восстановление совпадения

В сводке независимого GPU/VRAM-аудита число переходов между состояниями
«совпадает» и «различается» должно согласовываться с **первым и
последним** снимками общего префикса. Теперь контролируются чётность
числа переходов, необходимые границы различных интервалов и факт
первого реального восстановления.

Например, последовательность `разное → одинаковое → разное →
одинаковое` требует ровно трёх переходов и восстановление на
индексе 1; отчёт с одним или двумя переходами не может честно
утверждать, что расхождение появилось повторно. Если в конце
снимки уже совпадают, а различия были раньше, индекс восстановления
не может отсутствовать. Если расхождение не возникало повторно,
первое восстановление должно следовать непосредственно за
последним отличающимся снимком.

Независимый синтетический тест перебирает **все 16 булевых историй**
четырёх `before/after`-снимков (две GPU-пары) и сверяет фазовую
историю с отдельным эталонным подсчётом переходов.
Отрицательные тесты проверяют фальшивое число переходов и
отсутствующее восстановление. Все данные в CI созданы искусственно:
оригинальные VRAM, GPU-пакеты и кадры PlayStation не публикуются.

### Согласование SHA-256 всей VRAM-последовательности с побайтовым сравнением

В независимом локальном аудиторе добавлена ещё одна проверка:
**два одинаковых по длине и побайтово совпадающих набора VRAM-снимков
обязаны иметь одинаковые SHA-256 упорядоченной последовательности**.
И наоборот, если отличается хотя бы один снимок либо один захват
содержит дополнительные пары `before/after`, итоговые
хеши последовательностей не должны совпадать (за исключением
теоретически возможной коллизии SHA-256).

Проверка отдельно сверяет полное количество снимков двух процессов,
длину общего префикса и число несопоставленных записей. Недостаточно
согласовать между собой только две логические метки
`gpu_vram_timeline_commitments_identical` и
`repeated_full_gpu_vram_snapshot_sequence_identical`: теперь
они обязаны согласовываться и с реальным результатом побайтового
сравнения.

Отрицательные регрессии моделируют оба обмана: подмену сводки
на «разные хеши» при полностью равных снимках и объявление
«равных хешей» после кратковременного отличия VRAM, которое
исчезает до последнего BGR555-кадра. Все GPU/VRAM-байты остаются
приватными, а в публичном CI используются только синтетические
C11-захваты. Подлинность исходного MAP02 и эквивалентность
графики PlayStation этим тестом не устанавливаются.

### Связь конечного BGR555-кадра с последним снимком GPU

Добавлена отдельная проверка связи двух независимо измеренных
результатов: итогового BGR555-кадра дочернего ELF и последнего
снимка GPU `after` в журнале VRAM. Когда два захвата содержат
**одинаковое число подтверждённых GPU-пар**, их последние
`after`-снимки относятся к одному порядковому событию. Поэтому
факт несовпадения терминальных кадров обязан совпадать с фактом
несовпадения этих последних GPU-снимков.

Дополнительно проверяются допустимые счётчики изменённых пикселей,
строк и STP-битов, а также согласованность SHA-256 конечных кадров
с вычисленным числом отличающихся пикселей. В сквозных
синтетических C11-тестах используются полностью одинаковые захваты,
кратковременное отличие `before` с последующим совпадением и
различие последнего `after`-снимка. Ложный терминальный счётчик
должен отклоняться как в отдельном валидаторе, так и при полном
независимом повторном аудите.

**Важная граница:** если количество GPU-пар отличается, конец
общего префикса не является концом обоих журналов. В этом случае
нельзя объявлять два последних кадра эквивалентными только по
последнему *общему* снимку; строгая проверка полного совпадения
GPU-последовательностей уже отклоняет несопоставленный хвост.
Никакой вывод о подлинности оригинального MAP02 или точности
графического процессора PlayStation из этих проверок не следует.

### Дополнительная GPU-пара меняет конечный BGR555-кадр

Добавлен сквозной синтетический тест сценария, в котором первый
подтверждённый `DrawOTag` одинаков в двух независимых C11-запусках,
но только один процесс выполняет **дополнительную GPU-пару**,
изменяющую один пиксель итогового BGR555-кадра.

Отдельный тестовый аргумент `two-pair-extra-terminal` активирует
в уже скомпилированном и SHA-подтверждённом ELF вторую пару
`before/after`. Начальные два GPU-события и оба VRAM-снимка
полностью совпадают с более коротким захватом. Затем длинный
захват меняет один пиксель и сохраняет новое состояние как
`gpu-0003-vram.bin`; терминальный кадр соответствует последнему
снимку **его собственной** последовательности.

Для обоих направлений A→B и B→A тест требует одновременно:
несопоставленный хвост из двух GPU-событий и двух VRAM-снимков,
первое расхождение `unmatched-tail` в индексе 2 (GPU-пара 1,
фаза `before`), нулевые различия общей части, **один**
отличающийся пиксель итоговых кадров и отказ строгого режима.
Проверяется перестановка маркированных SHA-256 и числа GPU-пар
при обмене ролями источников.

Этот случай подтверждает важное различие: **совпадение конца
общего префикса не гарантирует совпадения конечных кадров**,
когда длина журналов различна. Исполняемый файл и все данные
теста синтетические, оригинальные игровые ресурсы не публикуются.
Графическая эквивалентность PS1 не подтверждается и HD-подмена
не разрешается.

### Строгий запуск с лишней GPU-парой и изменённым кадром

Предыдущий сценарий сравнивал диагностические отчёты и проверял
`_require_bit_exact_gpu_timeline` непосредственно. Добавлен
сквозной отрицательный тест **реального строгого оркестратора**
`run_map02_private_two_live_captures.run(...,
require_identical_gpu_timeline=True)`.

Оба независимых синтетических ELF-запуска создают свои приватные
BGR555-кадры и GPU-журналы, которые затем полностью перепроверяются.
В одном из процессов дополнительная GPU-пара меняет один пиксель
терминального кадра. После построения диагностического свидетельства
строгий оркестратор обязан завершиться ошибкой `not bit-exact`;
допустима только локальная диагностика, но **не** успешная квитанция
строгого совпадения.

Тест повторяет оба порядка источников и удостоверяется, что
неудачная строгая проверка не приводит к публикации приватных
путей и не меняет `hd_replacement_authorized=false`. Созданные
локальные файлы сохраняются только для приватного разбора причины
отказа. Эти синтетические испытания не заменяют подлинный захват
MAP02 с оригинальной PlayStation.

### Защита подлинной файловой идентичности GPU-свидетельств

При двух независимых приватных захватах недостаточно, чтобы файлы
совпадали по SHA-256. После первого запуска и до завершения второго
другой процесс способен заменить файл побитово идентичной копией:
содержимое не изменится, но его **inode** уже будет другим.
Аудитор должен отвергать такую замену, иначе исходное
опубликованное свидетельство не останется неизменным.

Новый интеграционный тест создаёт два реальных синтетических C11
захвата и после завершения второго заменяет в первом захвате
**один** из трёх файлов: `gpu-native-events.jsonl`,
`gpu-0000-vram.bin` или `gpu-0001-vram.bin`.
Для каждого варианта замещающий файл содержит точно те же байты
и имеет приватный режим `0600`. Полный строгий оркестратор
обязан прекратить работу с ошибкой изменения опубликованных
файлов, до выдачи успешной квитанции.

Эта проверка подтверждает стабильность inode в границах
локального Linux-аудита. Она не устанавливает происхождение
оригинальных GPU-команд PlayStation, не публикует игровые
ресурсы и не включает HD-подмену.

### Повторная проверка свидетельств перед строгим подтверждением

Строгий оркестратор теперь **независимо повторно проверяет**
согласованность всего GPU/VRAM-отчёта непосредственно перед выдачей
признака `strict_gpu_timeline_match_verified=true`. Это отдельная
граница принятия решения после полного приватного аудита:
даже если кто-то изменил только агрегированные поля после проверки
побайтовых данных, прежних логических флагов «равно» недостаточно.

Заново проверяются количество и фазы промежуточных отличий VRAM,
хронология восстановления совпадения, SHA-256 и счётчики терминального
BGR555, а также положение первого расхождения GPU-событий.
Противоречия приводят к отказу `not bit-exact`, а не к
положительной строгой квитанции.

Негативные тесты изменяют **только поля итогового синтетического
отчёта**, сохраняя исходные C11-захваты битово одинаковыми:
несуществующие различия `before/after`, фиктивное восстановление,
ложные GPU-ординалы, STP и SHA-256. Отдельный сквозной тест
имитирует искажение фазового счётчика именно **между** полным
повторным аудитом и выдачей строгого результата. Оригинальные
PS1-данные остаются приватными, совпадение с PlayStation этим
не удостоверяется и HD-подмена не разрешается.

### Сопоставление исходных SHA-256 журналов и количества DrawOTag-пар в строгом режиме

Независимый аудитор повторно воспроизводит два локальных C11-захвата,
читает их приватные журналы и строит сводку о равенстве GPU-событий.
В режиме `require_identical_gpu_timeline=True` добавлена ещё одна
защита непосредственно **перед выдачей положительной строгой
квитанции**: SHA-256 полных журналов обоих захватов должны быть
корректными строчными 64-символьными hex-значениями и совпадать.
Число подтверждённых `DrawOTag`-пар каждого запуска также обязано
давать ровно удвоенное число GPU-событий соответствующего журнала.

Это закрывает случай изменения уже рассчитанного агрегированного
отчёта после независимой проверки: простые поля
`repeated_gpu_event_journal_identical=true` и
`repeated_gpu_event_records_identical=true` не должны скрывать
противоречивый SHA-256 либо неподтверждённое количество пар.
Строгий режим выдаёт `not bit-exact` вместо успешной квитанции.

Негативные тесты изменяют только метки SHA-256 и счётчики пар
в результате настоящих синтетических C11-запусков. Отдельная
интеграционная проверка подменяет вторую SHA-256-метку именно
между полным приватным аудитом и завершающим строгим решением.
Это проверка согласованности локальных свидетельств, **не**
независимое подтверждение подлинности оригинальных данных MAP02;
сырые игровые ресурсы не публикуются и HD-подмена не включается.

### Сверка итогового отчёта с квитанциями двух настоящих запусков

Оркестратор двух независимых приватных ELF-запусков теперь сохраняет
**неизменяемые значения из каждой квитанции публикации** ещё до
начала независимого повторного аудита: SHA-256 терминального
BGR555-кадра, SHA-256 полного GPU-журнала и количество
подтверждённых `DrawOTag`-пар. После двух повторных проверок
всех файлов аудитор обязан вернуть **ровно те же метки для каждого
источника по отдельности**, независимо от того, включён ли строгий
режим или только диагностическое сравнение.

Это дополняет проверку взаимного совпадения двух результатов:
даже если после аудита злоумышленник меняет **обе** SHA-256-метки
на одинаковые, допустимо выглядящие значения, итоговый отчёт
не может скрыть расхождение с более ранними квитанциями фактических
запусков. Несовпадение хотя бы одного из шести значений приводит
к отказу `independent replay disagrees with pinned capture receipts`
до создания успешной двухзапусковой квитанции.

Сквозные синтетические C11-тесты имитируют подмену обоих
GPU SHA-256, обоих SHA-256 кадров и счётчика GPU-пар одного
источника уже **после** настоящих повторных проверок. Испытания
проверяют строгий и диагностический режимы. Сырые данные
захватов остаются приватными; новая сверка не является
криптографической подписью или подтверждением происхождения
оригинальных GPU-команд с консоли PlayStation.

### Квитанция запуска: память против канонического файла

Добавлена ранняя проверка **до второго ELF-запуска**, связывающая
результат, возвращённый функцией захвата, с точными байтами
`process-frame.json`, которые первый дочерний процесс уже
опубликовал в приватном каталоге. Файл читается через
зафиксированный дескриптор каталога, без переходов по символьным
ссылкам и с проверкой владельца/прав `0600`. Допускается только
канонический JSON с сортировкой ключей и завершающим переводом
строки — тот же формат, который записывает исходный запуск.

Такой барьер не позволяет изменённому в памяти результату
`capture()` незаметно заявить, например, ложное подтверждение
происхождения, другое число GPU-пар или отсутствие наблюдаемого
канала stdout, тогда как опубликованная квитанция содержит
иные значения. Ранее часть этих полей не сопоставлялась
непосредственно с опубликованным файлом в оркестраторе двух
запусков. Теперь он отказывает **до запуска второго процесса**,
не выдавая успешного свидетельства.

Негативные тесты используют подлинные синтетические C11-запуски:
после публикации первого захвата меняют исключительно одно поле
возвращённого словаря, не изменяя приватный файл. Проверяются
метки GPU, терминального кадра, ELF/stdout и происхождения.
Оригинальные данные MAP02/PS1 не используются и не публикуются.
