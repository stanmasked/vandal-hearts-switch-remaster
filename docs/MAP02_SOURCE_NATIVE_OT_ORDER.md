# MAP02 — сопоставление AddPrim и DrawOTag по OTZ/LIFO

Новый локальный инструмент `tools/verify_map02_source_native_ot_order.py`
проверяет **относительный порядок оригинальных граней MAP02** между
заявленным журналом вызовов `AddPrim` и записанной последовательностью
обработки GPU-примитивов `DrawOTag`.

Инструмент основан на предварительно проверенной
[связке исходных граней и GPU FT4](MAP02_SOURCE_NATIVE_FT4_JOIN.md)
и не требует загрузки оригинальных игровых ресурсов в GitHub.

## Как рассчитывается ожидаемый порядок

В закреплённом публичном PC-порте:

- `ClearOTag` связывает bucket от индекса 0 до `OT_SIZE − 1`.
- `AddPrim` вставляет новый пакет в **голову** bucket.
- `DrawOTag` обходит их по этой цепочке.
- `RenderMapTile` выбирает bucket
  `OT_SIZE − max(5, AVSZ4_OTZ)`.

Таким образом, полигоны с большей глубиной OTZ обрабатываются
раньше. При одинаковой глубине они обрабатываются **в обратном
порядке вызовов AddPrim (LIFO)**. Грани сравниваются по ранее
проверенным GPU XY, UV, tpage, CLUT и texture-window, а не по
совпадающему материалу.

Например, если три исходных полигона были отправлены с
OTZ `128, 192, 128`, ожидаемый порядок индексов — `1, 2, 0`.
Он будет проверен против захваченной последовательности FT4
с допущением промежуточных посторонних GPU-примитивов.

## Приватный манифест

Поместите в папку проверенного `source_bundle` файл
`gpu-ot-order-join.json`:

```json
{
  "schema": "vh.map02.source-native-ot-order.v1",
  "source_frame": 411,
  "gpu_draw_frame": 12,
  "face_join_manifest_sha256": "<sha256 gpu-face-join.json>",
  "source_events_sha256": "<sha256 gpu-events.jsonl>",
  "native_events_sha256": "<sha256 gpu-native-events.jsonl>",
  "source_events_in_addprim_order": true,
  "one_clear_otag_one_draw_otag": true
}
```

Номера и хеши — только пример формата.

Два последних параметра **обязательны**, поскольку программа не
может самостоятельно установить, что `gpu-events.jsonl`
действительно записан в порядке вызовов `AddPrim`, а журнал
GPU относится к единственной цепочке `ClearOTag/DrawOTag`.
Это **заявления оператора захвата**, а не доказательство.
Если они неизвестны, выставлять `true` нельзя и такая
проверка порядка не должна считаться выполненной.

Запуск из корня репозитория:

```sh
python3 -m tools.verify_map02_source_native_ot_order \
  /private/map02-frame /private/map02-gpu-capture \
  > /private/map02-ot-order-report.json
```

## Предварительные проверки и отказ при ошибке

Программа сначала проверяет SHA манифеста, обоих журналов,
исходных данных и полную уникальную привязку оригинальных
граней к GPU-пакетам, включая GTE и слова VRAM.

Далее вычисляется ожидаемый порядок **всех предъявленных
исходных граней**. Последовательность этих же граней в
реальном обходе GPU должна точно совпасть. В частности,
перестановка двух FT4 в одном bucket приводит к ошибке, даже
если совпадают все их координаты, UV и цвета.

В отчёте отображаются только SHA и счётчики: количество граней,
проверенных пар с одинаковой или разной глубиной, а также
пересечения экранных **ограничивающих прямоугольников (AABB)**.
Эти AABB служат лишь сигналом о возможном перекрытии и
**не доказывают реальное покрытие пикселей**.

## Что нельзя считать доказанным

- Числовые метки кадров и заявленный порядок AddPrim не
  аутентифицируются проверкой SHA; синтетические записи способны
  пройти её успешно.
- Проверяется **относительный порядок только предъявленных
  граней**. Посторонние FT4, спрайты, тайлы, команды состояния и
  прочие пакеты могут влиять на результат; инструмент не
  подтверждает порядок *всех* GPU-команд.
- Зафиксированный порядок FT4 не доказывает точность итогового
  наложения: необходимы действительные растеризация, drawing
  area, STP/ABR, маскирование и сравнение готовых кадров.
- 64-записный предел исходного GPU-регистратора ограничивает
  полноту наблюдения; при достижении предела проверка откажет.
- Наличие совпадения не доказывает исполнение кода на
  настоящей PlayStation или Nintendo Switch.

В CI используется синтетический комплект: два полигона
с одинаковой глубиной, разные CLUT и GPU-обход в обратном
порядке относительно исходных событий. Отдельные тесты
отклоняют неверный LIFO, повреждённые SHA и недоказанные
предпосылки о составе одной таблицы глубины.
