# MAP02 — синхронная связь DrawOTag и PutPixel

Новое расширение после
[локального наблюдения PutPixel](MAP02_NATIVE_PUTPIXEL_SAMPLE.md)
и [анализа наложения граней](MAP02_NATIVE_OVERDRAW_EVIDENCE.md)
позволяет **связывать действительный вызов записи пикселя с
порядковым номером GPU-примитива в выбранном кадре**.

Ранее наблюдатель одного адреса VRAM не знал, какой `POLY_FT4`,
`SPRT` или `TILE` вызвал `PutPixel`. Теперь инструментатор
`tools/instrument_map02_putpixel_scope.py` генерирует сразу две
совместимые копии строго закреплённых файлов PC-порта:

- `libgpu.scope.c` — существующий опциональный захват
  `before/after` снимков VRAM в `DrawOTag`, а также
  установка и снятие контекста каждого обработанного
  *не-bucket* GPU-примитива.
- `pc_raster.scope.c` — опциональный наблюдатель реального
  `WritePixel` с дополнительными полями `frame`,
  `primitive_ordinal` и `primitive_type` для выбранного
  адреса VRAM.

**Оба исходника необходимо собирать и запускать одновременно**
в одном экземпляре PC-порта. Нельзя соединять журнал
`PutPixel` из одной игры с журналом GPU из другого запуска
и считать их общим исходным кадром.

## Локальная сборка

Нужен публичный PC-порт ровно на коммите
`14552fffa0e0b47e02b57592e274fc6e7a649923`
и собственные законно полученные игровые ресурсы, остающиеся
локально у владельца.

Создание файлов из корня репозитория ремейка:

```sh
python3 -m tools.instrument_map02_putpixel_scope \
  /private/VandalHearts-PcPort/platform/pc/src/libgpu.c \
  /private/VandalHearts-PcPort/platform/pc/src/pc_raster.c \
  --output-dir /private/map02-scoped-build
```

В собственной локальной PC-сборке использовать сгенерированные
`libgpu.scope.c` и `pc_raster.scope.c` **вместо**
соответствующих обычных файлов, с двумя флагами:

```text
-DVH_MAP02_GPU_CAPTURE
-DVH_MAP02_PUTPIXEL_SCOPE
```

При запуске задать:

```sh
export VH_MAP02_GPU_CAPTURE_DIR=/private/map02-capture
export VH_MAP02_GPU_CAPTURE_FRAME=12
export VH_MAP02_PUTPIXEL_DIR=/private/map02-capture
export VH_MAP02_PUTPIXEL_FRAME=12
export VH_MAP02_PUTPIXEL_X=30
export VH_MAP02_PUTPIXEL_Y=30
```

Оба каталога должны существовать заранее. Приведённые значения
— **синтетический пример**, а не адрес или номер достоверного
кадра игры. Наблюдение выполняется только на синхронном нативном
CPU GPU-пути; отложенный рендеринг в `s_hires` не
инструментируется.

Захват VRAM ограничен 64 записями (32 парами).
Журнал одного адреса `PutPixel` — 64 вызовами.
При достижении предела доказательство полного обхода
невозможно; новый коррелятор отклоняет обрезанный журнал.

## Привязка к исходной MAP02

Подготовленный ранее комплект
[исходной карты, GTE, текстур и FT4](MAP02_SOURCE_NATIVE_FT4_JOIN.md)
должен проходить проверку, включая
[сопоставление порядка OT](MAP02_SOURCE_NATIVE_OT_ORDER.md)
и [согласованность всех снимков VRAM](MAP02_NATIVE_OVERDRAW_EVIDENCE.md).

Создайте в **приватной папке исходного MAP02-комплекта**
файл `gpu-putpixel-ot.json`:

```json
{
  "schema": "vh.map02.native-putpixel-ot.v1",
  "source_frame": 411,
  "gpu_draw_frame": 12,
  "overdraw_manifest_sha256": "<SHA256 файла gpu-native-overdraw.json>",
  "native_events_sha256": "<SHA256 файла gpu-native-events.jsonl>",
  "putpixel_events_sha256": "<SHA256 файла putpixel-native-events.jsonl>"
}
```

Номера в примере не подтверждены игровой записью.
Контрольные суммы необходимо вычислять из **реальных точных
байтов локальных файлов**.

Запуск:

```sh
python3 -m tools.verify_map02_putpixel_scope \
  /private/map02-source /private/map02-capture \
  > /private/map02-putpixel-ot-report.json
```

Программа повторно проверит всю прежнюю цепочку
исходная грань → GTE → пакет FT4 → OTZ/LIFO → VRAM.
Затем каждое событие пикселя связывается с конкретным
`primitive_ordinal`:

- ordinal начинается с нуля в каждом `DrawOTag`;
- увеличивается **для каждого не-bucket примитива**,
  включая спрайты, тайлы и `DR_MODE`;
- передачи `LoadImage/MoveImage/ClearImage` в этот ordinal
  не входят;
- строго сверяются номер кадра, тип пакета, координаты
  выбранного слова VRAM и реальная последовательность
  `before/after` для данного примитива;
- если у уже идентифицированной исходной FT4 наблюдаемое
  значение VRAM изменилось, но нет соответствующей
  записи `PutPixel`, проверка откажет.

Коррелятор не публикует исходные значения BGR555,
координаты, текстуры или содержимое бинарных файлов.
JSON-отчёт содержит хеши, количество вызовов и
агрегированные результаты.

## Временные изменения выбранного слова VRAM

Расширенный `tools/verify_map02_putpixel_scope.py` повторно читает
полные снимки VRAM перед/после **каждого** оригинального GPU-примитива
и сопоставляет их с вызовами `PutPixel` для одного выбранного адреса.
Теперь он публикует отдельные агрегаты только для исходных FT4,
сопоставленных с MAP02:

- `source_ft4_sampled_changed_word_draws` — число FT4, изменивших
  выбранное слово VRAM между собственными PRE/POST;
- `source_ft4_sampled_bit15_only_changes` — изменение только бита 15;
- `source_ft4_sampled_color_only_changes` — изменение только младших 15 бит;
- `source_ft4_sampled_color_and_bit15_changes` — изменение и цвета,
  и бита 15;
- `source_ft4_sampled_first_changed_pre_equals_last_changed_post` —
  совпадение значений перед первым **изменившим** FT4 и после
  последнего **изменившего** FT4 (`null`, если таких FT4 нет).

Дополнительно анализатор классифицирует **каждый зарегистрированный
вызов** `PutPixel`, принадлежащий сопоставленным FT4 (в отличие от
снимков до/после **всего примитива**). Публикуются только счётчики
`source_ft4_scoped_changed_putpixel_calls`,
`source_ft4_scoped_unchanged_putpixel_calls`, три взаимоисключающие
категории `source_ft4_scoped_bit15_only_putpixel_calls`,
`source_ft4_scoped_color_only_putpixel_calls`,
`source_ft4_scoped_color_and_bit15_putpixel_calls`, а также
`source_ft4_scoped_transient_draws_invisible_to_vram_delta` —
число сопоставленных FT4 с хотя бы одним изменившим слово вызовом,
но неизменным выбранным VRAM-словом между снимками примитива.

Все категории вызовов суммируются до количества приписанных источнику
зарегистрированных вызовов, не включая посторонние примитивы. Например,
записи `0x0000 → 0x8000 → 0x0000` внутри одного FT4 дают два
изменивших слово вызова и один **наблюдаемый** примитив с нулевой
разницей снимков VRAM. Отсутствие вызова в ограниченном журнале не
доказывает его невыполнение; полнота и подлинное происхождение
игрового захвата по-прежнему не удостоверены.

Три категории изменений в сумме равны
`source_ft4_sampled_changed_word_draws`. Например, два вызова
`PutPixel` могут последовательно установить, а затем снять бит 15;
оба события фиксируются, даже если итоговое слово VRAM снова равно
исходному. При этом между двумя сопоставленными FT4 могут быть
**другие GPU-примитивы**. Поэтому совпадение конечных значений не
доказывает, что эти FT4 были единственной причиной изменений:
`source_ft4_sampled_endpoint_causality_verified=false`.

Поскольку исходная ветка `DR_MODE` в закреплённом `libgpu.c`
не вызывает `WritePixel`, проверяющий отвергает **любой**
приписанный `DR_MODE` вызов `PutPixel` — даже с одинаковым
цветом до и после. Нативный VRAM-аудит отдельно отвергает любые
изменения VRAM самим `DR_MODE`.

Источник журналов использует бинарную запись JSONL с завершающим LF.
Проверяющий требует именно такую структуру и отвергает отсутствие
последнего LF, CRLF и NUL даже при пересчитанной контрольной сумме.
Это проверка формата, а не аутентификация игрового сеанса.

## Последовательность полупрозрачных наложений FT4

При проверке последовательных вызовов `PutPixel` в одном
`DrawOTag` теперь отдельно публикуются агрегаты **только для
сопоставленных с MAP02 исходных FT4**, не включая посторонние
примитивы:

- `source_ft4_scoped_semitransparent_blend_calls` — число
  непосредственно наблюдавшихся запросов `semi=1`;
- `source_ft4_scoped_semi_blend_abr0_calls` … `abr3_calls` —
  число этих запросов по каждому режиму ABR;
- `source_ft4_scoped_accurate_semi_blend_calls` и
  `source_ft4_scoped_legacy_semi_blend_calls` — разделение по
  режиму исходного PC-рasterizer;
- `source_ft4_scoped_draws_with_multiple_semi_blends` —
  число сопоставленных FT4 с двумя и более наблюдаемыми
  полупрозрачными вызовами на выбранном адресе.

Сумма четырёх ABR-счётчиков равна общему количеству
`source_ft4_scoped_semitransparent_blend_calls` и сумме
счётчиков accurate/legacy. Она не должна превышать число всех
зарегистрированных полупрозрачных вызовов в том же сеансе:
остальные могли принадлежать сторонним `DrawOTag` примитивам.

Синтетические регрессии покрывают accurate ABR1 → ABR2
**внутри одного FT4**, accurate ABR0 → ABR3 **между соседними FT4**,
legacy ABR0 → ABR3 **внутри одного FT4**
и корректную запись `semi=1` стороннего FT4, которая
не должна попасть в агрегаты исходных MAP02-граней.
Каждый результат записи сравнивается с закреплённым PC `BlendG1`
и контрольными VRAM-снимками. Даже успешное совпадение
не исключает недошедших до ограниченного журнала вызовов и
не подтверждает растеризацию или маску физической PlayStation.

## Проверка оригинального PC-смешивания (ABR)

Оба анализатора теперь используют
`tools/map02_pc_writepixel_reference.py` — отдельный программный
эталон функций `WritePixel` и `BlendG1` из закреплённого
`platform/pc/src/pc_raster.c` (Git blob
`ba8a05d161ad778c0b75e452ff0a11ed163c65cd`).

- При `semi=0` исходный `front` копируется без изменений, включая бит 15.
- При `semi=1, accurate=1` выполняется исходная 5-битная
  беззнаковая арифметика `BlendG1` для ABR 0, 1, 2, 3;
  значение `textured` определяет сохранение бита 15.
- При `semi=1, accurate=0` применяется отдельная legacy-ветка:
  распаковка 5-битных каналов в 8-битные, арифметика с усечением
  целочисленных частных, ограничение диапазона и обратная упаковка.
  Эта ветка всегда формирует значение без установленного бита 15.

Каждый зарегистрированный полупрозрачный вызов теперь требует
точного равенства `after` результату закреплённого PC-алгоритма,
даже если исходный и конечный пиксели совпадают. Отчёт содержит
только количество проверенных `accurate_pc_blend_results_checked`
и `legacy_pc_blend_results_checked`, не сами пиксели. Примеры
подмены `front` или `after` отвергаются независимо от хешей
манифеста и неизменности соседних снимков VRAM.

В закреплённом C функция `AccurateEnabled()` запоминает значение
переменной `VH_ACCURATE` при первом вызове. Поэтому внутри одного
нативного журнала этот режим не может переключаться: смешанные
`accurate=0` и `accurate=1` отклоняются. Синтетические эталонные
векторы проверены также против отдельно скомпилированной C11-версии
закреплённой арифметики. **Это доказательство согласованности
программной модели с предъявленными данными, а не доказательство
физической точности GPU PlayStation, STP/mask или подлинного MAP02.**

## Два слова VRAM в одном синхронном журнале

Для проверки **общего порядка** двух отдельных координат внутри
одного инструментированного `DrawOTag` теперь предусмотрена
[двухточечная диагностика](MAP02_NATIVE_MULTI_PUTPIXEL_SCOPE.md).
В отличие от простого сложения независимых выборок ниже, новый
`VH_MAP02_MULTI_PUTPIXEL_SCOPE` записывает обе координаты в
**один** монотонный журнал `PutPixel`, связанный с **теми же**
оригинальными нативными снимками VRAM каждого примитива. Его
`verify_map02_putpixel_multi_scope.py` строго проверяет два
разных адреса, межкоординатный порядок, корректность PC `WritePixel`,
все хеши и исходные MAP02 FT4/OTZ. Ограничение общего журнала
остаётся 64 вызовами. Это проверка структуры заявленного общего
наблюдения, **не** независимая аутентификация игрового процесса
и **не** доказательство пиксельной эквивалентности PS1.

## Несколько независимо выбранных слов VRAM

Инструмент `tools/audit_map02_putpixel_samples.py` позволяет
сводить **от двух до восьми** независимых приватных однопиксельных
сеансов `DrawOTag`/`PutPixel`. Каждый компонент заново и полностью
проверяется через `verify_map02_putpixel_scope.py` с оригинальной
цепочкой GTE/FT4/OT/VRAM и точным результатом `WritePixel`.
В локальном исследовании можно выполнить:

```sh
python3 -m tools.audit_map02_putpixel_samples \
  --capture /private/map02-a/source /private/map02-a/gpu \
  --capture /private/map02-b/source /private/map02-b/gpu \
  > /private/map02-two-coordinate-summary.json
```

Проверяются совпадение **заявленных** номеров исходного и нативного
кадров, уникальность выбранного слова VRAM у каждого захвата,
лимиты и корректность всех приватных журналов. Выход содержит
только суммарные счётчики зарегистрированных вызовов,
полупрозрачных записей, ABR и различимых точек выборки:
ни координаты, ни цвета, ни абсолютные пути в JSON не выдаются.
Повторная выборка одной координаты строго отклоняется, чтобы
не увеличивать счётчики повторным подсчётом одного слова.
Отчёт также раздельно суммирует
`observed_native_putpixel_calls` (все наблюдённые нативные вызовы),
`calls_attributed_to_source_keyed_ft4` (лишь вызовы от
сопоставленных MAP02-граней),
`source_keyed_ft4_draws_checked` и число соответствующих
примитивов с/без зарегистрированных вызовов или изменения
VRAM. Агрегатор отклоняет невозможные отношения этих
счётчиков, не приписывая вызовы посторонних FT4 исходным
граням.

**Существенное ограничение:** эти каталоги могут происходить из
*разных игровых запусков*. Даже одинаковые метки кадров и
SHA-256 GPU-событий не доказывают, что наблюдения выполнены
одновременно. Поэтому агрегатор всегда сообщает
`same_native_capture_session_authenticated=false`,
`simultaneous_multi_word_observation_proven=false` и
`complete_putpixel_write_stream_proven=false`. Суммируемые
значения — лишь **сумма независимо проверенных выборок**, а не
перекрытие полигонов в доказанном общем кадре. Подлинность
исходной игры, PlayStation GPU, HD-подмена и работа Switch
по-прежнему не подтверждены этим инструментом.

## Границы и интерпретация

Если `PutPixel` был вызван с тем же самым цветом,
это **положительное наблюдение вызова без изменения VRAM**.
Без отдельной инструментированной ветки отбора текселей
не следует считать отсутствие вызова доказательством
нулевого индекса текстуры, клиппинга, GPU mask-test или
скрытого полупрозрачного пикселя.

Этот коррелятор связывает *предъявленные* журналы, но
не удостоверяет происхождение оригинальной игры и
не доказывает непрерывность сбора после ограничений
на количество записей. Для режимов ABR/STP текущие
события подтверждают выполняемый PC-код, но не
физическую пиксельную идентичность GPU PlayStation.

Сборка GitHub компилирует два реальных публичных исходника
с включённым/выключенным наблюдением и проверяет
**синтетические** события, а не запускает оригинальную
игру или готовую карту MAP02 на Nintendo Switch.
