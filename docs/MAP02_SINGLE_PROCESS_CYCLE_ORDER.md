# MAP02 — порядок исходных CD и GPU вызовов в одном процессе

Этот этап добавляет **отдельный опциональный наблюдатель**, а не заменяет
[CD/GPU/GTE SHA-256-манифест](MAP02_CD_SOURCE_FINAL_WITNESS.md).
Цель — исключить прежнюю возможность ошибочно трактовать как полный
оригинальный игровой цикл совпадение идентификаторов из **раздельных**
искусственных тестов CdRead и DrawOTag.

## Состояния наблюдателя

При компиляции с `-DVH_MAP02_CYCLE_ORDER` один и тот же объект
`tools/map02_cycle_order.c` связывается со следующими **исходными**
точками входа закреплённого PC-порта:

1. `LoadCdFile(CDF_M_MAP02_PRS)`: заявка LBA `0x1bcc`, 12 секторов;
2. начало оригинального `CdRead` для этого диапазона;
3. окончание вызова оригинального `CdRead`;
4. терминальный переход оригинального `ContinueLoadingCdFile` к 99;
5. начало явно выбранного оригинального `DrawOTag`;
6. завершение прохода его ordering table без обрыва обхода.

Пропуск, повтор, нарушение порядка, неверные размеры CD-ресурса
или незавершённый проход приводят к отказу. Промежуточные вызовы GPU,
не относящиеся к выбранному кадру, игнорируются. Нельзя выбрать кадр
по умолчанию: требуется `VH_MAP02_PROBE_FRAME`.

Это **логический тест порядка вызовов**, а не доказательство, что в
`CdRead` переданы правильные байты или что `DrawOTag` отрисовал MAP02.
Для CD-содержимого нужен отдельный проверяющий модуль, для GPU — исходные
VRAM/FT4/PutPixel/BlendG1-свидетельства. Ни одно из существующих
свидетельств этот инструмент автоматически не повышает в статусе.

## Генерация копий закреплённых исходников

```sh
python3 -m tools.instrument_map02_cycle_order \
  /private/map02/VandalHearts-PcPort \
  /private/map02/generated-cycle
```

Выходной каталог должен быть пустым и находиться вне исходного checkout.
Создаются `core_cd.c`, `libcd.c`, `libgpu.c`: опциональная
инструментация исходного CD плюс существующий scoped-проход оригинального
`DrawOTag`. Содержимое оригинального checkout не изменяется.
При отличающемся SHA исходника или пропущенной точке внедрения
генерация завершается ошибкой. Это **не готовый игровой бинарник**:
копии требуется вручную включить вместо соответствующих translation units
в приватную сборку PC-порта вместе с
`tools/map02_cd_read_probe.c`, `tools/map02_cycle_order.c`,
`tools/map02_capture_session.c` и остальными необходимыми модулями
для выбранных режимов диагностики.

Обязательные параметры наблюдателя:

```sh
VH_MAP02_PROBE_FRAME=<фактический-номер-DrawOTag>
VH_MAP02_CYCLE_OUTPUT_DIR=/private/map02/cycle
```

Каталог `cycle` нужно заранее создать с правами `0700`, без
символической ссылки в конечном компоненте пути, владельцем текущего
процесса. При состоявшемся упорядоченном цикле инструмент может
создать единственный файл `map02-single-process-cycle.jsonl` с
правами `0600`; если файл уже существует, он никогда не заменяется.
В файл попадают только метаданные: текущий процессный nonce, номер
выбранного GPU-кадра, версия схемы и ограничительные поля. Исходные
сектора, текстуры, полный VRAM, адреса памяти и бинарник не сохраняются.

Если указан неверный/неприватный путь или запись не удалась, успех
не подтверждается. Для полноценного доверенного маршрута потребуется
дополнительно связать эту квитанцию с уже существующими CD/GPU/GTE
манифестами через отдельную повторную проверку.

## Что проверяет CI

`tests/test_map02_cycle_order.py` **синтетически вызывает функции
наблюдателя** в одном скомпилированном C-процессе, испытывает
неправильный порядок и защищённую запись. Workflow дополнительно
проверяет, что генератор действительно находит закреплённые
оригинальные точки в публичном PC-порту.

CI **не исполняет полного игрового** `LoadCdFile →
ContinueLoadingCdFile → DrawOTag` на пользовательском оригинальном
образе. Поэтому `original_map02_rendering_proven` и
`physical_ps1_equivalence_proven` остаются `false`.
HD-подмена остаётся отключённой.

Не публикуйте в GitHub игровой образ, исполняемый файл
с пользовательскими данными, полные GPU-снимки или содержимое приватных
каталогов захвата.

## Независимая привязка квитанции цикла к CD/GPU/GTE/процессу

После получения реального приватного захвата и **публикации** прежнего
`gpu-native-map02-cd-process-source-witness.json` можно запустить:

```sh
python3 -m tools.verify_map02_cycle_cd_gpu_join \
  /private/map02/source-bundle \
  /private/map02/native-windows \
  /private/map02/scoped \
  /private/map02/handoff \
  /private/map02/cycle \
  /private/map02/owned-game-image.bin \
  --upstream-checkout /private/map02/VandalHearts-PcPort \
  --pc-binary /private/map02/pc-port-instrumented \
  --frame <фактический-DrawOTag-кадр>
```

Этот **проверяющий инструмент ничего не публикует и не изменяет**.
Он требует единственный файл `map02-single-process-cycle.jsonl` в
отдельном приватном каталоге; у файла должны быть права `0600`.
Содержимое проверяется как одна строгая строка JSONL без лишних или
повторяющихся полей. Обязательно совпадают выбранный кадр и
SHA-256 процессного nonce с исходным итоговым CD/GPU-манифестом.

Перед успешным ответом полностью повторно выполняется **вся дорогая**
проверка `verify_published_original_cd_witness`: собственный raw BIN,
оригинальная CD-квитанция, источник GPU/GTE, VRAM, наблюдённый Linux ELF
и открытый дескриптор. Затем проверяется неизменность обоих входных
файлов. Печатаются лишь SHA-256 манифеста/квитанции/nonce и логические
ограничительные поля; необработанный nonce и игровые байты не выводятся.

Положительный ответ означает: отдельная квитанция порядка
`LoadCdFile → CdRead → ContinueLoadingCdFile → DrawOTag` согласована
с уже проверенным CD/GPU/процессным комплектом по кадру и nonce.
Это не самостоятельная защита от злонамеренной фальсификации процесса
и не свидетельство пиксельной точности или реального отображения MAP02.
Поля `full_original_gameplay_authenticated`,
`original_map02_rendering_proven` и
`physical_ps1_equivalence_proven` всегда ложны.

В CI для этой связи используются синтетические записи и уже
существующие тестовые fixture; внешняя загрузка игры не выполняется.
Реальная проверка возможна только после приватной сборки PC-порта
с общим экземпляром наблюдателя и пользовательским образом.

## Подготовка настоящей единичной PC-сборки (отдельный Makefile-overlay)

Генератор `tools.prepare_map02_cycle_build` дополняет предыдущую
проверку порядка **без модификации закреплённого checkout** и
отдельно сохраняет все файлы, необходимые GNU Make:

```sh
python3 -m tools.prepare_map02_cycle_build \
  /private/map02/VandalHearts-PcPort \
  /private/map02/cycle-build

# First: a full Make DAG dry-run, NO compilation, NO retail bytes read.
python3 -m tools.check_map02_cycle_make_plan \
  /private/map02/VandalHearts-PcPort \
  /private/map02/cycle-build

# Only after the audit succeeds AND your own game inputs are installed:
python3 -m tools.build_map02_cycle_pc_local \
  /private/map02/VandalHearts-PcPort \
  /private/map02/cycle-build

# Advanced equivalent (if diagnosing local build failures manually):
# cd /private/map02/VandalHearts-PcPort/platform/pc
# make -j1 -f Makefile -f /private/map02/cycle-build/map02_cycle.mk \
#   link BUILD_DIR=build-map02-cycle REGION=us NO_WEBP=1 NO_HDVIDEO=1
```

Запуск полной `make link` требует оригинального пользователя US-образа,
проверенного исполняемого файла, необходимых генератору данных ресурсов
и доступных зависимостей PC-порта. **В CI полного игрового бинарника
на пользовательском retail-образе нет.** Исходники в upstream не
перезаписываются: собранные объекты сохраняются исключительно в
специальном `build-map02-cycle` каталоге (не `build`). Базовый
Makefile не переписывается; `REGION=jp` и объединённые сборки отклоняются.

В диагностический ELF должны попасть конкретные оригинальные функции
`LoadCdFile`, `ContinueLoadingCdFile`, `CdRead` и `DrawOTag`,
компилируемые с опциональными source-хуками, единые объектные файлы
`map02_cycle_order`, `map02_cd_read_probe`,
`map02_capture_session`, а также **тот же оригинальный**
`pc_raster.c` с opt-in PutPixel/BlendG1-наблюдателем. Генератор
теперь совместно внедряет native GPU recorder, scoped DrawOTag и VRAM edge
hooks в `libgpu.c` и копирует stage/sink/edge-модули в приватную сборку.
Отдельный `map02_scoped_blend_stage.c` компилируется с необходимыми
`VH_MAP02_CD_READ_PROBE`, `VH_MAP02_VRAM_EDGE_PROBE` и
`VH_MAP02_CAPTURE_SESSION` флагами для пяти связанных scoped-файлов.

Для фактического захвата нужны заранее созданные **раздельные**
приватные каталоги `0700` и явно согласованные переменные
`VH_MAP02_GPU_CAPTURE_DIR`, `VH_MAP02_GPU_CAPTURE_FRAME`,
`VH_MAP02_GPU_CAPTURE_WINDOW_COUNT=2`,
`VH_MAP02_PROBE_FRAME`, `VH_MAP02_PROBE_X`,
`VH_MAP02_PROBE_Y`, `VH_MAP02_PROBE_OUTPUT_DIR` и
`VH_MAP02_CYCLE_OUTPUT_DIR`. Номер кадра должен быть одним и тем же
в GPU, scoped и cycle настройках. Для штатного PIXEL/BlendG1
теста требуются `VH_ACCURATE=1` и `VH_INTERNAL_SCALE=1`.
Обычный запуск без этих переменных не создаёт подтверждённой MAP02
квитанции.

Генератор требует точных Git blob SHA-1 исходных единиц
`src/core/cd.c`, `platform/pc/src/libcd.c`,
`platform/pc/src/libgpu.c` и `platform/pc/Makefile`.
Он создаёт приватные `0600` копии этих инструментированных исходников,
необходимые C-модули, заголовки и JSON с SHA-256 всего комплекта.
Путь каталога должен быть безопасным для GNU Make, новым и находиться
вне исходного checkout.

В GitHub Actions дополнительно собираются в один **перемещаемый объект**
(`ld -r`) четыре подлинные оригинальные translation units — CD core,
libcd, libgpu, pc_raster — и общие CD/GPU/VRAM/BlendG1-наблюдатели,
после чего проверяются разрешённые символы и отсутствие оставшихся
неразрешённых диагностических `vh_map02_*` ссылок.
Это значительный шаг к настоящей единичной программе, но `ld -r`
не создаёт исполняемый игровой ELF и не исполняет MAP02.
Нельзя считать эту проверку подтверждением её отрисовки.

## Подключение полного цикла к контролируемому Linux-запуску

Опциональная поддержка `--cycle-dir` добавлена в существующий
`tools.map02_verified_process_launch run`, чтобы **сам launcher**
передавал путь единой квитанции выбранному дочернему процессу.
Прежнее наследование переменных `VH_MAP02_*` из окружения намеренно
запрещено: `VH_MAP02_CYCLE_OUTPUT_DIR` формируется только из
проверенного аргумента. Пример после подготовки плана запуска:

```sh
mkdir -m 700 /private/map02/cycle

python3 -m tools.map02_verified_process_launch run \
  /private/map02/handoff \
  /private/map02/native-windows \
  /private/map02/scoped \
  --pc-binary /private/map02/VandalHearts-PcPort/platform/pc/build-map02-cycle/vandalhearts_pc \
  --owned-game-image /private/map02/owned-game-image.bin \
  --upstream-checkout /private/map02/VandalHearts-PcPort \
  --cycle-dir /private/map02/cycle \
  --x 10 --y 20 --timeout 900
```

Координаты 10,20 условные: действительный целевой пиксель необходимо
определить по исходным GTE/FT4-свидетельствам, а не принимать эту пару
за эталон MAP02. Если `--cycle-dir` не указан, launcher сохраняет
прежнюю семантику и не создаёт свидетельства порядка.

С указанным каталогом launcher **до запуска** требует отдельную пустую
папку `0700`; после завершения дочерней программы, но **до публикации**
Linux-квитанции требует ровно один приватный
`map02-single-process-cycle.jsonl` с тем же номером DrawOTag и
SHA-256 nonce, что в нативном GPU/scoped комплекте.
Без совпадения успех не публикуется. Привязку к настоящим CD-байтам,
GTE/FT4 и собственному raw-образу отдельно и позже подтверждает
`verify_map02_cycle_cd_gpu_join`, который **повторяет** всю исходную
проверку свидетельств. Наличие квитанции порядка само по себе
не доказывает построение игровой сцены или аппаратную точность PS1.

## Предварительная проверка полного ELF перед запуском

Опциональный `--cycle-dir` теперь также включает **fail-closed
структурную проверку самого бинарника до его исполнения**:

```sh
python3 -m tools.check_map02_cycle_elf \
  /private/map02/VandalHearts-PcPort/platform/pc/build-map02-cycle/vandalhearts_pc
```

Проверяются права и владение исполняемым файлом, формат Linux ELF
(`EXEC` или `DYN`, но не `ET_REL` от `ld -r`), а также
экспортируемые имена оригинальных `LoadCdFile`,
`ContinueLoadingCdFile`, `CdRead`, `DrawOTag` и всех ключевых
наблюдателей CD/GPU/cycle, VRAM, PutPixel, BlendG1 и POSIX staging.
Бинарник без хотя бы одного обязательного символа, очищенный от
символов `strip --strip-all`, либо неподходящий частичный объект
отклоняется **до запуска**. Режим без `--cycle-dir` остаётся прежним.

Важно: совпадение **имён** само по себе не подтверждает реализацию или
аутентичность исходного кода — намеренно созданная синтетическая
программа с такими же экспортами проходит только этот структурный
этап. Полноценное доказательство требует сверки исполняемого файла с
подготовленным SHA-256-планом, наблюдения Linux `/proc` во время
исполнения, подлинных CD-байтов и всех независимых GPU/GTE
свидетельств. Поэтому даже успешная структурная проверка не означает
фактического построения MAP02 и не разрешает HD-подмену.

## Неподменённый графический путь при запуске цикла

В исходном PC-порту установленный HD pack автоматически включается
при обнаружении, а `VH_HD_PACK` и `VH_HD_VIDEOS` могут обходить
обычный переключатель. Кроме того, локализованные фоновые изображения
из language pack могут заменить исходные независимо от HD-переключателя.

Поэтому **только при включённом `--cycle-dir`** контролируемый Linux
launcher принудительно передаёт дочернему процессу:

```text
VH_HDPACK=0
VH_HD_PACK=
VH_HD_VIDEOS=
VH_LANG=
VH_LANGPACK=
VH_INTERNAL_SCALE=1
VH_ACCURATE=1
VH_RASTER_THREADS=1
```

Пустые значения здесь преднамеренны: они блокируют не только внешние
переменные среды, но и их восстановление из ini-файла при запуске.
Результат — отключение обычных путей HD-подмены, локализации
фоновых изображений и внутреннего повышения разрешения, а также
детерминированный однопоточный профиль. Наблюдение исходной сцены
всё равно должно быть подтверждено независимыми VRAM/CD/GTE-данными;
структурная проверка ELF и окружение сами по себе этого не доказывают.
Вмешательство игрока в игровые настройки после запуска проверкой
окружения отдельно не отслеживается.

## Дополнительный контроль полного графа GNU Make

Поэтому `make -n` проверяет **полный граф сборки**: все объекты
оригинального игрового кода, `generated_data.o`, четыре
инструментированные translation units и общие шесть CD/GPU/VRAM модулей
должны присутствовать в окончательной команде линковки. Проверяющий
`tools.check_map02_cycle_make_plan` до сухого запуска повторно сверяет
SHA-256 **каждого** файла приватного набора с неизменённым манифестом,
соответствие закреплённых оригинальных C-источников и Makefile,
владельца и права `0600` / `0700`. Подозрительные, лишние файлы или
изменённые исходники вызывают отказ. Команда печатает только короткий
результат со SHA-256 развёрнутой строки линковщика, а не игровые данные.

Сухой запуск не создаёт `vandalhearts_pc`, не подтверждает доступность
подлинного пользовательского SLUS-образа, не компилирует оригинальные
игровые данные и не является доказательством исполнения MAP02.
Локальная `make link` всё ещё требует пользовательский оригинальный
образ и зависимости для всех генераторов исходного PC-порта.

## Строгая локальная полная сборка ELF

`python3 -m tools.build_map02_cycle_pc_local` выполняет сухую
проверку входных SHA-256 и полного графа GNU Make **перед любой
компиляцией**. Он отказывается перезаписывать ранее созданный бинарник
`build-map02-cycle/vandalhearts_pc`, вызывает `make -j1 link`
(без конкурирующих операций перестройки staging-заголовков) и после
компиляции проверяет, что результат является полноценным исполняемым
ELF со всеми требуемыми экспортами оригинального CD/GPU-кода и
наблюдателей. Входные файлы перепроверяются после сборки.

Скрипт печатает только SHA-256 исполняемого файла, отпечаток команды
линковки и безопасные флаги готовности. Содержимое EXE, игрового BIN,
байты VRAM, исходные адреса или полные журналы компилятора не
публикуются. В случае ошибки компилятора диагностический вывод
подавляется, чтобы приватные пути и данные не попадали в общий чат
или публичный CI. Для локального исследования ошибок опытный
разработчик может вручную выполнять приведённую выше команду
`make` в своём закрытом окружении.

**Сборка ещё не равна запуску игры:** даже успешно созданный полный
ELF не доказывает чтение настоящих 12 секторов MAP02, создание сцены,
соответствие оригинальному PlayStation и корректность HD. В GitHub
CI тестируется только сухой граф `make -nB` и искусственные ответы
компилятора; оригинальные игровые данные и настоящая полная
компиляция остаются локальными.
