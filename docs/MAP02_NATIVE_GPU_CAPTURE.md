# MAP02 — опциональный захват реального порядка событий PC GPU

Инструмент `tools/instrument_map02_gpu_native_events.py` создаёт
**отдельную** копию исходного `platform/pc/src/libgpu.c` из
публичного PC-порта `HalmyLyseas/VandalHearts-PcPort` с закреплённым
Git blob `9d0fab71c45ed09dda072cfeacd557ab9c5d81e5`.

Цель — наблюдать порядок реальных вызовов CPU/PC GPU, а не
восстанавливать его по различию двух снимков. При обычной компиляции
без `VH_MAP02_GPU_CAPTURE` диагностические функции отсутствуют.
В оригинальные исходники и игру инструмент самостоятельно не пишет.

## Что регистрируется

В специально выбранном кадре `DrawOTag` регистрация делает
**полный снимок 1024×512×16 бит VRAM до и после** каждого обработанного
примитива, включая `POLY_FT4`, `SPRT`, `TILE`, `DR_MODE` и
другие случаи исходного `switch(type)`. Сохраняются номер кадра,
порядковый номер, тип примитива, признак полупрозрачности, значения
texture-window и draw mode. Для FT4 фиксируются также GPU-координаты,
UV, tpage и CLUT.

Отдельно фиксируются события `LoadImage`, `MoveImage`,
`ClearImage` до/после фактического изменения VRAM. Для
`LoadImage` регистратор по возможности сохраняет **исходный
буфер после локализационного патча** в отдельный приватный
`gpu-NNNN-upload.bin` (до 16384 слов). Исходные значения буфера
нельзя восстанавливать из одного прямоугольника после клиппинга.

Все операции жёстко ограничены **64 записями** (максимум 32 пары).
Это защищает от безграничного сохранения мегабайтных снимков
во время игры. Если предел достигнут, результат неполный:
он не доказывает, что более поздних команд не было.

## Генерация и сборка

Из корня нашего репозитория, с локальной копией **именно
закреплённого** PC-порта:

```sh
python3 -m tools.instrument_map02_gpu_native_events \
  /private/VandalHearts-PcPort/platform/pc/src/libgpu.c \
  --output /private/pc-gpu-probe/libgpu.capture.c
```

Созданный `libgpu.capture.c` нужно подать в локальную PC-сборку
**вместо** обычного `libgpu.c`, сохраняя остальные исходники,
заголовки и настройки сборки. Дополнительно передать флаг
компиляции `-DVH_MAP02_GPU_CAPTURE`. Это ручная интеграция
в собственную локальную сборку PC-порта, не автоматическая
модификация или обход механизмов защиты оригинальной игры.

Для запуска подготовить существующий **приватный** каталог и
установить две переменные окружения:

```sh
export VH_MAP02_GPU_CAPTURE_DIR=/private/map02-gpu-capture
export VH_MAP02_GPU_CAPTURE_FRAME=411
# Затем запустить собранный локально инструментированный PC-порт
# с собственными законно полученными ресурсами игры.
```

Без обеих переменных регистратор не записывает файлы.
Число `411` — лишь пример: нужен реальный номер интересующего
вызова `DrawOTag`. Передачи VRAM регистрируются с предыдущим
значением счётчика (до входа в DrawOTag), а примитивы — с текущим.

Файлы `gpu-native-events.jsonl`, `gpu-0000-vram.bin`,
`gpu-0001-vram.bin`, ... и необязательные
`gpu-NNNN-upload.bin` являются **приватными оригинальными
игровыми данными**. Не публиковать их в GitHub, CI-логах
или открытых артефактах.

## Проверка созданного журнала

После завершения локального захвата:

```sh
python3 -m tools.verify_map02_native_gpu_capture \
  /private/map02-gpu-capture --frame 411 \
  > /private/map02-native-gpu-report.json
```

Аудитор сверяет последовательные номера и фиксированные имена
снимков, пары `before/after`, кадры, метаданные FT4 и передачи,
границы 1-МиБ файлов и допустимость загрузок. При пропущенной
половине пары, повреждённом/неполном снимке или некорректной
метке он завершает работу ошибкой.

В отчёте остаются **только хеши и агрегированные счётчики**:
события передач и отрисовки, различия VRAM после `DrawOTag`
и после передач, а также признаки неполноты захвата.
Исходные пиксели, UV, материалы и камера в отчёт не попадают.

## Сопоставление нативного FT4 с MAP02 и отдельными снимками VRAM

Для локального захвата с изменяющимися текстурами между полигонами
используется режим `--timeline` уже существующего инструмента
`tools.verify_map02_source_native_ft4_join`. Он проверяет
`timeline.json` через независимые исходные геометрию/GTE/CLUT,
а затем связывает каждый FT4 с парой нативных записей `before/after`
по точным XY, UV, tpage, CLUT и texture window.

**Важно:** номер исходного кадра и номер `DrawOTag` имеют
**разные счётчики**. Нельзя считать их равными; требуется собственный
приватный файл `gpu-face-timeline-join.json` в каталоге временной шкалы:

```json
{
  "schema": "vh.map02.source-native-ft4-timeline-join.v1",
  "source_frame": 411,
  "gpu_draw_frame": 12,
  "timeline_manifest_sha256": "<SHA-256 приватного timeline.json>",
  "native_events_sha256": "<SHA-256 приватного gpu-native-events.jsonl>"
}
```

Номера кадров приведены **только для примера**. Их надо получить из
фактического локального захвата. SHA-256 — хеши реальных, неизменённых
байтов соответствующих файлов, а не строки, показанные выше.

```sh
python3 -m tools.verify_map02_source_native_ft4_join \
  /private/map02-timeline /private/map02-gpu-capture \
  --timeline > /private/map02-native-ft4-timeline-report.json
```

Аудитор проверяет один снимок `gpu-vram-NNN.bin` **на каждую**
исходную грань и сравнивает используемые слова страницы текстуры и CLUT
со снимком `before` соответствующего нативного FT4. При несовпадении
хотя бы одного слова, отсутствии точного пакета, одинаковых
неразличимых пакетах или исчерпании лимита нативной записи результат
отклоняется. Он не предполагает одинаковый порядок CPU-отправки
полигонов и исполнения `DrawOTag`.

Инструмент выдаёт только количества и SHA-256, не публикуя снимки,
координаты, игровые данные или адреса исходных клеток. Подтверждается
**внутренняя согласованность предоставленных данных**, а не
подлинность исходной игры, полнота GPU-журнала или bit-exact PS1-пиксели.

## Ограничения проверки

- CI пока **компилирует** настоящий закреплённый `libgpu.c`
  с включённым/выключенным захватом и тестирует обработку
  **синтетического журнала**. CI не запускал оригинальную игру и
  не подтвердил захват реальной MAP02.
- Это порядок работы публичного **PC GPU backend**, а не запись
  электрических команд физического GPU PlayStation.
- Между двумя снимками примитива могли быть кратковременные
  изменения с последующим восстановлением: регистратор не пишет
  каждый вызов `PutPixel` и не претендует на безупречную полноту.
- Снимки разных операций позволяют выявлять эффект растеризации
  FT4, SPRT и TILE. Отдельный опциональный join по FT4 связывает
  совпадающие пакеты с проверенными гранями MAP02, но не доказывает
  подлинность игрового кадра или полноту потока `DrawOTag`.
- При недоступном каталоге, недостатке дискового пространства или
  ошибке записи могут возникать неполные файлы; аудитор должен
  их отклонять. Не следует использовать вывод без его проверки.
- Наличие локального GPU-дампа не доказывает PS1 bit-exact
  растеризацию, достоверность источника или готовность ремейка
  для реальной консоли Switch.

Таким образом, это **новая точка инструментирования**, которая
позволит пользователю добыть более точные доказательства поведения
GPU, когда оригинальные данные будут доступны локально.
