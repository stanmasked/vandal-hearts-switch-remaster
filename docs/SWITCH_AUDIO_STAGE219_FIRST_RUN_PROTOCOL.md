# Vandal Hearts Remake — этап №219: первый реальный запуск аудио на Nintendo Switch

> **Состояние на момент подготовки: HARDWARE NOT TESTED.**
> Этот документ — план и пустая форма фиксации реальных фактов. Здесь **нет** результатов с консоли. GitHub Actions, structural `NRO0`, совпадение SHA-256 на SD или синтетические host-тесты не заменяют аудиопроверку на устройстве.

## 0. Выбранная сборка и запрет подмены

Используйте только **основной тактический** `vandal-hearts-prototype.nro` из конкретного успешного `Switch toolchain readiness`, а не отдельную пробу SDL2, OpenAL или audout. Версию `0.1.0` нельзя использовать как идентификатор бинарника: фиксируйте **полные 40 символов Git SHA, run ID, artifact ID и SHA-256 NRO**.

1. Проверьте NRO и ZIP по [этапу №216](SWITCH_AUDIO_STAGE214_DEVICE_HANDOFF.md#7-этап-216--офлайн-сверка-nro-с-конкретным-github-actions-artifact).
2. Непосредственно перед переносом выполните [этап №217](SWITCH_AUDIO_STAGE214_DEVICE_HANDOFF.md#8-этап-217--онлайн-проверка-актуального-head-перед-передачей-nro), чтобы не считать старый коммит нынешним HEAD ветки. Ранее зафиксированный исторический NRO можно исследовать отдельно, но не заявлять как актуальную сборку.
3. Подготовьте `plan` и проведите [двустороннюю SHA-256-сверку SD-переноса №218](SWITCH_AUDIO_STAGE214_DEVICE_HANDOFF.md#9-этап-218--контроль-sha-256-до-и-после-ручного-копирования-nro-на-sd). **Не меняйте файлы на SD в процессе верификации.**
4. Запишите результат `MATCHED_CURRENT_HEAD_AT_CHECK_TIME` / `DESTINATION_BYTES_MATCH_PLANNED_NRO` в отдельную карточку — это **не** подтверждает запуск.

Заранее запишите вывод звука и режим homebrew (Application/applet), версию HOS/libnx, свободное место на SD и точные условия воспроизведения. Основной прототип может использовать синтезированную музыку вместо оригинальных игровых ресурсов; этот этап проверяет **аудиовывод и жизненный цикл**, а не соответствие оригинальному саундтреку PlayStation.

## 1. Первый запуск: чистый старт и запись CSV (H01)

1. Запустите тестовый NRO **на физической консоли** через разрешённый homebrew-режим. Отметьте, загрузилась ли тактическая сцена, активны ли управление и звук.
2. Нажмите **Minus** для показа панели диагностики, затем **Y** для запуска записи. Не считайте появление панели доказательством слышимого звука — прослушайте динамики или выбранный HDMI/наушники.
3. Отдельно отметьте, слышна ли музыка, стабильны ли тембр/громкость, наблюдаются ли щелчки, обрывы, пропущенные ноты, повторяющиеся заикания. Запишите положение громкости и режим вывода.
4. Не останавливая запись, перейдите к проверкам HOME и сна. Делайте заметки в реальном времени: какие события случились и как долго приходил в норму слышимый звук.
5. Завершите игру штатно **Plus**. Выключать питание или вытаскивать SD для тестирования экспорта **нельзя**. Файл `audio-diagnostics-XXXX.csv` сохраняется в `sdmc:/switch/vandal-hearts-remake/` **после** остановки и соединения аудиопотока; не принимайте `.tmp` за готовый отчёт.
6. Скопируйте **исходный неизменённый** CSV, запишите SHA-256 и сравните хеш после повторного чтения файла с SD.

Выполните **два независимых запуска** с двумя разными CSV и минимум **1000 наблюдаемыми страницами PCM на CSV**. Наличие двух разных файлов/хешей само по себе не доказывает независимость запусков — это подтверждает заполненная человеком карточка.

## 2. HOME и сон (H02/H03)

HOME и физический сон — **разные сценарии**; не объединяйте их счётчики.

- **H02: минимум 10 возвратов HOME → игра.** При активной музыке откройте HOME и вернитесь. После каждого раза оцените слышимый выход: есть ли задержка, пауза, выпадение нот, щелчок, зависание. Запишите собственное число возвратов (можно распределить по двум сеансам). Сопоставьте с изменениями `home_resumes`/ `home_fail` в CSV, учитывая возможное вытеснение старых событий.
- **H03: минимум 5 сон → пробуждение.** В рамках отдельного безопасного сценария штатно отправьте Switch в сон, пробудите, вернитесь в игру и проверьте звук. Запишите количество, приблизительную слышимую задержку и режим вывода. **Текущий CSV не различает физический сон и обычный возврат HOME**; число циклов сна подтверждается только журналом испытателя.

При сбое воспроизведения зафиксируйте **момент и последовательность действий**. Самостоятельный перезапуск приложения для восстановления возможен, но тогда это **новая сессия**, а не продолжение прежней.

## 3. Длительный прогон и сохранность SD (H04/H05)

**H04:** выполните хотя бы один непрерывный тест прослушивания длиной **30–60 минут**, не приписывайте продолжительность из короткого кольцевого CSV. Журнал содержит не более 128 последних снимков: первая строка — исходное состояние окна, а не начало всех событий сессии.

**H05:** перед следующим запуском зафиксируйте SHA-256 **ранее сохранённого** CSV на SD, после следующего штатного запуска прочитайте тот же старый файл и сравните SHA-256. Отдельно получите **новый номерной CSV**. Два совпавших вручную введённых хеша не доказывают независимость измерений — сохраняйте контекст и скриншоты/заметки.

Опасный тест внезапного отключения питания/извлечения SD не проводится. H06 допускается только безопасным способом на отдельном тестовом носителе; H07 нужен лишь для сравнения **двух разных сборок**.

## 4. Строгий анализ сырых CSV

Сложите **только NRO и подлинные CSV** в отдельный каталог:

```text
switch-audio-real-run-219/
  nro/vandal-hearts-prototype.nro
  session-01/audio-diagnostics-0000.csv
  session-02/audio-diagnostics-0001.csv
```

Создайте и проверьте хеш-манифест (полный SHA действительно протестированной сборки):

```sh
python3 tools/verify_switch_audio_bundle.py create switch-audio-real-run-219 \
  --git-sha ACTUAL_FULL_40_HEX_GIT_SHA \
  --ci-run-url https://github.com/stanmasked/vandal-hearts-switch-remaster/actions/runs/ACTUAL_RUN_ID \
  --nro nro/vandal-hearts-prototype.nro \
  --session session-01/audio-diagnostics-0000.csv \
  --session session-02/audio-diagnostics-0001.csv

python3 tools/verify_switch_audio_bundle.py verify switch-audio-real-run-219
python3 tools/report_switch_audio_hardware.py switch-audio-real-run-219 \
  --format json > /path/outside-evidence/telemetry-review-219.json
```

`INCOMPLETE`, `INVESTIGATE` или ошибки разбора требуют отдельного расследования. `NO_OBSERVED_FAULTS` и `ENOUGH_DATA_FOR_MANUAL_REVIEW` — не сертификаты слышимого качества. Не изменяйте реальные CSV для получения желаемого результата.

## 5. Сопоставление с ручной карточкой (новое для №219)

1. На каждый физический запуск заполните [ручную карточку](SWITCH_AUDIO_STAGE212_SESSION_TEMPLATE.md), включая время, HOME, сон, слышимые дефекты, повторное чтение старого CSV.
2. Скопируйте [пустой JSON-шаблон](SWITCH_AUDIO_STAGE219_OPERATOR_TEMPLATE.json) **вне** папки `switch-audio-real-run-219`; замените placeholders на реально проверенные Git SHA/SHA-256 и пути зарегистрированных CSV. При неизвестном результате пишите `UNKNOWN` либо `null` — **не придумывайте нули, минуты или PASS**.
3. **В схеме v2** обязательно добавьте `prior_csv_path` — относительный путь **первой** CSV-сессии из манифеста, например `session-01/audio-diagnostics-0000.csv`. Старый v1 с одинаковыми хешами, но без привязки к CSV, остаётся `INCONCLUSIVE`. Подробности и контроль противоречий описаны в [этапе №220](SWITCH_AUDIO_STAGE220_CONSISTENCY_GATES.md).
4. Для полей `home_returns` / `sleep_resumes` / `continuous_minutes` введите **фактические наблюдения оператора**. Значения в CSV не подтверждают полную физическую длительность. Для `prior_csv_sha256_before` и `prior_csv_sha256_after` используйте замеры одного и того же **старого** CSV на SD; если измерений нет, оба поля `null`.

```sh
python3 tools/assess_switch_audio_first_run.py switch-audio-real-run-219 \
  --observations /path/outside-evidence/first-run-operator.json \
  > /path/outside-evidence/first-run-review.json
```

Результаты нового инструмента:

| Результат | Что означает |
| --- | --- |
| `READY_FOR_INDEPENDENT_MANUAL_REVIEW` | Оператор **заявил** достаточные H01–H05 наблюдения, зарегистрированные CSV структурно пригодны и критических неисследованных признаков не найдено. **Не аппаратный PASS.** |
| `INCONCLUSIVE` | Нет данных, неполное выполнение сценариев, некорректный EXIT или недостаточно измерений |
| `INVESTIGATE` | Заявлен дефект звука, повреждение старого CSV, отказ/сбой HOME/PCM, возможная остановка |
| `INVALID_EVIDENCE`, код `2` | Повреждённое/подменённое свидетельство, чужой NRO, неучтённый CSV либо неверная структура JSON |

Нормальный код `0` означает **только успешное составление отчёта**. Во всех случаях `hardware_status: HARDWARE NOT TESTED` — это статус **независимой машинной проверки**, не отрицание того, что оператор мог фактически провести тест. Инструмент **не может подтвердить личность оператора, наличие Switch, независимость физических сеансов и подлинность человеческих наблюдений**. Финальное решение оформляется отдельно человеком.

25 host-only регрессий [`tests/test_assess_switch_audio_first_run.py`](../tests/test_assess_switch_audio_first_run.py) используют **синтетические** CSV и NRO-заголовки, не игровые ресурсы или физическую Switch. Включены в `make test` и `make test-audio-stream`.

## 6. Критерий завершения этапа №219

**Программная готовность** означает опубликованный протокол, валидатор, тесты и CI. **Аппаратное завершение** возможно лишь после отдельного подтверждённого реального запуска, заполненных карточек и двух исходных CSV со Switch. До этого не писать `PASS` в журнале проекта и не публиковать синтетические логи как аппаратные.


## 7. Этап №220 — контроль противоречивости

Перед отдельным человеческим решением проверьте `consistency_findings` из [руководства №220](SWITCH_AUDIO_STAGE220_CONSISTENCY_GATES.md). Даже `FILE_BOUND_OPERATOR_HASHES_MATCH` означает только согласованность заявленных хешей с проверенным файлом, **не** физическое доказательство сохранности SD.

## Этап №232 — связь предзапускового NRO с реальными CSV

Для доказуемой **согласованности исходных файлов** после испытаний добавлен [этап №232](SWITCH_AUDIO_STAGE232_DEVICE_EVIDENCE_BINDING.md) — `tools/link_switch_audio_device_evidence.py`. Он сопоставляет две host-квитанции №231 (с их независимо сохранёнными SHA-256), версию и номер GitHub Actions run, NRO в расширенном evidence bundle и настоящие CSV/карточки по аудиту №222. Поскольку после испытания bundle содержит новые CSV, SHA-256 всего манифеста **не обязан совпадать** с предзапусковым; сверяются сам NRO, Git-коммит, CI run и хеши первичных CSV. Противоречивые даты и результаты помечаются для расследования. Успех — только `READY_FOR_INDEPENDENT_MANUAL_REVIEW`, никогда аппаратный PASS; `HARDWARE NOT TESTED` остаётся.

## Этап №233 — безопасное получение сырых CSV с SD

Для подготовки фактических материалов первого запуска разработан [импорт №233](SWITCH_AUDIO_STAGE233_RAW_SD_CAPTURE.md) через `tools/capture_switch_audio_sd_csv.py`. Утилита сверяет NRO с исходным планом SD №218, **только читает** выбранные номерные CSV из `switch/vandal-hearts-remake/`, отказывается от `.tmp` и некорректных/меняющихся файлов, переносит первичные байты в новый отдельный bundle с манифестом SHA-256 и повторно сверяет источник. Режим `verify` сравнивает готовый bundle со свежими чтениями той же SD, не меняя оригиналы. Для дальнейшего аудита №219–232 по-прежнему нужны реальные карточки сессий и независимая физическая проверка звука. `HARDWARE NOT TESTED` остаётся без настоящего запуска консоли.
