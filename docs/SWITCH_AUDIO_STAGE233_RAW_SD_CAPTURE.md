# Vandal Hearts Remake — этап №233: безопасное получение сырых CSV с SD

**HARDWARE NOT TESTED.** Этот инструмент работает только с файлами компьютера и с путём, который оператор обозначил как подключённую SD-карту. Он не подтверждает, что там действительно находится карта Nintendo Switch, что игра исполнялась на устройстве или что музыка была слышна.

## Проблема

В [протоколе реального запуска №219](SWITCH_AUDIO_STAGE219_FIRST_RUN_PROTOCOL.md) после двух независимых испытаний необходимо перенести номерные `audio-diagnostics-XXXX.csv` с `sdmc:/switch/vandal-hearts-remake/` в отдельную неизменяемую папку, приложить **именно тот NRO**, который находился в установленной сборке, и создать проверяемый SHA-256-манифест.

Ручное копирование легко допускает неполный `.tmp`, повреждение CSV, неправильное соответствие NRO и журнала или замену старых файлов. Новый [`tools/capture_switch_audio_sd_csv.py`](../tools/capture_switch_audio_sd_csv.py) выполняет ограниченное копирование **только выбранных оригинальных файлов**, повторно проверяет SHA-256 каждого файла и формирует готовую структуру bundle №213.

## Перед началом

1. Используйте оригинальный NRO из конкретной сборки GitHub Actions, уже проверенный через [№230](SWITCH_AUDIO_STAGE230_PRELAUNCH_GATE.md). Сохраните исходный `source-bundle`, его манифест с полным Git SHA/CI run URL, а также `sd-transfer-plan.json` за пределами SD.
2. На **физической Switch**, если она доступна, пройдите [№219](SWITCH_AUDIO_STAGE219_FIRST_RUN_PROTOCOL.md): штатный Plus-выход, два отдельных запуска с настоящими CSV, HOME/сон и наблюдение слышимого звука.
3. Безопасно завершите запись CSV, штатно отключите/извлеките SD и подключите её к компьютеру. Не извлекайте носитель во время игры или операции записи.
4. Проверьте, что выбранные файлы имеют точные номерные имена, например `audio-diagnostics-0000.csv` и `audio-diagnostics-0001.csv`. **Не используйте файл `.tmp`** как завершённую диагностику.

### Первый шаг — создать новый комплект только из сырых данных

```sh
python3 tools/capture_switch_audio_sd_csv.py capture \
  --source-bundle /safe/original-source-bundle \
  --sd-root /Volumes/ACTUAL_SWITCH_SD \
  --transfer-plan /safe/outside/sd-transfer-plan.json \
  --csv audio-diagnostics-0000.csv \
  --csv audio-diagnostics-0001.csv \
  --output /safe/outside/real-switch-audio-evidence-233 \
  > /safe/outside/capture-review-233.json
```

Названия и количество CSV в примере **не подтверждают**, что такие сессии реально проводились. Используйте точные имена своих файлов и не смешивайте CSV разных сборок без ручной проверки происхождения.

Что происходит: программа повторяет №218 для NRO по исходному плану; читает *выбранные* CSV из `switch/vandal-hearts-remake/` под SD-root; отвергает символьные ссылки, неправильные имена, незавершённые `.tmp` и некорректные данные CSV; вычисляет исходные SHA-256; копирует NRO и CSV **в новый временный каталог вне SD**; перечитывает каждый источник и назначение, создаёт манифест №213 и проверяет всю структуру; публикует **новый** каталог только после успешной проверки.

Результат размещается следующим образом:

```text
real-switch-audio-evidence-233/
  audio-evidence-manifest.json
  nro/vandal-hearts-prototype.nro
  session-01/audio-diagnostics-0000.csv
  session-02/audio-diagnostics-0001.csv
```

- Порядок `--csv` — **явное решение испытателя**, он задаёт `session-01`, `session-02`. Программа не знает, какая сессия была первой физически.
- Другие CSV на SD не удаляются и не присваиваются автоматически этой сборке.
- Если конечный каталог уже существует, он **не перезаписывается**.
- Скрипт не записывает ничего на SD и не изменяет первоначальный `source-bundle`.

## Второй шаг — независимое повторное чтение оригинальных CSV

Пока та же SD подключена и доступна, повторите контроль исходных байтов:

```sh
python3 tools/capture_switch_audio_sd_csv.py verify \
  --source-bundle /safe/original-source-bundle \
  --sd-root /Volumes/ACTUAL_SWITCH_SD \
  --transfer-plan /safe/outside/sd-transfer-plan.json \
  --captured /safe/outside/real-switch-audio-evidence-233 \
  > /safe/outside/capture-second-readback-233.json
```

Команда повторно проверяет копии, NRO, исходный план и **перечитывает оригинальные CSV** с SD. Если один байт изменился, компьютер возвращает `INVALID_EVIDENCE`. Сама проверка **не подтверждает**, что два чтения произошли после физического переподключения — для этого есть отдельная процедура №231, с теми же ограничениями.

При успехе выдаётся `CAPTURED_RAW_BYTES_MATCH_FRESH_SD_READBACK`. Код `0` означает только согласованность файлов. **Не объявляйте аппаратный PASS или независимость двух запусков** по этим хешам.

## Как продолжить аудит

1. Проверить полученный bundle: `python3 tools/verify_switch_audio_bundle.py verify /safe/outside/real-switch-audio-evidence-233`.
2. Заполнить **вне папки bundle** оригинальный `operator-v2.json` и **отдельные JSON-карточки** №222: указать настоящий номер CSV, времена запуска, слышимый звук, число HOME/сна и фактическую длительность.
3. Выполнить [аудит №222](SWITCH_AUDIO_STAGE222_HARDWARE_HANDOFF.md), затем [привязку №232](SWITCH_AUDIO_STAGE232_DEVICE_EVIDENCE_BINDING.md) к исходным предзапусковым записям №231 (если они были сохранены), и только после этого оформить независимое ручное заключение.

Синтетические host-тесты ничего не говорят о физических сигналах Nintendo Switch: статус всего комплекта остаётся `HARDWARE NOT TESTED`.

## Ограничения безопасности и регрессии

Экспорт принимает до 64 выбранных CSV, каждый не больше 4 МиБ; поддерживает только номерные `audio-diagnostics-XXXX.csv`, отклоняет `.tmp`/частичные аудиофайлы, меняющиеся байты и исходный NRO, не соответствующий плану, и ограничивает общий размер копирования. Отдельная папка создаётся после предварительных проверок; при ошибке временные копии удаляются.

[23 синтетических регрессионных теста](../tests/test_capture_switch_audio_sd_csv.py) проверяют точную копию NRO/CSV, свежий readback, незавершённый `.tmp`, некорректные CSV, пустые файлы, symlink/traversal, неправильные имена/дубликаты, повреждение NRO/манифеста и источник, меняющийся во время копирования. Они включены в `make test` и `make test-audio-stream` без реальной SD или игровых ресурсов.

## Этап №234 — контроль сохранности исходного CSV между запусками (H05)

Перед **следующим реальным запуском** можно сохранить [контрольную точку H05 №234](SWITCH_AUDIO_STAGE234_H05_CSV_PERSISTENCE.md): `tools/verify_switch_audio_h05_csv_persistence.py record` фиксирует SHA-256 старого оригинального CSV и полный список уже существовавших номерных CSV на указанной SD. После штатного второго запуска `recheck` требует **независимый SHA-256 карточки**, неизменность прежних файлов и появление **выбранного нового завершённого CSV, которого не было раньше**. Проверка не записывает на SD, не подтверждает реальность второго физического запуска или звук и сохраняет `HARDWARE NOT TESTED`. После H05 для импорта данных используйте этап №233, для полноценной оценки — аудит №222/232.
